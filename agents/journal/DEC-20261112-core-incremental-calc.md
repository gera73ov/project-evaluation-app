## Решение

1. **Ответ правки считается инкрементально.** `mutation_view` (PATCH `/nodes/{id}`,
   POST `/projects/{id}/nodes`) больше не читает все узлы и не прогоняет полный расчёт.
   Экземпляр API держит в памяти состояние расчёта проекта с версией проекта
   (`services/tree/calc_cache.py`, до 32 проектов, не старше 5 минут) и пересчитывает только
   изменённые узлы, их прежних и новых родителей и предков (`domain/calc/incremental.py`).
2. **Несколько реплик.** Состояние догоняет версию в БД по `change_log`: после своей версии
   экземпляр читает события. Если там только `node.updated` и `node.created` (узел `data.node.id`)
   и события, не влияющие на часы (сообщения, обсуждения, вопросы заказчику, состав команды,
   деньги, проверка документа), он перечитывает из БД только эти узлы. Иначе — полная постройка,
   как раньше: перенос, удаление, восстановление, статус ветки, параметры проекта, пропуск версии,
   хвост длиннее 200 событий, другой отпечаток фаз, дисциплин, статусов веток и параметров проекта.
3. **Откат.** Состояние запоминается только после commit (хук `after_commit`): иначе после отката
   ту же версию получила бы другая транзакция.
4. **Ответ не изменился.** Итоги проекта считает общий `summarize` (его же вызывает `calculate`),
   сумма родителя складывается в порядке `rollup`. Без переносов результат совпадает с полным
   расчётом знак в знак (тест на случайных деревьях); с переносом меняется только порядок
   сложения соседей. Флажки ◆/↔ узла считаются по самому листу (`leaf_candidate`), как в
   `decomposition`. Метрика `estimator_calc_cache_total{result=hit|delta|rebuild}`.

Контракт и SPEC не меняются.
