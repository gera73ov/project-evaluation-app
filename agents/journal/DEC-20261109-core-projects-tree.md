# DEC-20261109-core-projects-tree

- **Тип:** решение (DEC), уровень A1
- **Время:** 2026-11-09T11:40:00Z
- **Трек:** CORE (CORE-010, CORE-014, CORE-027), ADM (ADM-008), NTF (NTF-003); потребители — FE-011…FE-022,
  CORE-011…CORE-033, RT-007
- **Основание:** SPEC 5.1, FR-PRJ-01, FR-PRJ-05, BR-CALC-05, BR-TREE-06, 14.2, 14.3, 7.5, GAP-03, Q-43,
  FR-NOTIF-01; contracts/openapi.yaml, contracts/notifications.yaml

## Контекст

SPEC и контракты не фиксируют несколько деталей, от которых зависят следующие задачи трека и клиент.

## Решение

1. **Фазы проекта.** При создании в `project_phases` пишутся строки для всех активных фаз справочника;
   невыбранные — `is_enabled = false` (их можно включить в настройках). Узел-фаза создаётся для
   включённой фазы; при выключении узел-фаза остаётся, а ветки фазы со всеми детьми уходят в корзину
   одним пакетом (`deleted_batch_id`). При повторном включении создаются новые ветки дисциплин проекта
   со статусом «не начато». Сквозная фаза «Управление проектом» включается всегда и получает узел —
   строку УП в конце дерева (11.4 №15).
2. **База УП по умолчанию** — все фазы работ, кроме фазы справочника с названием «Гарантийная
   поддержка» (BR-CALC-05 называет её по имени); сквозная фаза в базу не входит.
3. **Версия проекта** нового проекта — 1 (создание — первое изменение); `PATCH` без изменений версию
   не повышает. Каждое изменение настроек: `projects.version++` одной командой `UPDATE … RETURNING`,
   запись `change_log` с событием `project.updated`, запись журнала `project.settings`.
4. **Позиции соседей** — дробные ключи с целой частью переменной длины (алгоритм fractional-indexing:
   `a0`…`az`, `b00`…): дописывание в конец растит ключ логарифмически, вставка между соседями —
   без перенумерации. Порядок корней дерева задаёт `phases.sort_order`, а не `position`.
5. **CSV календаря** data.gov.ru содержит строки нескольких лет: загружается самый поздний год
   (обычно календарь следующего года). Поле формы `dry_run` читается строкой: FastAPI считает
   отсутствующее булево поле формы `false`, а по контракту по умолчанию `true`.
6. **Уведомления:** каталог видов продублирован в `notifications/inapp` (`KINDS`), тест сверяет его с
   contracts/notifications.yaml. Получатель проектного уведомления — активный участник проекта, которому
   проект виден по статусу (в «Подготовке» — модератор); исключение — `project_without_moderator`
   (администраторы без членства).
7. **Создатель-администратор.** Если у создателя проекта есть системная роль «Администратор», его
   членство помечается `added_by_admin_self` (Q-25, BR-ADM-03).

## Последствия

CORE-013 (дисциплины) создаёт ветки во всех включённых фазах по тем же правилам позиций; CORE-015
пользуется `services/tree/positions.key_between`; CORE-033 считает дедлайн через
`admin.calendar.working_days`. Изменение любого пункта — новой записью DEC.
