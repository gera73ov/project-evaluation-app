# DEC-20261112-core-tree-response

- **Тип:** решение (DEC), уровень A1
- **Время:** 2026-11-12T04:20:00Z
- **Трек:** CORE (CORE-014); потребитель — QA-020
- **Основание:** NFR-PERF-02; замер QA-020 на домашнем стенде до #128: открытие 2 000 узлов p95
  2,16 с (норма 2 с), 5 000 узлов p95 4,54 с (норма 4 с); из них ответ `GET /projects/{id}/tree`
  793 мс и 2,70 с.

## Что съедало время (5 000 узлов, один процесс)

Полный расчёт на каждый запрос (~110 мс), сборка 5 000 строк ответа (~100 мс), проверка ответа
pydantic и его сериализация (~60 мс), паузы сборщика мусора — полные сборки по всей куче посреди
запроса (до 200 мс). Плюс 3,5 МБ JSON без сжатия: на 100 Мбит это ~280 мс передачи.

## Решение

1. **Расчёт из кэша #124, сверка по строкам.** `load_tree` всё равно читает все живые узлы, поэтому
   журнал событий ему не нужен: `calc_cache.state_for_rows` сравнивает каждую строку с отпечатком,
   из которого посчитано состояние (`row_key`: родитель, вид, фаза, дисциплина, тип, название,
   O/R/P, множитель). Совпали все — состояние как есть; есть новые или изменённые — `refresh` только
   их и предков; узел исчез — полная постройка. Ответ всегда согласован с прочитанными строками,
   даже если строку изменили мимо `change_log`. Метрика та же, `estimator_calc_cache_total`.
2. **Расчётная часть строки — один раз на результат узла.** `CalcState.memo` хранит готовый словарь
   полей узла, зависящих от расчёта и самой строки; запись годна, пока результат узла — тот же
   объект и порог «крупного листа» тот же. Поля, которые меняются без пересчёта (версии полей,
   комментарии, проверка, счётчики обсуждений), собираются заново каждый раз.
3. **Ответ без повторной проверки.** `load_tree` собирает ответ из примитивов JSON по схеме `Tree`;
   эндпоинт отдаёт `json.dumps` как есть. `response_model` остаётся для OpenAPI; совпадение с
   проверкой и выдачей pydantic проверяет `test_tree_body_matches_schema`.
4. **Сборщик мусора.** При старте приложения объекты старта замораживаются (`gc.freeze`), пороги
   поколений — `(10 000, 20, 20)` вместо `(2 000, 10, 10)` (`main.tune_gc`).
5. **gzip только для ответа дерева в Nginx.** В ответе дерева нет секретов (токенов, CSRF), так что
   атака по длине сжатого ответа (BREACH) ничего не даёт; остальной API не сжимается, как раньше.

Итог в тесте на 5 000 узлах: `load_tree` ~400 → ~110 мс. Контракт и SPEC не меняются.
