# DEC-20261110-core-discussions-lifecycle

- **Тип:** решение (DEC), уровень A1
- **Время:** 2026-11-10T11:20:00Z
- **Трек:** CORE (CORE-041, CORE-042, CORE-043), контракт CR-012. Потребители: FE-030 (лента,
  «Решено», история), ADM-012 (переадресация вопросов), RT (`thread.resolved/reopened`,
  `message.updated`).
- **Основание:** SPEC FR-DISC-05…07, FR-TREE-34, FR-ADM-05, 14.2 `message_history`, 4.4;
  contracts/openapi.yaml (`resolveThread`, `reopenThread`, `editMessage`, `revokeMessage`).

## Решение

1. **«Решено» и «Переоткрыть» (CORE-041).**
   - Право `thread.resolve` проверяется на вопросе. Модератор может любой вопрос, эксперт и
     пресейл — только вопрос, где они автор или адресат. Адресаты разворачиваются до
     пользователей, как в «вопрос мне».
   - Gate пускает и по `cq.close`/`cq.reopen`, поэтому обработчик дополнительно проверяет
     `thread.resolve`.
   - Повторное закрытие или переоткрытие → 409 `INVALID_TRANSITION`.
   - Вопросы заказчику здесь → 409: их закрытие и переоткрытие — CORE-044.
2. **Вывод в комментарий.**
   - `conclusion` добавляет строку `{tag_id, text}` в конец `comment_lines` узла вопроса.
   - Это обычная правка узла: история, версия, проверки R-03, уведомление экспертов
     (FR-TREE-34), серое событие.
   - Нужно право `comment.write` на узле.
   - У вопроса проекта вывода нет → 422.
3. **Правка и отзыв (CORE-042).**
   - Действует только автор и только на обычное сообщение; чужое → 403.
   - Ответом считается более позднее сообщение другого автора:
     - для сообщения в вопросе — в этом же вопросе;
     - для сообщения без вопроса — в той же ленте узла или проекта.
     - Серые события ответами не считаются.
   - После ответа правка → 409 `MESSAGE_HAS_REPLIES`, отзыв доступен.
   - Вопрос заказчику после `new` автор не правит → 403 (BR-CQ-01).
   - Каждая правка и отзыв пишут прежний текст в `message_history` (`edit`/`revoke`).
   - Правка тем же текстом ничего не пишет. Повторный отзыв — 200 без изменений.
   - Отозванное сообщение не правится.
4. **История для модератора (CR-012).** Контракт не давал прочитать `message_history`, поэтому
   добавлен `GET /messages/{id}/history` с правом `discussion.history` только у модератора
   проекта (рекомендованный вариант карточки).
5. **Серые события (CORE-043).**
   - Запись `kind = event`: `body = ""`, автор — кто изменил. Структура лежит в `event`:
     - `node_changed` — поля O/R/P, ×N, комментарий, тип; название остаётся только в истории;
     - `node_moved` — смена родителя;
     - `question_redirected` — `thread_id`, `from`, `to` (UserRef).
   - Значения записываются как в истории узла. Текст строки собирает клиент.
   - Событие появляется, только если у узла есть хотя бы одно сообщение (не событие).
   - Каждое публикуется как `message.created` со своей версией.
   - Серые события входят в `messages_count`, но не в `replies_count`.
6. **API для ADM-012.**
   - `events.redirect_questions(db, project_id, from_user, to_user, actor_id)` заменяет
     адресата-пользователя в открытых вопросах. Если замена уже есть среди адресатов, исходный
     адресат просто убирается.
   - В ленту каждого вопроса пишется событие «вопрос переадресован».
   - Возвращает id вопросов для уведомления `question_redirected`. Решённые вопросы не трогает.
   - `events.add_event(...)` — общий вход для других сервисов.
