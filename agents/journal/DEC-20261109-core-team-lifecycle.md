# DEC-20261109-core-team-lifecycle

- **Тип:** решение (DEC), уровень A1
- **Время:** 2026-11-09T12:00:00Z
- **Трек:** CORE (CORE-011, CORE-012, CORE-013); потребители — FE-020…FE-022, RT-008, ADM-012, NTF-006
- **Основание:** SPEC 4.2, 4.4, FR-PRJ-01, FR-PRJ-04, FR-PRJ-05, BR-PRJ-01, BR-PRJ-03, BR-PRJ-04,
  BR-PRJ-07, BR-ROLE-04..08, FR-ADM-05, BR-ADM-03, Q-25, 5.1, FR-TREE-04; contracts/openapi.yaml,
  permissions.yaml (D-04), notifications.yaml, ws-events.schema.json

## Контекст

SPEC задаёт переходы статуса, правила команды и дисциплин, но не фиксирует несколько деталей, от
которых зависят клиент и соседние треки.

## Решение

1. **Предупреждения перехода** (`StatusChangeResult.warnings`) считаются на сервере по состоянию до
   перехода и отдаются в ответе; ненулевые только: запуск оценки — `disciplines_without_expert`;
   к сведению — `branches_not_done` (ветки «не начато» и «черновик» во включённых фазах работ);
   завершение — `branches_not_done`, `open_customer_questions`, `no_snapshot`. Диалог подтверждения
   клиент строит сам по дереву и команде (FR-PRJ-05).
2. **Открытый вопрос заказчику** — в состояниях «новый», «отправлен», «отвечен» (4.4: «решён» и
   «снят» — закрытые).
3. **«Восстановить» (Архив → Завершена)** ставит `completed_at` заново и снимает `cancel_reason` и
   `archived_at`: иначе ночная автоархивация (BR-PRJ-03) вернула бы проект в архив сразу.
4. **Причина** нужна только для «Оценка → Архив»; в других переходах поле `reason` не используется.
5. **Одна версия — одно событие.** `change_log` хранит одно событие на версию, поэтому действие с
   несколькими событиями (`node.created` на каждую ветку, `member.updated` по видам изменения,
   `project.updated`) повышает `projects.version` на каждое событие (`services.common.emit`).
6. **`project.updated.changes.disciplines`** — полный список `{discipline_id, profile_id}` дисциплин
   проекта (при добавлении, удалении и смене профиля).
7. **Команда, `PUT`.** Системные роли проверяются только у новых строк (уже назначенные остаются,
   BR-ROLE-08). Новых модераторов назначают из пользователей с ролью «Модератор»; руководитель
   пресейла — только сам, через CORE-071. Заблокированного и анонимизированного назначить нельзя
   (422). `LAST_MODERATOR` — если в новом составе нет ни одной строки модератора. Дубликат строки
   «пользователь × роль × дисциплина» — 409 `ALREADY_EXISTS`.
8. **`member.updated`**: `added` — новые пользователи, `removed` — пользователи, у которых не осталось
   ни одной строки (по нему RT-008 отзывает доступ, BR-ROLE-06), `updated` — остальные изменённые.
9. **«Вас назначили»**: модераторам — сразу; экспертам, ревьюерам и пресейлу — сразу, если проект не
   в «Подготовке», иначе при запуске оценки. Отметка — `project_members.notified_at` (по ней NTF-006
   отправит письмо).
10. **Замена в проекте** (модератор, FR-ADM-05) — только заблокированного участника; замена получает
    те же строки. Переадресация открытых вопросов подключится в ADM-012 после CORE-040
    (`redirected_threads = 0`).
11. **`no_moderator_since`** пересчитывается после изменений команды: нет активного модератора —
    ставится момент и всем администраторам уходит «Проект без модератора» (один раз до появления
    активного модератора).
12. **Удаление дисциплины** (все ветки пустые): пустые ветки уходят в корзину одним пакетом
    (`node.deleted`), строки `branch_status` удаляются, назначения экспертов на эту дисциплину
    снимаются с аудитом `project.team.changed`.
13. **Профиль по умолчанию** — `disciplines.default_profile_id`, иначе первый профиль дисциплины по
    названию; дисциплина без профилей — 422.

## Последствия

RT-008 слушает `member.updated` с `change = removed`. NTF-006 рассылает письма по строкам с
`notified_at`. ADM-012 подключит переадресацию вопросов в `team.replace_member`. Изменение любого
пункта — новой записью DEC.
