# Инструкция службы эксплуатации ИТ

Приложение оценки проектов, SPEC 18.2–18.4. Инструкция для тех, кто ставит, обновляет,
резервирует и восстанавливает приложение на stage и prod. Работа внутри приложения (настройки,
пользователи, безопасность) описана в [руководстве суперадминистратора](superadmin.md).

## 1. Зоны ответственности

Решение Q-28 (SPEC 18.2):

| Кто | Что |
|---|---|
| Служба эксплуатации ИТ | серверы, ОС, Docker, PostgreSQL, сеть и TLS-сертификат приложения, резервные копии и восстановление, консольные команды `estimator …`, рабочие ключи (мастер-ключ и пароль копий), мониторинг |
| Служба ИБ | запечатанные копии ключей в сейфе, согласование `project purge`, приём событий аудита в SIEM |
| Суперадминистратор приложения | мастер первичной настройки, режим входа (приложение или AD), политики безопасности, почта, SIEM, сроки хранения, администраторы |

Каждый запуск консольной команды записывается в журнал аудита приложения.

## 2. Состав

Один сервер с Docker 24+ и compose. Сервисы `deploy/compose/docker-compose.yml`:

| Сервис | Назначение |
|---|---|
| `nginx` | единственная точка входа: HTTPS (TLS 1.2/1.3), статика интерфейса, прокси REST и WebSocket |
| `api` ×2 | приложение (FastAPI, Uvicorn); две реплики за Nginx, события между ними — через Redis |
| `worker` | фоновые задачи Celery: выгрузки, письма, проверка документов, синхронизация AD |
| `beat` | расписание задач; всегда один экземпляр (блокировка в Redis) |
| `postgres` | PostgreSQL 16 с pgBackRest (образ `deploy/docker/postgres.Dockerfile`) |
| `redis` | сессии, блокировки ячеек, очередь задач, обмен событиями между репликами |
| `clamav` | антивирус для документов заказчика |
| `migrate` | одноразовый запуск `estimator migrate` перед стартом приложения |
| `prometheus` | метрики и оповещения (профиль `monitoring`) |

PostgreSQL можно держать и на отдельном сервере БД службы эксплуатации (решение Q-47). Тогда
`DATABASE_URL` указывает на него, `DATABASE_SSLMODE=verify-full`, а сервис `postgres` из compose
не запускается.

Тома с данными: `pgdata` (БД), `documents` (документы заказчика, уже зашифрованы), `exports`
(выгрузки, живут 24 часа), `backups` (копии), `backupmark` (файл-метка последней копии).

## 3. Установка на stage и prod

1. Подготовить сервер: Docker с compose, пользователь `estimator` с доступом к `docker`, каталог
   `/opt/estimator` с рабочей копией репозитория нужной версии (тег релиза).
2. Выпустить ключи и положить их в Docker secrets стенда (раздел 6):
   - `estimator generate-key` выдаёт мастер-ключ (`ENCRYPTION_KEY`);
   - пароль репозитория копий (`BACKUP_CIPHER_PASSWORD`) — случайная строка не короче 32 символов;
   - пароли PostgreSQL и Redis.
   Запечатанные копии мастер-ключа и пароля копий в тот же день передать в сейф ИБ.
3. Создать `.env` по `.env.example` (полный список переменных — [README.md](../README.md#переменные-окружения)).
   Для stage и prod обязательно:
   - `APP_ENV=prod` (на stage — `stage`), `APP_VERSION` — тег релиза;
   - `APP_BASE_URL=https://<адрес приложения>` и `TRUSTED_HOSTS=<адрес приложения>`;
   - `FORWARDED_ALLOW_IPS` — адрес контейнера Nginx (не `*`);
   - `DATABASE_SSLMODE=verify-full` и `DATABASE_SSLROOTCERT`, если БД на отдельном сервере;
   - `APP_TLS_CERT_PATH` — путь к сертификату приложения внутри `api` (для оповещения об истечении).
   Секреты в `.env` не пишутся: приложение читает их из файлов `/run/secrets/<имя переменной в
   нижнем регистре>`, например `/run/secrets/encryption_key` (SEC-CRYPT-01).
4. Создать файл своего стенда рядом с основным, например `deploy/compose/docker-compose.site.yml`:
   сертификат TLS, отдельный диск для копий, секреты.

   ```yaml
   services:
     nginx:
       volumes:
         - /etc/estimator/tls/server.crt:/etc/nginx/certs/server.crt:ro
         - /etc/estimator/tls/server.key:/etc/nginx/certs/server.key:ro
       ports: ["443:8443", "80:8080"]
     api:
       secrets: [encryption_key, postgres_password, redis_password]
   secrets:
     encryption_key: { file: /etc/estimator/secrets/encryption_key }
     postgres_password: { file: /etc/estimator/secrets/postgres_password }
     redis_password: { file: /etc/estimator/secrets/redis_password }
   volumes:
     backups:
       driver: local
       driver_opts: { type: none, o: bind, device: /mnt/backup/estimator }
   ```

   Копии должны лежать не на том диске, где `pgdata`. Скрипты бэкапа берут список файлов compose из
   `COMPOSE_FILES` (через двоеточие), например
   `COMPOSE_FILES=deploy/compose/docker-compose.yml:deploy/compose/docker-compose.site.yml`.
5. Собрать или скачать образы и поднять стенд:
   `docker compose -f … -f … up -d --wait`. Сервис `migrate` применит миграции, `api` стартует
   после него, Nginx — после зелёного healthcheck `api`.
6. Создать первого суперадминистратора:
   `docker compose run --rm api estimator create-superadmin --login <логин> --email <почта>`.
   Команда печатает ссылку установки пароля (действует 60 минут). Ссылку передать
   суперадминистратору; он задаёт пароль, подключает TOTP и проходит мастер первичной настройки.
7. Поставить расписания cron: `deploy/backup/estimator-backup.cron` → `/etc/cron.d/estimator-backup`,
   `deploy/logging/estimator-logs.cron` → `/etc/cron.d/estimator-logs` (пути и пользователя
   поправить под стенд).
8. Подключить мониторинг (раздел 8) и проверить:
   - `https://<адрес>/health/ready` отвечает 200;
   - `deploy/backup/backup.sh` проходит, и «Состояние системы» в админке показывает время копии;
   - `docker compose run --rm api estimator audit verify` — цепочка аудита цела.

`estimator seed-demo` (демо-пользователи и проекты) запускается только на test и stage, на prod —
никогда.

## 4. Консольные команды

Запуск: `docker compose run --rm api estimator <команда>` (с теми же `-f` файлами стенда).
Подсказка по каждой — `--help`.

| Команда | Когда | Что делает |
|---|---|---|
| `migrate` | при установке и обновлении (делает `upgrade.sh`) | миграции БД до последней версии; `--downgrade РЕВИЗИЯ` — откат схемы (только по `rollback.sh`) |
| `create-superadmin --login --email` | установка | суперадминистратор и ссылка установки пароля на 60 минут |
| `issue-activation --login` | ссылка не дошла или истекла | новая ссылка, прежняя аннулируется |
| `reset-superadmin --login` | все суперадминистраторы потеряли доступ | сброс пароля и TOTP, ссылка на 60 минут, все сессии завершаются |
| `auth-mode local [--dry-run]` | AD недоступен надолго, решение суперадминистратора и ИБ | вход через приложение: учётки AD становятся локальными, ссылки установки пароля на 72 часа, все сессии завершаются |
| `generate-key` | установка, ротация | новый мастер-ключ; выводится один раз |
| `rotate-key [--check]` | раз в год и при подозрении на компрометацию (раздел 6) | перешифровать секреты текущим ключом; `--check` — сколько значений ещё на старых ключах |
| `audit verify` | после восстановления; ежедневно делает `beat` в 04:00 | проверка хэш-цепочки журнала аудита; результат — в аудите и «Состоянии системы» |
| `audit purge [--dry-run]` | ежемесячно | удаление записей аудита старше срока хранения (не меньше 6 месяцев) |
| `project purge ID --ticket --approved-by [--dry-run]` | по согласованной с ИБ заявке | физическое удаление проекта: сначала состав (`--dry-run`), затем подтверждение вводом id; запись в аудите остаётся |
| `seed-demo [--password]` | test и stage | демо-данные: 12 пользователей, «Портал дилеров», проект на 2 000 узлов |
| `config-env --check README.md` | разработка | таблица переменных в README совпадает с конфигом |

Проект, удалённый `project purge`, остаётся в резервных копиях до истечения их срока (30 дней,
BR-PRJ-04).

## 5. Резервные копии и восстановление

Подробно — [deploy/backup/README.md](../deploy/backup/README.md). Цели: RPO ≤ 15 минут, RTO ≤ 4 часа
(NFR-REL-02), копии хранятся 30 дней.

| Что | Как | Когда |
|---|---|---|
| БД непрерывно | архивация WAL в pgBackRest | каждые 60 с |
| БД полностью + документы | `deploy/backup/backup.sh` | ежедневно в 01:00 (cron) |
| Проверка архивации | `deploy/backup/backup.sh --check` | ежечасно (cron) |
| Восстановление | `deploy/backup/restore.sh [--time "ГГГГ-ММ-ДД ЧЧ:ММ:СС+03"] [--wipe]` | по аварии |

Порядок восстановления:

1. Если рабочих ключей нет — вскрыть по акту конверт ИБ с мастер-ключом и паролем копий, положить
   их в секреты стенда.
2. `restore.sh` (диск БД цел) или `restore.sh --wipe` (диск потерян). На момент времени — `--time`.
   Скрипт останавливает приложение, восстанавливает БД и документы, поднимает стенд и ждёт
   healthcheck.
3. Проверить «Состояние системы» и выполнить `estimator audit verify`.

Проверка восстановления раз в квартал (NFR-REL-03) — на test, скриптом
`deploy/backup/verify-restore.sh протокол.md`. Он делает копию, удаляет том БД, восстанавливает и
пишет протокол с RPO и RTO. Шаблон протокола — раздел 10.

## 6. Ключи и эскроу

SEC-CRYPT-07, SPEC 18.4, решения Q-48 и R-10.

| Ключ | Где рабочий | Копия |
|---|---|---|
| Мастер-ключ `ENCRYPTION_KEY` (секреты TOTP, пароли AD/SMTP/SIEM, ключи документов) | Docker secret `encryption_key` у службы эксплуатации | запечатанный конверт в сейфе ИБ |
| Пароль репозитория копий `BACKUP_CIPHER_PASSWORD` | Docker secret у службы эксплуатации | запечатанный конверт в сейфе ИБ |

Без мастер-ключа копия БД бесполезна: секреты и документы в ней не расшифровать.

**Ротация мастер-ключа** (раз в год и при подозрении на компрометацию):

1. Вскрыть по акту конверт ИБ с текущим ключом и восстановить им тестовую копию на test (так
   раз в год проверяется копия из сейфа, решение R-10).
2. `estimator generate-key` — новый ключ.
3. На стенде: новый ключ — в `encryption_key`, прежний — в `ENCRYPTION_KEYS_OLD`
   (через запятую, если их несколько); перезапустить `api`, `worker`, `beat`.
4. `estimator rotate-key`, затем `estimator rotate-key --check` — на старых ключах 0 значений.
5. Убрать прежний ключ из `ENCRYPTION_KEYS_OLD` и перезапустить сервисы.
6. В тот же день передать в сейф ИБ запечатанную копию нового ключа, старый конверт уничтожить
   по акту.

## 7. Обновление и откат

SPEC 18.3. Миграции совместимы с предыдущей версией кода (NFR-MNT-02, проверка CI «старый код на
новой схеме»), поэтому при откате БД обычно не трогают.

**Обновление:** `deploy/scripts/upgrade.sh ВЕРСИЯ`. Скрипт:

1. делает резервную копию;
2. скачивает образы версии;
3. применяет миграции;
4. поочерёдно перезапускает `api` (пользователи видят короткое переподключение без потери данных),
   затем `worker`, `beat` и `nginx`;
5. проверяет `/health/ready`.

В конце он печатает прежнюю версию: она нужна для отката.

**Откат** при критичном дефекте:

| Команда | Когда |
|---|---|
| `deploy/scripts/rollback.sh ПРЕЖНЯЯ_ВЕРСИЯ` | обычный случай: прежние образы на новой схеме |
| `rollback.sh ПРЕЖНЯЯ_ВЕРСИЯ --downgrade РЕВИЗИЯ` | новая схема мешает прежнему коду |
| `rollback.sh ПРЕЖНЯЯ_ВЕРСИЯ --restore "ВРЕМЯ"` | данные испорчены: БД на момент до обновления; правки после него теряются, решение за владельцем продукта |

## 8. Мониторинг и оповещения

Prometheus опрашивает `api` (метрики SPEC 18.4); правила — `deploy/monitoring/alerts.yml`, их
проверяет CI (`promtool test rules`). Оповещения направить в канал дежурной смены через
Alertmanager службы эксплуатации.

| Оповещение | Важность | Условие | Что делать |
|---|---|---|---|
| `Estimator5xxRatioHigh` | critical | 5xx > 1 % за 5 минут | логи `api`, «Состояние системы» |
| `EstimatorLoginFailuresBurst` | warning | > 50 неуспешных входов за 5 минут | сообщить ИБ: возможен перебор паролей |
| `EstimatorAdCheckStale` | warning | проверка AD (каждые 15 минут) не шла > 1 часа | доступность контроллера AD, логи `worker` |
| `EstimatorAdDailySyncStale` | warning | ежедневная синхронизация AD не шла > 26 часов | то же |
| `EstimatorBackupStale` | critical | копия старше 26 часов | `/var/log/estimator-backup.log`, запустить `backup.sh` |
| `EstimatorWalArchiveLag` | critical | архивация WAL не работает > 15 минут | `backup.sh --check`, место на диске копий |
| `EstimatorCertificateExpiring` | warning | сертификат TLS приложения или УЦ AD истекает < 30 дней | выпустить новый, заменить файл, перезапустить `nginx` |
| `EstimatorSiemQueueOverflow` | critical | очередь в SIEM > 10 000 событий | доступность SIEM, сообщить ИБ |
| `EstimatorAuditChainBroken` | critical | проверка цепочки аудита не прошла | сообщить ИБ немедленно, ничего не удалять |
| `EstimatorClamavDown` | warning | ClamAV недоступен 10 минут | перезапустить `clamav`; документы ждут проверки |
| `EstimatorClamavDbOld` | warning | базы ClamAV старше 3 дней | доступ `clamav` к серверу обновлений или локальное зеркало |
| `EstimatorApiLatencyP95High` | warning | p95 ответа API > 300 мс 15 минут | нагрузка на сервер и БД |
| `EstimatorWsDeliveryP95High` | warning | p95 доставки событий > 1 с 15 минут | Redis, нагрузка |
| `EstimatorComponentDown` | critical | компонент «Состояния системы» красный | по компоненту |

## 9. Логи

Контейнеры пишут JSON-логи (драйвер `local`, не больше 5 × 50 МБ на сервис). Ежедневно
`deploy/logging/collect-logs.sh` собирает их в `/var/log/estimator/ГГГГ-ММ-ДД.log.gz` и удаляет
архивы старше 90 дней (NFR-REL-06). В логах нет паролей, токенов и cookie. IP-адреса хранятся не
дольше срока логов.

## 10. Регулярные работы

Сроки и ответственные — в [регламентах сопровождения](regulations.md).

| Работа | Периодичность |
|---|---|
| Проверка, что копии и архивация WAL работают (оповещения и «Состояние системы») | ежедневно |
| `estimator audit purge` | ежемесячно |
| Обновление зависимостей и образов (новый релиз) | ежемесячно |
| Проверка восстановления на test (`verify-restore.sh`) | ежеквартально |
| Ротация мастер-ключа и проверка копии из сейфа ИБ | ежегодно |
