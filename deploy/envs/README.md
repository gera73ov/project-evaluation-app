# Стенды test и stage (INF-011)

Оба стенда разворачиваются одной командой на своём сервере. Основание: SPEC 18.1, NFR-ENV-01,
NFR-COMP-03.

| | test | stage |
|---|---|---|
| Назначение | CI, ручные проверки, демонстрации | приёмка перед prod, нагрузка (QA-020), ZAP (QA-021) |
| Корпоративные сервисы | эмуляторы: Samba AD, Mailpit, syslog TLS | настоящие: тестовый OU корпоративного AD, почтовый релей, SIEM |
| Данные | демо-данные `seed-demo` | справочники из миграций и тестовые проекты `seed-demo` |
| Файлы compose | базовый + `docker-compose.test.yml` + `docker-compose.stand.yml` | базовый + `docker-compose.stand.yml` |
| Параметры | `test/stand.env` | `stage/stand.env` |

## Что нужно от сервера

- Ubuntu 22.04+, Astra Linux или РЕД ОС; 4 ядра, 16 ГБ памяти, 100 ГБ SSD (stage — как prod).
- Docker Engine 24+ и Docker Compose 2.24+, `python3`, `curl`, `git`.
- DNS-имя стенда в корпоративной зоне и сертификат на это имя от корпоративного УЦ (для test
  подходит сертификат, который выпускает сервис `certs`).
- Сетевой доступ: входящие 443 и 80 только из офисной сети и VPN; исходящие к реестру образов,
  а для stage ещё к AD (LDAPS 636), почте и SIEM.

## Развернуть

```sh
git clone <репозиторий> /opt/estimator && cd /opt/estimator
git checkout <тег релиза>
# Имя сервера, сети офиса и VPN — в deploy/envs/<стенд>/stand.env (или в .env после первого запуска)
sudo deploy/envs/deploy.sh stage 1.0.0        # образы версии 1.0.0 из реестра
sudo deploy/envs/deploy.sh test --build       # собрать образы из рабочей копии
```

Скрипт делает следующее:

1. Проверяет сервер: версии Docker и Compose, ОС из списка.
2. Создаёт `.env` в корне рабочей копии со случайными паролями (`make_env.py`) и переносит в него
   параметры стенда из `stand.env`.
3. Переносит мастер-ключ шифрования в Docker secret `STAND_SECRETS_DIR/encryption_key`
   (владелец — пользователь приложения 10001, права 0400) и убирает ключ из `.env`. Копию ключа
   храните в сейфе ИБ: без неё не расшифровать документы и секреты из резервных копий.
4. Пишет список сетей Nginx `deploy/envs/<стенд>/access.conf` из `STAND_NETWORKS`. Остальным
   Nginx отвечает 403 и на HTTPS, и на HTTP.
5. Скачивает образы или собирает их (`--build`), накатывает миграции, запускает сервисы и ждёт
   healthcheck.
6. Создаёт демо-данные, если `STAND_SEED=demo`. Уже созданное пропускается.
7. Делает смоук: `/health/ready` и главная страница по имени стенда с самого сервера.

Повторный запуск безопасен: пароли, ключ и данные сохраняются, обновляются только образы и
настройки. Обновлять версию на работающем стенде лучше `deploy/scripts/upgrade.sh`: он сначала
делает резервную копию. Резервные копии и восстановление описаны в `deploy/backup/README.md`.

## Сертификат

Положите сертификат и ключ стенда в `deploy/compose/certs/nginx.crt` и `nginx.key` до первого
запуска: сервис `certs` существующие файлы не трогает. Если стенд выпускает сертификаты сам
(test), он выпускает сертификат Nginx на имя из `APP_BASE_URL`, а `deploy/compose/certs/ca.crt`
нужно добавить в доверенные на машинах тестировщиков. Если `nginx.crt` уже выпущен на другое имя,
скрипт предупредит: удалите `nginx.crt` и `nginx.key` или положите сертификат стенда.

## test без sudo

test можно развернуть и без root, например исполнителем CI на домашнем стенде, у которого нет sudo
(workflow `deploy-test`). Тогда `STAND_SECRETS_DIR` укажите в каталоге этого пользователя: ключ
остаётся его файлом с правами 0444 в каталоге 0700, владельца 10001 без root не назначить. stage без
root скрипт не разворачивает.

Если пользователь без sudo состоит в группе docker, `STAND_CHOWN_VIA_DOCKER=1` ставит ключу
владельца 10001 и права 0400 одноразовым контейнером от root: итог тот же, что под sudo, и так
можно развернуть stage. Членство в группе docker и так равно root на этом сервере, новых прав
это не даёт.

## Репетиция stage на домашнем стенде

Пока серверов stage нет, stage разворачивается на домашнем стенде рядом с test: workflow
`deploy-stage` (вручную, action `deploy`). Процедура та же, `deploy.sh stage`, плюс
`STAND_ENV_EXTRA=deploy/envs/stage/home-stand.env`: строки этого файла дописываются в `.env` после
`stand.env`. Там свой проект compose `estimator-stage` (e2e и deploy-test его не трогают), своя
подсеть Docker и свои порты на loopback. Рабочая копия — `/home/stand/estimator-stage`, ключ,
пароль демо и ссылка суперадминистратора — в `/home/stand/estimator-stage-secrets`. Демо-пользователи
входят после мастера первичной настройки: его проходит суперадминистратор `stage.admin`.
Корпоративных AD, почты и SIEM здесь нет, поэтому такая репетиция не заменяет приёмку на stage.

## Доступ только из сети компании

Доступ ограничен двумя слоями:

1. **Межсетевой экран сервера** — основной слой: входящие 443 и 80 только из офиса и VPN.
   Пример для `ufw`: `ufw allow from 10.0.0.0/8 to any port 443,80 proto tcp`. Для `firewalld`
   — зона `internal` с этими сетями. Docker публикует порты в обход `ufw`, поэтому правило
   продублируйте в цепочке `DOCKER-USER`. Порт там уже заменён на порт контейнера, поэтому
   сравнивайте исходный: `iptables -I DOCKER-USER -p tcp -m conntrack --ctorigdstport 443
   ! -s 10.0.0.0/8 -j DROP`, и так же для 80.
2. **Nginx** — второй слой: `allow` для сетей из `STAND_NETWORKS`, для самого сервера и подсети
   Docker стенда (`STAND_DOCKER_SUBNET`), затем `deny all`. Проверка 403 для чужого адреса —
   `deploy/nginx/test_nginx.sh`.

Проверка снаружи: с адреса вне офиса и VPN `curl -m 5 https://<стенд>/` не должен получить
ответ приложения.

## stage: подключить корпоративные сервисы

После развёртывания суперадминистратор проходит мастер первичной настройки
(`manuals/superadmin.md`). На этом шаге подключаются:

- тестовый OU корпоративного AD: адрес LDAPS, учётка поиска, базовый DN тестового OU, группа
  доступа;
- почтовый релей и адрес отправителя;
- SIEM (syslog TLS).

Пароли этих подключений приложение хранит зашифрованными мастер-ключом.
