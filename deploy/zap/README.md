# DAST: OWASP ZAP (QA-021)

Сканирование стенда OWASP ZAP 2.17 по SPEC SEC-SDLC-02 и SEC-SDLC-05. Приёмка релиза (17.3)
требует, чтобы не было находок с риском High.

| Файл | Что делает |
|---|---|
| `run.sh` | все шаги на развёрнутом стенде одной командой |
| `prepare.py` | сессии ролей и копия OpenAPI для сканирования; запускается в контейнере `api` |
| `rules.tsv` | правила ZAP, которые понижены до INFO, с обоснованием |

## Что сканируется

1. **Baseline, без входа.** Паук обходит сайт, пассивные правила проверяют заголовки, cookie,
   CSP, утечки в ответах и ошибках.
2. **API с сессией для каждой роли**: эксперт, модератор (оба участники проекта в статусе
   «Оценка») и администратор. `zap-api-scan` импортирует OpenAPI и запускает активные правила:
   инъекции, обход путей, XSS в ответах и другие.
   - Сессия передаётся cookie `__Host-session` (`ZAP_AUTH_HEADER`), CSRF-токен — заголовком
     `X-CSRF-Token` через правило подмены.
   - Из копии OpenAPI убраны операции, которые оборвали бы сканирование: `/auth/*`,
     `/me/sessions`, `/me/password`, `/me/totp` и `/me/backup-codes`. Вход и восстановление
     доступа проверяются в baseline и в тестах безопасности (`backend/tests/security`).
   - ZAP работает в два потока: лимит изменяющих запросов — 300 в минуту на пользователя. Ответы
     429 ожидаемы и находкой не считаются.

Пользователи и проект для сканирования создаются с уникальными логинами `zap.<роль>.<суффикс>`.
Сессии `prepare.py` создаёт напрямую, с пройденным TOTP.

## Запуск

```sh
deploy/zap/run.sh                       # стенд из этой рабочей копии, отчёты в deploy/zap/report
ZAP_ROLES=expert ZAP_MAX_MINUTES=5 deploy/zap/run.sh
```

Отчёты лежат в `deploy/zap/report`:

- `baseline.html` и `.json`;
- `api-<роль>.html` и `.json`;
- `verdict.txt` — число находок по уровням риска и список находок High.

Если есть хотя бы одна находка High, код выхода — 1. Находки Medium и Low разбираются задачами
треков-владельцев. Ложное срабатывание понижается строкой в `rules.tsv` с обоснованием.

На домашнем стенде то же самое запускается вручную в GitHub Actions: workflow `zap`. Стенд для
сканирования — одноразовый: активные правила создают и меняют данные. На prod `prepare.py`
отказывается работать.
