# FE-081 · отчёт профилирования рабочего экрана

Дата: 10.11.2026. Локальный стенд: API (`uvicorn --factory estimator.main:app_factory`), Postgres 16,
Redis, `serve.mjs` со сборкой `frontend/dist`; Chromium из Playwright без ограничения CPU, окно
1440×900. Проект: 2 фазы × 2 дисциплины, 4 999 узлов (`fill.py`: модули → подузлы → листья с O/R/P).

Порог SPEC задан для ноутбука Core i5 / 8 ГБ и сети 100 Мбит; контейнер стенда быстрее по сети и
сопоставим по CPU. Подтверждение на эталонной машине — QA-020.

## Как повторить

```bash
(cd frontend && npm run build)
cd e2e && E2E_PERF=1 npx playwright test perf
# с профилем CPU на время ввода (вложение input.cpuprofile, открывается в DevTools → Performance):
E2E_PERF=1 E2E_PERF_PROFILE=1 npx playwright test perf
```

Цифры каждого прогона печатаются строкой `FE-081 {…}` и прикладываются к тесту (`perf-report.json`).

## Что нашёл профиль

Профиль CPU пяти вводов O (до исправлений), собственное время функций:

| Функция | Доля | Причина |
|---|---|---|
| `extraOf` (фильтры) | 24% | на каждый узел и каждый из 7 чипов строился `Map` из полей `extra` |
| `riskCount`, `openQuestions` (верхняя панель) | 10% | то же копирование полей для всех 5 000 узлов при каждой отрисовке |
| `branchReadiness` | 2% | то же в каждой строке дисциплины |
| Mantine `Popover`/`useFloating`, `NodeMenu`, `AddMenu`, `SumTooltip`, i18n `t()` | ~15% | при каждом изменении дерева перерисовывались все видимые строки: `memo` строки не срабатывал, потому что объекты действий и контекст создавались заново |

## Что изменено

1. Поля `extra` узла читаются по имени (`extraOf` в `store/treeStore.ts`) без копирования
   в `Map`: фильтры, счётчики чипов, верхняя панель, готовность ветки, удаление.
2. Строка таблицы сравнивается по «подписи» (`sig`): данные своего узла и расчёта, статус ветки,
   свои захваты, ошибки и подсказки ячеек, открытое меню, ключ справочников и прав. Объекты действий
   (ввод, меню, статус ветки) передаются через `useFresh` (`tree/fresh.ts`): функции — постоянные
   обёртки над версией последней отрисовки, поэтому неперерисованная строка не вызывает устаревший
   обработчик. Ввод в лист перерисовывает этот лист, его предков и строку итогов, а не все строки.
3. Экраны вне рабочего (админки, система, аудит, статистика, сравнение, портфель, мастер настройки,
   документы, итоги, корзина) грузятся отдельными частями сборки (`app/lazyPages.tsx`).

## Что не потребовалось

- Инкрементальный пересчёт уже был (`CalcTree.updateLeaf`, FE-021): правка оценки листа
  пересчитывает лист и предков, около 1 мс на 5 000 узлах. Полная пересборка (~45–60 мс) остаётся
  для правок структуры и смены статуса ветки — в норму ввода не входит.
- Виртуализация (FE-022) уже держит в DOM 31–45 строк.

# QA-020 · производительность фронтенда

Сценарий тот же (`perf/tree.spec.ts`), добавлены проект на 2 000 узлов, p95 по `E2E_PERF_RUNS`
открытиям и приближение к эталонному ноутбуку (Core i5 / 8 ГБ, 100 Мбит) средствами DevTools:
замедление CPU страницы (`E2E_PERF_CPU`, `Emulation.setCPUThrottlingRate`) и сеть
(`E2E_PERF_NET`, `Network.emulateNetworkConditions`, задержка 2 мс). Скорость CPU страницы после
замедления пишется в отчёт как `cpuBenchMs` (один и тот же расчёт, медиана пяти замеров): по нему
прогоны на разных машинах сравнимы между собой.

На стенде замеры гоняет workflow `perf` (запуск вручную): стенд профиля test с Nginx и сборкой
как в prod, прогон на каждый коэффициент из `cpu` (по умолчанию 1 и 2), 20 открытий на размер.

Нормы: открытие до интерактивности p95 ≤ 2 с на 2 000 узлах и ≤ 4 с на 5 000 (NFR-PERF-02), ввод O
→ новая сумма на экране ≤ 100 мс (NFR-PERF-03), прокрутка 5 000 строк в среднем ≥ 30 fps
(NFR-PERF-06), в DOM не больше ~150 строк (FR-TREE-15). Дополнительная проверка FE-081 «долгих
кадров не больше 1%» действует только без замедления CPU; с замедлением доля долгих кадров и p95
кадра идут в отчёт.

## Результаты

| Машина | CPU | `cpuBenchMs` | Открытие 2 000, p95 | Открытие 5 000, p95 | Ввод O, макс. | Прокрутка, fps / p95 кадра / долгих |
|---|---|---|---|---|---|---|
| Облачный контейнер агента, 4 ядра, 100 Мбит, 5 открытий | ×1 | 20 | 1,09 с | 1,94 с | 28 мс | 59 / — / 0,9% |
| То же | ×2 | 40–43 | 1,29–1,37 с | 1,97–2,43 с | 59–65 мс | 37–38 / 43 мс / 12–14% |

Все нормы SPEC выполнены и при двукратном замедлении CPU. Запас на открытии 5 000 узлов — около
1,6 с, на вводе — около 35 мс.

При замедлении ×2 прокрутка в среднем держит 37 fps, но каждый восьмой кадр длиннее 33 мс. Профиль
прокрутки (`E2E_PERF_PROFILE=1`) ровный: время делится между отрисовкой React новых строк,
Mantine (подсказки, выпадающие списки в ячейках) и самим DOM; одной горячей функции нет. Сценарий
прокручивает очень быстро (120 px за кадр, около 200 строк в секунду), так что каждый кадр
монтирует новые строки. Если на стенде или эталонном ноутбуке среднее упадёт ниже 30 fps, следующий
шаг — отложенный монтаж тяжёлых частей строки (меню, подсказки) до остановки прокрутки.

## Домашний стенд (workflow `perf`)

Стенд: test-профиль с Nginx и двумя репликами API, Chromium, сеть 100 Мбит, 20 открытий на размер.
`cpuBenchMs` стенда около 41 мс: процессор страницы примерно вдвое медленнее облачного контейнера и,
по оценке, вдвое медленнее эталонного ноутбука. Поэтому прогон при CPU ×1 на стенде строже нормы, а
при CPU ×2 — строже вчетверо.

Что было исправлено по итогам замеров:

- #128 (FE): правки одного узла уходят очередью. Раньше параллельные PATCH сервер мог применить не в
  порядке ввода, и последнее введённое значение терялось. Дерево и справочники теперь запрашиваются
  параллельно с карточкой проекта.
- #130 (CORE): ускорен `GET /projects/{id}/tree`.
- #132 (FE): правка снимается из `pending` по своей метке, а не по значению. При вводах 3 → 4 → 3
  ответ на первую правку снимал третью.

Долгие кадры прокрутки на стенде: средние 32 fps выполняют норму SPEC (≥ 30 fps), но доля кадров
длиннее 33 мс — 23–32%. Строгая проверка FE-081 (≤ 1%) включается только на машине уровня эталона
(`cpuBenchMs` ≤ 25, `E2E_PERF_REF_BENCH`). В облаке при CPU ×1 она выполняется: 0,6%.
