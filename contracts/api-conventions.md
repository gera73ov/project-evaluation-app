# Соглашения API v1 (API-001)

Версия контракта: **0.1 (черновик до вехи M0)**. Владелец: трек API. Основание: SPEC v0.5, 15.1, 15.3,
SEC-WEB-03/04/07/08/09, SEC-AUTHZ-02…04, FR-SESS-02, FR-2FA-05, ARCH-01/02, BR-CALC-03.
Словарь кодов ошибок — [`errors.yaml`](errors.yaml); операции и схемы — [`openapi.yaml`](openapi.yaml) (API-002).

Нормативные слова — как в AGENTS.md 0.1 (ДОЛЖЕН, ЗАПРЕЩЕНО, СЛЕДУЕТ, ДОПУСКАЕТСЯ).

---

## 1. Адрес, версия, транспорт

1. Базовый путь — `/api/v1`. Все пути в OpenAPI и в таблице 15.2 — относительно него. WebSocket — `/api/v1/ws` (RT-001).
2. Только HTTPS (SEC-WEB-01). CORS выключен: фронтенд и API на одном домене (SEC-WEB-05).
3. Ломающее изменение API — новая версия пути (`/api/v2`), а не изменение `v1`. До вехи M0 контракт `v1`
   меняется обычным PR (contracts/README.md), после M0 — только через CR.
4. Документация OpenAPI (`/api/docs`, `/api/openapi.json`) включается только при `APP_ENV` = `dev`, `test`,
   `stage`; в `prod` эти пути отвечают 404 (15.1, API-005).

## 2. Формат тела

1. Запросы и ответы — `application/json; charset=utf-8`. Ошибки — `application/problem+json` (раздел 5).
   Загрузка документов и календаря — `multipart/form-data`; скачивание файлов — бинарный ответ с
   `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff` (SEC-WEB-10).
2. Имена полей — `snake_case`. Значения перечислений — строки в нижнем регистре, совпадают с перечислениями
   БД (contracts/db/schema.md, раздел 7): `"status": "estimation"`, `"quote_figure": "p80"`.
3. Отсутствующее значение — `null`, если поле входит в схему ответа для этого пользователя. Поле, которое
   пользователю не положено (деньги, заметки), **отсутствует** как ключ (раздел 4), а не равно `null`.
4. Неизвестные поля в теле запроса отклоняются: 422 `VALIDATION_FAILED` (`additionalProperties: false`
   в схемах запросов). Так опечатка в имени поля не превращается в молчаливое «ничего не изменилось».

### 2.1. Числа

| Что | Тип JSON | Формат | Пример | Основание |
|---|---|---|---|---|
| O, R, P (ввод и хранение) | строка | `DecimalString`: `^-?\d+(\.\d+)?$`, без лишних нулей справа; сервер принимает и `,`, и `.`, округляет до 0,5 по ROUND_HALF_UP и возвращает фактическое значение | `"12.5"`, `"16"` | 15.1, 15.3, BR-CALC-03 |
| Расчётные часы (E, σ, P80, P90, ΣO/ΣR/ΣP) | строка | 2 знака после точки, ROUND_HALF_UP; клиент округляет до 1 знака при показе | `"17.00"`, `"3.67"` | 15.3, BR-CALC-03 |
| Деньги (стоимость, итоги, НДС, сумма договора) | строка | целое число, без разделителей | `"1146798"` | BR-MONEY-04 |
| Ставка ₽/ч | строка | целое | `"3000"` | BR-CALC-03 |
| Курс | строка | до 4 знаков после точки, без лишних нулей | `"92.5"` | BR-MONEY-03 |
| Проценты (УП, НДС, соотношения) | строка | до 2 знаков после точки, без лишних нулей | `"18"`, `"0.5"` | BR-CALC-03 |
| Коэффициенты K_F | строка | 6 знаков после точки (только для показа подсказки) | `"1.046823"` | 6.5 |
| ×N, версии, счётчики, размеры | число | целое | `12`, `1051` | 15.3 |

Числа с плавающей точкой (`number` с дробной частью) в API ЗАПРЕЩЕНЫ для часов, денег, курса и процентов.
В OpenAPI такие поля имеют схему `DecimalString` / `MoneyString` (API-002), а в TypeScript — branded-тип
`DecimalString` (API-006).

### 2.2. Время и даты

- Моменты времени — строка ISO 8601 в UTC с суффиксом `Z`: `"2026-11-03T12:01:44Z"`; доли секунды
  ДОПУСКАЮТСЯ (до микросекунд). Сервер всегда отдаёт UTC; перевод в пояс пользователя — на клиенте (FR-UI-02).
- Календарные даты (дедлайн, день итогов, производственный календарь) — `"2026-11-05"` и понимаются по
  часовому поясу приложения `app.timezone`.
- Длительности — целые секунды (`retry_after`, `expires_in`).

### 2.3. Идентификаторы

UUID v7 строкой в нижнем регистре (`"0192f1c4-7a1e-7c3b-9f00-1a2b3c4d5e6f"`). Непредсказуемость идентификатора
мерой защиты не считается (SEC-AUTHZ-03). Номер вопроса заказчику — отдельное целое поле
`customer_question_no`; строка «В-007» собирается на клиенте.

## 3. Аутентификация, сессия, CSRF

1. Сессия — cookie `__Host-session` (`HttpOnly; Secure; SameSite=Strict; Path=/`) (FR-SESS-01). Токены в
   заголовке `Authorization` и в `localStorage` не используются.
2. Все изменяющие запросы (`POST`, `PUT`, `PATCH`, `DELETE`) ДОЛЖНЫ нести заголовок `X-CSRF-Token` со значением
   из cookie `__Host-csrf` (не HttpOnly), привязанным к сессии (SEC-WEB-04). Без заголовка или с чужим токеном —
   403 `CSRF_FAILED`. Исключения — `POST /auth/login`, `POST /auth/totp` (по временному токену шага),
   `POST /auth/activate`, `POST /auth/password/forgot`, `POST /auth/password/reset`: у них ещё нет сессии, их
   защищают `SameSite=Strict`, одноразовые токены и rate limit.
3. Фоновые запросы (опросы, продление захватов, автообновление статуса выгрузки) ДОЛЖНЫ нести заголовок
   `X-Background: 1`: они не продлевают сессию по бездействию (FR-SESS-02).
4. Step-up (SEC-AUTH-05): эндпоинт, требующий step-up, без действующего подтверждения отвечает 403
   `STEP_UP_REQUIRED`; клиент вызывает `POST /auth/step-up` и повторяет запрос. Окно step-up — 5 минут.
5. Деньги и заметки (FR-2FA-05): без пройденного в сессии TOTP денежные поля отсутствуют в общих ответах, а
   эндпоинты с правами `money.*` и `notes.*` отвечают 403 `TOTP_REQUIRED`; клиент вызывает
   `POST /auth/step-up` с `{"totp_only": true}`.
6. Пока мастер установки не завершён, любой запрос не суперадминистратора получает 503 `APP_SETUP_IN_PROGRESS`
   (FR-SA-02).

## 4. Права и поля с ограниченным доступом

1. Каждая операция OpenAPI ДОЛЖНА иметь расширение `x-permission` — код права из `contracts/permissions.yaml`
   (SEC-001) или псевдоправо (`public`, `authenticated`, `session.pre_mfa`, `token.login_step`,
   `token.activation`). Если операция допускает несколько прав («любое из»), `x-permission` — список.
   Операция без `x-permission` роняет TC-SEC-01 (SEC-AUTHZ-02).
2. Порядок проверок на сервере и соответствующие ответы:

   | Шаг | Проверка | Ответ при отказе |
   |---|---|---|
   | 1 | Мастер установки завершён (или это суперадминистратор) | 503 `APP_SETUP_IN_PROGRESS` |
   | 2 | Сетевое ограничение админки суперадминистратора (FR-SA-06) | 404 `NOT_FOUND` |
   | 3 | Сессия действительна | 401 `UNAUTHENTICATED` |
   | 4 | TOTP подключён, если обязателен (FR-2FA-04) | 403 `TOTP_ENROLL_REQUIRED` |
   | 5 | CSRF для изменяющих запросов | 403 `CSRF_FAILED` |
   | 6 | Объект существует и пользователь имеет доступ к его проекту (участник, руководитель пресейла, режим поддержки) | 404 `NOT_FOUND` |
   | 7 | Право по роли, дисциплине, авторству (матрица 3.3) | 403 `FORBIDDEN` |
   | 8 | Право разрешено статусом проекта (таблица 3.4) | 409 `PROJECT_STATUS_CONFLICT` |
   | 9 | TOTP пройден в сессии для `money.*`, `notes.*` | 403 `TOTP_REQUIRED` |
   | 10 | Step-up для действий SEC-AUTH-05 | 403 `STEP_UP_REQUIRED` |
   | 11 | Валидация тела | 422 `VALIDATION_FAILED`, `VALUE_OUT_OF_RANGE`, … |
   | 12 | Состояние объекта (версии, лимиты, захваты, переходы) | 409, 423 |

   На шаге 6 сервер НЕ ДОЛЖЕН различать «объекта нет» и «объект в чужом проекте» (SEC-AUTHZ-03). Отказы 403/404
   на объекты проекта пишутся в аудит агрегированно (SEC-AUD-01, «Безопасность»).
3. Денежные данные (SEC-AUTHZ-04):
   - выдаются только с правом `money.read` и пройденным в сессии TOTP;
   - отдельные эндпоинты (`/projects/{id}/money`, выгрузки с деньгами, `/portfolio/*`);
   - в общих ответах (дерево, проект, список проектов, статистика, снимки, сравнение, журнал) деньги лежат
     **только** во вложенном объекте `money` (или массиве объектов с суффиксом `_money`), схема которого
     в OpenAPI называется `*Money`. Без права ключа `money` нет. В других местах ответа ключей `rate`, `cost`,
     `currency`, `exchange_rate`, `money`, `vat`, `contract_amount`, `quote_rub`, `quote_cur` нет (TC-SEC-03
     ищет их рекурсивно);
   - в ответе `PATCH /nodes/{id}` денег нет никогда: они приходят событием `money.updated` по каналу
     `project:{id}:money` (15.3).
4. Закрытые заметки — только эндпоинты `/projects/{id}/notes`, `/notes/{id}` с правами `notes.read` /
   `notes.write`; в другие ответы заметки и их счётчики не попадают (FR-NOTE-01, TC-SEC-07).

## 5. Ошибки (RFC 9457)

1. Любой ответ 4xx и 5xx — Problem Details с `Content-Type: application/problem+json`:

   ```json
   {
     "type": "https://estimator.local/problems/field-conflict",
     "title": "Значение уже изменено",
     "status": 409,
     "code": "FIELD_CONFLICT",
     "detail": "Поле r узла изменено после версии 7",
     "error_id": "01JD3K6Q2V9X8T7R5N4M3P2Q1Z",
     "instance": "/api/v1/nodes/0192f1c4-7a1e-7c3b-9f00-1a2b3c4d5e6f",
     "conflicts": [
       { "field": "r", "current": "18", "changed_by": "П. Петров", "changed_at": "2026-11-03T12:01:44Z" }
     ],
     "current_version": 9
   }
   ```

2. Поля:

   | Поле | Обязательно | Смысл |
   |---|---|---|
   | `type` | да | `https://estimator.local/problems/<slug>`; slug — `type` из errors.yaml |
   | `title` | да | `title` из errors.yaml |
   | `status` | да | HTTP-статус, совпадает со статусом ответа |
   | `code` | да | Стабильный код из errors.yaml (15.1) |
   | `detail` | нет | Пояснение для разработчика по-русски; без ПДн, секретов, денег, SQL, трассировок |
   | `error_id` | да | Идентификатор записи в логах (ULID); у 5xx — единственная связь с логом (SEC-WEB-09) |
   | `instance` | нет | Путь запроса без строки запроса |
   | расширения | по коду | Поля `extensions` кода в errors.yaml |

3. Клиент показывает пользователю текст по `code` из i18n (FR-UI-01), а не `title` и `detail`. Тексты SPEC
   в кавычках (`verbatim: true`) переносятся дословно (DESIGN.md 12).
4. Сообщения ошибок входа одинаковы для всех причин отказа (FR-AUTH-AD-13): сервер НЕ ДОЛЖЕН включать в тело
   `LOGIN_FAILED` и `LOGIN_LOCKED` поля, по которым можно отличить причину. Причина — только в аудите.
5. 5xx: тело содержит только стандартные поля; `detail` отсутствует.
6. Код, которого нет в errors.yaml, сервер отдавать НЕ ДОЛЖЕН: контрактный тест API-004 сверяет коды ответов
   с errors.yaml. Новый код добавляется в errors.yaml тем же PR, что и код сервера.
7. Ошибки WebSocket-команд — сообщение `{"op": "error", "ref": "<id команды>", "code": "<код из errors.yaml>", …}`
   с теми же кодами и расширениями (например, `CELL_LOCKED` с `locked_by` на команду `lock`); формат сообщения —
   `contracts/ws-events.schema.json` (RT-001).

## 6. Списки и пагинация

1. Пагинация — курсорная (15.1): `?cursor=<строка>&limit=<1–200>`, по умолчанию `limit=50`.
2. Ответ списка:

   ```json
   { "items": [ … ], "next_cursor": "eyJpZCI6IjAxOTJmMWM0In0" }
   ```

   `next_cursor: null` — последняя страница. Курсор непрозрачен для клиента (base64url серверной позиции,
   подписанный HMAC, чтобы его нельзя было подделать); подделанный или чужой курсор — 400 `CURSOR_INVALID`.
3. Порядок по умолчанию — по времени создания, от новых к старым (UUID v7 сортируется по времени), если
   операция не задаёт другой. Фильтры — параметры запроса с именами полей (`status=archived`,
   `discipline_id=…`); несколько значений — повтором параметра (`status=new&status=sent`).
4. Списки, которые по смыслу целиком помещаются в экран и нужны клиенту полностью (дерево, команда,
   справочники, ставки), пагинации не имеют и отдаются массивом в поле `items` без `next_cursor`.
   Дерево проекта — объект `GET /projects/{id}/tree` (до 5 000 узлов одним ответом, ARCH-03).

## 7. Версии и совместная работа

1. Изменения отправляются по REST, а не через WebSocket (ARCH-01).
2. Каждое изменение проекта увеличивает `project_version`; ответ изменяющего запроса по проекту содержит
   `project_version` (15.3). Клиент применяет события WebSocket по возрастанию `project_version` и при
   разрыве запрашивает `GET /projects/{id}/changes?since=<версия>` (FR-TREE-33). Слишком старая версия —
   410 `VERSION_TOO_OLD`, клиент перезагружает дерево (ARCH-02).
3. Правка узла несёт `base_version` — версию узла, известную клиенту. Конфликт **того же поля** —
   409 `FIELD_CONFLICT` с текущим значением; разные поля не конфликтуют (FR-TREE-32). «Оставить моё» —
   повтор запроса с `base_version = current_version`.
4. Поле, захваченное другим пользователем, — 423 `CELL_LOCKED` (FR-TREE-31).

## 8. Долгие операции, предпросмотр, подтверждение

1. Выгрузки (FR-EXP-05): `POST` создаёт задачу и отвечает `202 Accepted` с телом `{"id": "…", "status": "pending"}`
   и заголовком `Location: /api/v1/exports/{id}`. `GET /exports/{id}` отвечает `200` с
   `{"status": "pending" | "ready", …}`; при `ready` — ссылка на скачивание `download_url`. Ошибка задачи —
   409 `EXPORT_FAILED`, истёкший файл — 410 `EXPORT_EXPIRED`. Если файл готов быстрее 3 секунд, клиент сразу
   скачивает его без надписи «Готовим файл…».
2. Предпросмотр (`dry_run`): операции с отчётом перед применением (`/system/auth/switch-mode`,
   `/admin/users/{id}/replace`, включение сопоставления групп AD, выключение фазы) принимают
   `"dry_run": true` в теле и возвращают отчёт без изменений; `"dry_run": false` применяет.
3. Подтверждение последствий: если SPEC требует подтверждения, а запрос пришёл без `"confirm": true` — 409
   `CONFIRMATION_REQUIRED` с описанием последствий (5.1).

## 9. Повторы и идемпотентность

1. `GET`, `PUT`, `DELETE` идемпотентны по смыслу.
2. `POST`, создающие объект (узел, сообщение, вопрос, снимок, выгрузка, документ), ДОПУСКАЮТ заголовок
   `Idempotency-Key` (UUID, создаёт клиент на одно действие пользователя). Сервер хранит ключ 10 минут
   (в Redis, на пару «пользователь + ключ») и на повтор с тем же ключом возвращает исходный ответ без повторного
   действия. Клиент ДОЛЖЕН передавать ключ при автоматическом повторе после обрыва связи.

## 10. Заголовки

| Заголовок | Направление | Смысл |
|---|---|---|
| `X-CSRF-Token` | запрос | Раздел 3 (SEC-WEB-04) |
| `X-Background: 1` | запрос | Фоновый запрос, не продлевает сессию (FR-SESS-02) |
| `Idempotency-Key` | запрос | Раздел 9 |
| `X-Request-Id` | ответ (и запрос, если задан Nginx) | Идентификатор запроса для логов (NFR-MNT-04) |
| `Retry-After` | ответ 429, 503 | Секунды до повтора (SEC-WEB-07) |
| `Cache-Control: no-store` | ответ | Для всех `/api/*` (SEC-WEB-03) |
| `Location` | ответ 201, 202 | Адрес созданного объекта или задачи |

## 11. Лимиты

- Размер тела — 1 МБ; сертификат УЦ — 64 КБ; производственный календарь — 256 КБ; документ — 50 МБ; сообщение
  WebSocket — 64 КБ. Превышение — 413 `PAYLOAD_TOO_LARGE` (SEC-WEB-08).
- Частота — 300 изменяющих запросов в минуту, 30 выгрузок в час, 60 сообщений в обсуждениях в минуту на
  пользователя; 20 попыток входа в минуту с IP. Превышение — 429 `RATE_LIMITED` с `Retry-After`
  (SEC-WEB-07, FR-LOCK-02). «Напомнить не начавшим» — раз в сутки на проект (429 `REMIND_TOO_OFTEN`).
- Длины строк — NFR-LIM-01; в OpenAPI задаются `maxLength`/`minLength` и проверяются сервером (422).
