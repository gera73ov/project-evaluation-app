# Эталонные фикстуры расчёта (CORE-001)

Версия контракта: **0.1 (черновик до вехи M0)**. Владелец: трек CORE. Потребители: CORE-002…CORE-007 (сервер,
Python `Decimal`), FE-002 (клиент, `decimal.js`), EXP-005 (экспорт «С деньгами»), QA.
Основание: SPEC v0.5, раздел 6 целиком, 5.1, BR-CALC-01…05, BR-MONEY-02…06, BR-TREE-02/03/09, R-01, TC-CALC-01…04,
TC-MONEY-01, G-07, G-18, G-23, G-24.

| Файл | Что внутри |
|---|---|
| [`portal-dilerov.json`](portal-dilerov.json) | Дерево «Портала дилеров» (5.1), k = 18%, база УП — три фазы с работами, «Цифра для КП» = P80, ставки 6.5, USD по 92,5, НДС 20%. Ожидаемые значения листьев, узлов, дисциплин, фаз, работ, УП, итога (E, σ, P80, P90), деньги по E, P80 и P90 (строки, итоги, НДС, валюта), контрольное соотношение, объёмы по типам, «крупные» листья |
| [`edge-cases.json`](edge-cases.json) | 13 граничных случаев на деревьях (×N, свёртка и разбиение, пустые и неверные листья, нули, E = 0, база УП, ставки, RUB, «без НДС», переполнение денег) и табличные проверки функций (ROUND_HALF_UP, нормализация ввода, ×N, вместимость кэша, z-квантили) |

Обе реализации — сервер и клиент — ДОЛЖНЫ читать эти файлы как есть и давать одинаковые результаты
(SPEC 6: «расхождение клиента и сервера в тестах — дефект»).

## 1. Общий формат

```json
{
  "schema_version": 1,
  "id": "portal-dilerov",
  "title": "…",
  "spec": ["6.5", "TC-CALC-01", "…"],
  "input": { … },
  "expected": { … }
}
```

`edge-cases.json` вместо пары `input`/`expected` содержит массив `cases` (у каждого `id`, `title`, `spec`,
`input`, `expected`) и объект `functions`.

Все десятичные значения — **строки** (`"12.5"`, `"92.5"`), как в API (contracts/api-conventions.md 2.1); целые
счётчики и ×N — числа. `null` — «значения нет» (например, нет НДС или переполнение).

### 1.1. `input`

| Поле | Смысл |
|---|---|
| `project.pm_percent` | Процент УП k, строка (`"18"`); `"0"` — УП выключено |
| `project.quote_figure` | `e` / `p80` / `p90` — «Цифра для КП» (BR-MONEY-06) |
| `project.detail_level` | `coarse` / `medium` / `detailed` (для подсказки «крупный») |
| `phases[]` | `id`, `name`, `is_cross_cutting` (УП), `in_pm_base` (BR-CALC-05), `enabled` |
| `disciplines[]` | `id`, `name` в порядке строк расчёта денег и вывода |
| `nodes[]` | Плоский список узлов как в 14.3: `id`, `parent_id` (`null` у фаз), `kind` (`phase` / `discipline` / `item`), `phase_id`, `discipline_id`, `type` (название типа или `null` — «Работа», BR-TREE-08), `title`, `o`, `r`, `p` (строки; поля нет — значение пустое), `multiplier` (целое). Порядок соседей — порядок в массиве |
| `branch_status[]` | `phase_id`, `discipline_id`, `status` (`not_started` / `draft` / `done` / `not_needed`); `not_needed` исключает ветку из расчёта (BR-CALC-01) |
| `money` | Необязательно. `currency`, `exchange_rate` (₽ за 1 единицу), `vat_percent` (`null` — «без НДС»), `rates[]` — `discipline_id` (`null` — ставка УП) и `rate_rub`. Нет записи — ставка не задана (BR-MONEY-02) |

Идентификаторы — читаемые строки (`n-auth`, `d-backend`, `ph-dev`), а не UUID: тесты подставляют их как есть.

### 1.2. `expected`

Группы (в каждой — `values`; в `from_spec` — какие поля группы приведены в SPEC дословно, остальные вычислены по
формулам SPEC 6 и сверены эталонным расчётом при подготовке фикстуры):

| Группа | Ключ в `values` | Поля |
|---|---|---|
| `leaves` | id листа | `e`, `sigma`, `e_unit` (E одной штуки), `p80`, `p90` |
| `nodes` | id узла (фаза, ветка, группа) | `e`, `sigma`, `p80`, `p90`, `sum_o`, `sum_r`, `sum_p` (ΣN·O и т. д., подсказка FR-TREE-10) |
| `disciplines` | id дисциплины | Свёртка по дисциплине через все фазы: `e`, `sigma`, `p80`, `p90` |
| `phases` | id фазы | `e`, `sigma`, `p80`, `p90` |
| `works`, `pm`, `total` | — | Работы, УП (`base_e` — E базы УП, `sigma_exact` — σ_УП до округления), итог; `unaccounted_leaves` — число неучтённых листьев |
| `money.by_figure.<e\|p80\|p90>` | — | `k` (K_F, 6 знаков), `rows_rub` и `rows_cur` (id дисциплины или `pm` → сумма), `total_rub`, `vat_rub`, `total_with_vat_rub`, `total_cur`, `vat_cur`, `total_with_vat_cur`; `rates_missing` — вместо сумм, если ставки не заданы |
| `analytics` | — | Контрольное соотношение, объёмы по типам, «крупные» и «повторяющиеся» листья по порогам, широкие вилки |

`portal-dilerov.json` дополнительно содержит `money.naive_total_cur_wrong = "12398"` — неверный итог
`округл(1 146 798 / 92,5)`, который реализация НЕ ДОЛЖНА выдавать (BR-MONEY-04).

## 2. Правило сравнения

1. Реализация считает без промежуточных округлений (`Decimal` / `decimal.js`, SPEC BR-CALC-03).
2. Вычисленное значение округляется по **ROUND_HALF_UP** до числа знаков после точки в ожидаемой строке и
   сравнивается со строкой на равенство. Ожидаемое `"83.3"` — сравнение до 0,1 ч, `"83.33"` — до 0,01 ч,
   `"208333"` — до 1 ₽. Так выполняется требование TC-CALC-01 «точность 0,1 ч и 1 ₽ по округлённым значениям».
3. Деньги в `rows_*` и `total_*` — уже итоговые целые значения по правилам 6.4 (строка округляется, итог — сумма
   округлённых строк, валюта — построчно); их сравнивают без дополнительного округления.
4. `null` в ожидании означает, что значения нет: `vat_*` при «без НДС»; `k` при E = 0; `total_cur` при
   переполнении `NUMERIC(20,0)` (поле `total_cur_overflow: true`).
5. Ключи `not_expected` (в `edge-cases.json`) перечисляют значения, которые реализация выдавать НЕ ДОЛЖНА
   (например, σ = 2,3 по формуле √N).

## 3. Точные значения, на которых ошибаются реализации

| Значение | Точно | Показ | Почему важно |
|---|---|---|---|
| σ работ | 115/6 = 19,1666… (σ² = 13 225/36) | 19,17 / 19,2 | Сумма квадратов σ листьев — рациональное число; корень из него точный |
| σ УП | 0,18 · 115/6 = 3,45 | 3,5 | Пограничное значение ROUND_HALF_UP: при вычислениях с плавающей точкой получается 3,4499… → 3,4 |
| E итога | 406,51 | 406,5 | K_P80 = 425,5442 / 406,5100 = 1,046823 |
| Итог в USD по E | Σ строк = 12 397 | 12 397 | `округл(1 146 798 / 92,5)` = 12 398 — неверно (BR-MONEY-04) |

## 4. Изменение фикстур

До вехи M0 — PR трека CORE с ревью FE, EXP, QA. После M0 — через CR (contracts/README.md). Значения из SPEC
(`from_spec`) меняются только вместе со SPEC. Контрактный тест
`backend/tests/contract/test_calc_fixtures_contract.py` проверяет структуру файлов и арифметику денежных строк
(сумма строк = итог, НДС, пересчёт в валюту), но не сам расчёт: расчёт проверяют CORE-007 и FE-002.
