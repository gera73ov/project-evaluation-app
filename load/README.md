# Нагрузочный тест (QA-019)

Проверяет NFR-PERF-01 (профиль нагрузки), NFR-PERF-03 (сервер подтверждает правку O/R/P за
≤ 300 мс, p95) и NFR-PERF-04 (правка доходит до других участников за ≤ 1 с, p95). Инструмент —
Locust 2.47 и websocket-client.

| Файл | Что делает |
|---|---|
| `seed.py` | пользователи, проекты, команды и сессии по профилю NFR-PERF-01, печатает JSON со слотами |
| `locustfile.py` | поведение эксперта, замер доставки по WebSocket, проверка порогов |
| `run.sh` | сид, прогон и отчёт на развёрнутом стенде одной командой |
| `REPORT.md` | результаты прогонов |

## Профиль

- 300 экспертов `load.u001…u300` и модератор `load.moderator`. Пароля для входа у них нет:
  `seed.py` создаёт сессии напрямую, иначе 50 входов упёрлись бы в лимит 20 входов в минуту с
  одного IP.
- 30 проектов в статусе «Оценка». Первый — «Нагрузочный тест (2 000 узлов)» из `seed-demo`
  (создаётся, если его нет), остальные — «Нагрузка NN» по `--nodes` узлов (300 по умолчанию).
- В каждом проекте 15 экспертов, поровну «Бэкенд» и «Фронтенд». Эксперт может состоять в двух
  проектах: 30 × 15 = 450 мест на 300 человек.
- Locust запускает 50 одновременных пользователей (NFR-PERF-01). Первые 15 работают в проекте на
  2 000 узлов, это максимум людей в одном проекте. Остальные 35 распределены по прочим проектам.

Каждый пользователь Locust ведёт себя как эксперт. Он открывает дерево и подписывается на проект
по WebSocket. Затем каждые 3–8 секунд он делает одно из действий:

- правит O/R/P своего листа (вес 10);
- догружает изменения `GET /changes` (вес 3);
- открывает статистику (вес 1).

У каждого эксперта свои листья, поэтому правки разных людей не конфликтуют.

## Что измеряется

- **`PATCH /nodes/{id}`**: время ответа на правку, порог p95 ≤ 300 мс.
- **`WS node.updated (доставка другому участнику)`**: время от отправки PATCH автором до прихода
  события каждому из остальных подписчиков проекта. Порог p95 ≤ 1000 мс. Отметки времени ставит
  один процесс Locust, поэтому часы у них общие. По той же причине Locust запускается одним
  процессом, без `--processes`.
- Ошибки: допускается не больше 1 % запросов.
- Первые `LOAD_WARMUP` секунд (60 по умолчанию) — разогрев. За это время все пользователи
  открывают дерево и подключаются. Затем статистика сбрасывается, и пороги проверяются по
  установившемуся режиму. Отчёт HTML за весь прогон пишет сам Locust.

Если хотя бы один порог не выполнен, код выхода — 1, а в итоговой строке `QA-019: …` указана
причина.

## Запуск на стенде

```sh
load/run.sh                                   # 50 пользователей, 10 минут, отчёт в load/report
LOAD_DURATION=3m LOAD_SEED_ARGS=--mark-setup load/run.sh   # одноразовый стенд без мастера настройки
```

`run.sh` запускает сид одноразовым контейнером из образа `api` (те же `DATABASE_URL`, `REDIS_URL`
и ключ, что у API), а Locust — в контейнере из того же образа Python, что у `api`, в сети хоста.
Зависимости Locust (`requirements.txt`) ставятся при запуске, так что серверу нужен доступ к PyPI
или зеркалу. В `load/report` скрипт кладёт `report.html`, `load_stats.csv`, `summary.txt` и
`verdict.txt`. Файл со слотами содержит действующие сессии, поэтому в конце скрипт его удаляет.
На домашнем стенде то же самое запускается вручную в GitHub Actions: workflow `load`.

Чтобы генератор нагрузки не отнимал процессор у стенда, запускайте Locust с отдельной машины в
сети стенда:

- сид — на сервере: `docker compose … run --rm --no-deps -T -v "$PWD/load:/load:ro" api python
  /load/seed.py > slots.json`;
- Locust — на своей машине: `LOAD_SLOTS=slots.json LOAD_CA=ca.crt LOAD_ORIGIN=https://<стенд>
  locust -f load/locustfile.py --headless --host https://<стенд> -u 50 -r 5 -t 10m --html report.html`.

На stage Nginx балансирует две реплики `api` (SPEC 13.2), так что доставка проверяется и между
экземплярами. Без Nginx можно указать экземпляры прямо: `LOAD_HOSTS=http://api1:8000,http://api2:8000`.
Тогда пользователи раздаются по ним по кругу.

На prod `seed.py` не запускается: при `APP_ENV=prod` он отказывается работать. Нагрузочные проекты
после прогона на stage удаляются командой `estimator project purge` (CORE-090) с заявкой и
согласованием ИБ, как любой проект.
