## Что нашлось

1. **Каждая правка пересчитывает проект целиком.** Ответ PATCH содержит итоги узла, его предков
   и проекта (15.3), поэтому сервер читает все живые узлы и прогоняет расчёт. На 2 000 узлах это
   около 50 мс процессора на правку. Пока расчёт идёт, остальные запросы этого экземпляра ждут:
   у uvicorn один цикл событий на процесс. Поэтому медленнее отвечают и правки в маленьких
   проектах, которые попадают на тот же экземпляр.
2. **Правка читала лишние поля.** Для расчёта узлы загружались со всеми колонками, включая jsonb
   `field_versions` и `comment_lines`. Их разбор занимал заметную долю времени правки. Теперь
   `mutation_view` читает только колонки расчёта (`CALC_COLUMNS`), а полную строку — только для
   изменённого узла. PATCH p95 упал с 540 до 360 мс. Ответ при этом не изменился, тесты дерева
   зелёные.
3. **Двух однопроцессных реплик мало для 4 ядер.** Они загружают только 2 ядра. Число реплик
   теперь задаётся параметром `API_REPLICAS`: по умолчанию 2, как в SPEC 13.2. Nginx и Prometheus
   находят все реплики через DNS сервиса. Именно реплики, а не процессы uvicorn внутри одной: при
   нескольких процессах метрики Prometheus расходились бы между ними.

Доставка правок укладывается в норму с запасом при любом числе экземпляров. Её p99 не выше
740 мс.

В каждом прогоне была примерно 0,1 % доставок дольше 20 секунд, и причина не найдена. Это не
влияет на p95 и p99. Разобрать эти случаи надо на stage: включить там журнал событий
`node.updated` и посмотреть, на каком шаге они задерживаются.

## Что осталось для закрытия QA-019

- Прогон на stage с Nginx и генератором нагрузки на отдельной машине (`load/README.md`): сначала
  с `API_REPLICAS=2`, а если PATCH p95 больше 300 мс, то с 4.
- Если на stage и с 4 репликами порог не выполняется, нужен инкрементальный пересчёт: кэш
  расчёта проекта в памяти экземпляра, который обновляется по изменённому узлу. Это задача трека
  CORE.
